# Locale

ogis.app includes built-in multi-language support. The active language is detected
automatically from the OS/browser, with an English fallback, and updates live when
the OS/browser language changes. Nothing is stored. Every user-visible string —
core chrome and feature panels alike — resolves through the translation layer;
English is the single source language and the runtime fallback.

---

## Language resolution

The active language is resolved in this order:

1. **`?locale=` URL param** — set on the iframe `src` to control the initial locale;
   matched against the registered locale codes using script-prefix matching (below)
2. **Browser languages** — `navigator.languages` is walked in order; each code is
   matched the same way, and the first supported match wins
3. **English fallback** — `'en'` is used if no other match is found

Matching is case-insensitive and tries progressively shorter `-`-separated prefixes,
longest first: `zh-Hans-CN` → `zh-Hans` → `zh`. A registered `zh-Hans` locale therefore
serves `zh-Hans-CN`, and `fr` serves `fr-CA`. The comparison is implemented by the
exported `matchLocale(tag, codes)` helper ([`src/composables/useLocale.js:80`](../src/composables/useLocale.js#L80)).

The browser list is kept live via the `languagechange` event, so changing the
OS/browser language updates the UI and map labels without a reload.

The same raw browser language list (`navigatorLanguages`) supplies the second
tier of the cold-start country focus cascade in `useMap`: it is consulted after
the browser timezone and before the random fallback. It is independent of the
resolved app locale and `?locale=`, neither of which affects the country focus
(see [Map — cold-start country focus](./4.map.md#cold-start-country-focus)).

---

## URL param

The `?locale=` URL param sets the default language, overriding browser detection:

```html
<iframe src="/app/?locale=fr"></iframe>
```

## Available languages

Languages are auto-registered from the JSON files in `src/locales/`. Adding a
language is as simple as dropping in a new `{code}.json` file — no code change:

| Code | Language |
| ---- | -------- |
| `en` | English  |
| `fr` | Français |

## Composable API — `useLocale()`

```js
import { useLocale } from "@/composables/useLocale.js";

const {
  locale, // Ref<string>                           — active language code, e.g. 'en', 'fr'
  mapLanguageTag, // Ref<string>                           — locale code for OSM name:xx lookups
  t, // (key: string, params?: object) => string — translate, interpolate and pluralise
} = useLocale();
```

`t()` is reactive — template expressions re-evaluate when the locale changes
(including runtime OS/browser changes). Missing keys fall back to English; if also
missing from English, the key itself is returned.

**Interpolation.** `{token}` placeholders in the resolved message are replaced
with `String(params[token])`; a token without a matching parameter key is left
verbatim. There is no HTML escaping and no nested-message expansion — messages
are plain strings.

**Plurals.** When `params.count` is a number, the CLDR plural category for the
active locale is selected with `Intl.PluralRules`, and the message resolves as
`key_<category>` → `key_other` → `key` → the key string, before interpolation.
`{count}` is an ordinary token — it is not auto-injected. Plural variants are
ordinary keys, so they share the base namespace and pass through the
[completeness gate](#translation-completeness-gate) like any other key.

`useLocale()` also keeps `document.documentElement.lang` in sync with the active
locale.

## Translation keys

Keys use dot-separated namespaces that mirror the UI structure:

| Namespace           | Example key                    | English value       |
| ------------------- | ------------------------------ | ------------------- |
| `common.*`          | `common.close`                 | Close               |
| `nav.*`             | `nav.menu`                     | Menu                |
| `menu.*`            | `menu.info`                    | Info                |
| `panel.<feature>.*` | `panel.privacy.title`          | Your Privacy        |
| `locate.*`          | `locate.button.locate`         | Locate              |
| `modal.locate.*`    | `modal.locate.permissionTitle` | Permission Required |

`common.*` holds labels shared across features — for example, the close button
every modal binds to `common.close`. `menu.*` holds the menu-facing labels: the
side-panel tab strip, one per registered feature panel, plus the Info
attribution chip's label (`menu.info`). `panel.<feature>.*` gives each panel its own
namespace — the live features (`panel.recordings.*`, `panel.offline.*`,
`panel.routes.*`), the account UI (`panel.account.*`), the disabled backend
panels (`panel.maps.*`, `panel.collections.*`) and the core Info pane's sections
(`panel.about.*`, `panel.privacy.*`, `panel.info.*`, `panel.view.*`). Plural
variants are base keys with a CLDR category suffix (`panel.offline.tiles_one`,
`panel.offline.tiles_other`).

Every user-visible string in the app — core chrome and feature panels alike —
is rendered through `t()`; feature logic stays language-free (see [Message codes
and sentinel errors](#message-codes-and-sentinel-errors)).

`en.json` is the single source language: it defines the complete key set and
the English values, and every other locale file is a translation of it. At
runtime `t()` falls back to English when a key is missing from the active locale
— and to the key itself when it is missing from English too — so a missing
message cannot break the UI. In the committed tree, translations are held at
full parity by the [translation completeness
gate](#translation-completeness-gate), making that fallback a safety net rather
than the normal path.

Full list: [`src/locales/en.json`](../src/locales/en.json), [`src/locales/fr.json`](../src/locales/fr.json).

## Message codes and sentinel errors

Logic layers — composables, stores, utils and feature logic — never render
user-facing English themselves. They emit stable machine codes (plain strings
such as `map-not-ready`, `invalid-gpx`, `no-routes`, `session-load-failed` or
`magic-link-sent`), usually attached to a thrown `Error` as `.code` or held in
state. The Vue render site maps each code to a `t()` key; anything unrecognised
falls through to the raw message (or the code itself) rather than a translated
string, so the fallback is diagnostic rather than user-facing copy.

- **GPX parsing** — `parseGPX` throws errors carrying `invalid-gpx` /
  `no-routes` ([`src/features/routes/gpx.js:20`](../src/features/routes/gpx.js#L20));
  `RoutesPanel.vue` maps them to `panel.routes.errorInvalidGpx` /
  `panel.routes.errorNoRoutes` ([`RoutesPanel.vue:23`](../src/features/routes/RoutesPanel.vue#L23)).
- **Offline download** — `buildRegionUrls` throws `map-not-ready`
  ([`download.js:176`](../src/features/offline/download.js#L176)); `OfflinePanel.vue`
  maps it to `panel.offline.errorMapNotReady`.
- **Account** — the auth composables set codes such as `session-load-failed`,
  `logout-failed`, `email-required`, `too-many-attempts`, `invalid-request` and
  `request-failed`, plus the success message `magic-link-sent`; `AccountPanel.vue`
  maps them to `panel.account.*` keys
  ([`AccountPanel.vue:63`](../src/features/account/AccountPanel.vue#L63)).
- **Sync store** — a failed queue item falls back to the `sync-failed` code
  ([`src/stores/syncStore.js:76`](../src/stores/syncStore.js#L76)).

Keeping codes in the logic layer and their translations in the locale files
means every string a user can see is visible to the [completeness
gate](#translation-completeness-gate), while pure logic stays free of UI copy
and is unit-testable without a locale.

## Locale-aware formatting

Numbers are formatted with the active locale through `Intl.NumberFormat`, so
values read naturally in every language:

- **Distances** — `formatDistance(metres, isMetric, locale)` formats the number
  and unit symbol via the `unit` style, with no digit grouping
  ([`src/utils/geo.js:53`](../src/utils/geo.js#L53)). French renders comma
  decimals and Intl's narrow no-break space before the unit symbol (`2,35 km`),
  while English produces exactly what the previous fixed-point formatter did —
  deliberately, so English E2E assertions and the screenshot matrix stay stable.
- **Download sizes** — the Offline panel formats byte sizes for `MB`/`KB`/`B`
  the same way ([`OfflinePanel.vue:205`](../src/features/offline/OfflinePanel.vue#L205)).

Values are pre-rounded before localisation, so only the separators and unit
symbols differ between locales.

## Contributing a translation

1. Copy `src/locales/en.json` to `src/locales/{code}.json`
2. Keep `en.json`'s keys and their order. Full key parity is required in both
   directions — the completeness gate fails on a key missing from the
   translation and on a key that only the translation defines (dead or
   misspelled). Plural variants (`key_one`, `key_other`, …) are ordinary keys
   and follow the same parity rule.
3. Translate every value. Empty values fail, and a value left identical to
   English fails unless the key is recorded in the allowlist (step 4).
4. If the accepted form in the target language genuinely matches the English
   string — a cognate or loanword — add the key to `UNTRANSLATED_ALLOWLIST` in
   `tests/unit/locales.test.js`. That is a deliberate, reviewed decision, never
   a shortcut for a key still awaiting translation.

The file is discovered automatically; there is no registration step. For script-variant
languages use the full BCP 47 filename: `zh-Hans.json`, `zh-Hant.json`, `sr-Latn.json`.
The prefix matcher then resolves regional variants down to that file — `zh-Hans-CN`
matches `zh-Hans` without an extra regional file.

## Translation completeness gate

[`tests/unit/locales.test.js`](../tests/unit/locales.test.js) audits every
locale file against `en.json` so that drift cannot leak raw keys or
untranslated strings into the UI. It is an ordinary unit test — no separate
script — so it runs with `npm test`, in the `npm run check` pre-push gate, and
in CI's unit job.

For each `src/locales/*.json` file the gate enforces:

- **Key parity with `en.json` in both directions** — a missing key fails, and
  so does an extra key that `en.json` does not define.
- **No empty or whitespace-only values** — an empty string would render as
  blank UI.
- **No value left identical to English** — unless the key is allowlisted for
  that locale. The in-file `UNTRANSLATED_ALLOWLIST` records cognates and
  loanwords whose accepted form is the same string as English; adding an entry
  is a deliberate, reviewed decision.
- **Every literal `t("…")` key in `src/` exists in `en.json`** — catches typos
  that would otherwise leak the raw key string into the UI.
- **Dynamic `t(...)` arguments are rejected** — the gate can only verify literal
  keys, so every `t()` call must pass a single- or double-quoted string, or a
  template literal without `${…}` interpolation. A variable, a function call or
  an interpolated template fails with the offending call cited.

> [!NOTE]
> The allowlist lives in the test file, beside the rule it relaxes, so the gate
> stays self-contained and every exception is visible in review.

The English fallback in `t()` remains as a runtime safety net (see
[Composable API](#composable-api--uselocale)), but a committed translation is
expected to be complete: `en.json` is the single source language and the
reference key set.

## OSM multilingual names

ogis.app locale codes align with the [OSM multilingual names convention](https://wiki.openstreetmap.org/wiki/Multilingual_names). Every locale code is a valid OSM `name:xx` tag suffix — no conversion needed.

Map labels update automatically when the OS/browser language changes. On `style.load`, `useMap` applies the following coalesce expression to every symbol layer whose `text-field` references an OSM name field (road refs and other non-name fields are left untouched):

```js
[
  "coalesce",
  ["get", "name:fr"], // preferred language
  ["get", "name"], // local / native name
  ["get", "name:en"], // English fallback
];
```

The expression is re-applied reactively whenever `mapLanguageTag` changes.

```js
const { mapLanguageTag } = useLocale();
// mapLanguageTag.value === 'fr' when French is active
```
