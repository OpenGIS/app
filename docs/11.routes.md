# Routes — GPX/GeoJSON import and navigation

The Routes feature imports GPX and GeoJSON files, renders each route or waypoint
document on the map, and provides offline follow-mode navigation via Locate,
with a direction and distance readout in the core top-centre navigation card.
Like Recordings, it is a panel-only feature: its panel is registered with
`addPanel` and it ships no corner control chip — a chip is optional feature UI,
not a requirement.

---

## Overview

Routes is the import counterpart to the Recordings feature. It consumes the
canonical [`v: 2` track model](./15.tracks.md): imported GPX/GeoJSON is parsed
into route documents (and, when needed, a waypoint-only document), persisted in
`localStorage`, and projected to GeoJSON only for rendering. Imported routes
start hidden; visibility and navigation ownership are persisted in a separate
tab-owned navigation store in `sessionStorage` and restored without moving the
camera.

## Storage

Routes are stored as an array of v2 documents under the standard instance-scoped
key:

```
ogis_routes_{instanceId}
```

```js
const routes = useStorage("routes", {
  version: 1,
  defaults: [],
  hydrate: hydrateRoutes,
  crossTab: true,
  onSync: () => reconcileRoutes(),
}).state; // src/features/routes/index.js:42
```

Values are written as a versioned envelope, not a bare array. `hydrateRoutes`
migrates legacy route shapes, sanitises every document and point, drops invalid
documents and keeps the **first** document when two share an id
([`hydrateRoutes`](../src/resilience/hydrators/routes.js#L14)). A stored route
is a track document; the full field reference is in
[Tracks — Document shape](./15.tracks.md#document-shape). The common fields
are:

```js
{
  v: 2,
  id: "m1abc2d-x9k2p1q7",
  kind: "route",              // or "waypoints"
  name: "Morning Loop",
  gpxType: "trk",             // or "rte" / null
  createdAt: null,
  source: { format: "gpx", filename: "morning.gpx", groupId: "…", index: 0 },
  segments: [{ points: [{ lat: 48.949011, lng: -55.652574, ele: 42 }] }],
  waypoints: [],
  color: "#3498db",
}
```

On hydrate, legacy route shapes are migrated with
[`migrateRoute`](../src/utils/track/model.js#L34) and sanitised with
`sanitiseTrackDocument`; missing colours are then assigned
([`index.js:49`](../src/features/routes/index.js#L49)). The storage key is
unchanged. A legacy bare array remains bare until the first mutation, then the
normal write path emits an envelope. Only routes recorded as visible are
re-rendered on install; see [Visibility](#visibility).

Route visibility and navigation ownership are stored separately in tab-owned
`sessionStorage` under `ogis_navigation_{instanceId}` (version 1):

```js
{ routeId: "m1abc2d-x9k2p1q7", visible: ["m1abc2d-x9k2p1q7"], followOwned: true }
```

`routeId` is `null` when nothing is navigating, `visible` is the set of shown
route ids, and `followOwned` records whether navigation started the follow
session. The hydrator trims ids, dedupes `visible`, adds a navigated route to
`visible`, and keeps `followOwned` only alongside a route. See
[State and resilience — Route visibility and navigation restore](./16.state-and-resilience.md#route-visibility-and-navigation-restore).

## Import

[`importTracks(files)`](../src/features/routes/index.js#L311) parses files
sequentially with
[`parseTrackFile`](../src/utils/track/import.js#L568). A failure in one file
does not discard successful imports from the others; the last failure is kept
in `error` for the panel.

- Supported formats: GPX and GeoJSON, detected from content rather than file
  extension.
- Multiple files can be selected at once.
- A file may produce several documents: multiple lines become separate route
  rows, and waypoints become a sibling waypoint document when there is more
  than one line.
- Files are capped at 10 MB.
- Imported documents are appended to the stored array but are **not** shown on
  the map until the user presses Show.

Parsing details and the supported subset are documented in
[Tracks — Import](./15.tracks.md#import).

## Rendering

`renderRoute(route)` ([`index.js:138`](../src/features/routes/index.js#L138))
projects the document to map features:

```js
geoJSON.setFeature({
  type: "Feature",
  id: `routes-route-${route.id}`,
  geometry: lineGeometry(route), // LineString or MultiLineString
  properties: {
    "ogis.color": route.color,
    "ogis.width": 4,
    "ogis.opacity": 0.85,
    "ogis.direction": true,
  },
});
```

- The line geometry is built with `lineGeometry`; segments with fewer than two
  valid points are omitted, and multiple usable segments become a
  `MultiLineString`.
- Waypoints are rendered as separate point features with a 5 px radius in the
  same colour.
- The stored colour is used, so a route keeps its swatch and map colour across
  sessions.
- `ogis.direction: true` renders the static direction chevrons described in
  [GeoJSON — Direction chevrons](./6.geojson.md#direction-chevrons). Direction
  follows point order, not timestamps or bearing data.

`showOnMap(id, options)` ([`index.js:201`](../src/features/routes/index.js#L201))
takes `{ fit = true, claim = true, persist = true }`. A normal Show claims the
map (`claimMap()`) — ending any active follow, draw or navigation mode as a
hand-off — then renders the route, persists visibility and fits the map to its
bounds, including waypoints, with 40 px padding. A normal Show claims the map
first, so an active follow is ended as a hand-off before the fit. Locate keeps
tracking, but its chip reads Located while the camera moves to the route.

Restore calls the same function with `{ fit: false, claim: false, persist: false }`,
so it renders without moving the camera, taking ownership or rewriting storage.
`hideOnMap(id)` ([`index.js:250`](../src/features/routes/index.js#L250))
removes the line and waypoint features and updates the store. Hiding or deleting
the route that is currently navigating also ends navigation
([`index.js:250`](../src/features/routes/index.js#L250),
[`index.js:265`](../src/features/routes/index.js#L265)). See
[UI actions and map modes](./5.ui.md#ui-actions-and-map-modes).

### Visibility

Visibility is a `Set` of document ids mirrored into `navigation.visible`
([`index.js:64`](../src/features/routes/index.js#L64),
[`index.js:182`](../src/features/routes/index.js#L182)):

- Imported routes start hidden.
- `toggleVisibility(id)` drives the row's Show/Hide button.
- Show/Hide and delete persist the new set; a stale id with no matching route
  document is pruned when visibility is restored.
- Visible routes are re-rendered on install **without** fitting the camera,
  claiming the map or changing the stored view.
- `navigation` is version 1 and instance-scoped; its `visible` list is the
  source of truth for the next load.

### Cross-tab sync

Route documents are shared content and sync live between tabs. When another tab
writes `ogis_routes_{instanceId}`, the receiving store replaces the array
contents and [`reconcileRoutes()`](../src/features/routes/index.js#L281) runs
([`index.js:46-47`](../src/features/routes/index.js#L46-L47)):

- colours are filled for any document that lacks one;
- a visible route that no longer exists has its line and waypoint features
  removed and leaves the in-memory `visible` set, persisting the pruned set;
- a visible route that still exists is re-rendered from its new document,
  removing its previously rendered features first so no duplicate ids remain;
- navigation stops when its route disappears, which also releases an owned
  follow and persists `routeId: null`.

Last-writer-wins applies: the replacement array contents are not merged with the
local ones. Visibility and navigation ownership stay tab-owned and are never
synced.

## Navigation

Navigation is follow-mode guidance, not turn-by-turn routing. It reuses Locate's
existing [following state](./4.map.md#view-orientation) and follow camera rather
than fitting or recentring the map. The feature registers a `navigate` mode
with [`useActions`](../src/features/routes/index.js#L488), alongside `follow`,
and `startNavigation(id)` claims the map with `navigate` excluded so the mode
about to start is not stopped.

`startNavigation(id)` ([`index.js:332`](../src/features/routes/index.js#L332))
requires the route to have a renderable line and to be visible. Line-less rows
have no Navigate button, and the button is disabled while the route is hidden
(see [Panel UI](#panel-ui)). It calls
[`locate.startFollowing`](../src/composables/useLocate.js#L759), which:

- enters following immediately when Locate is already active;
- shows the first-use permission confirmation, then starts watching and enters
  following straight away, when Locate is inactive;
- re-opens the error modal instead of starting when Locate is in its error
  state.

Navigation becomes active only when following actually begins — a cancelled
permission prompt or a geolocation error leaves the route rows untouched. On
start the side panel closes, and the existing follow camera takes over unchanged;
there is no route fit or recentre. While one route is navigating, Navigate is
disabled on every other route.

When following starts, the feature writes `navigation.routeId` and
`navigation.followOwned`. `followOwned` is `true` only when navigation started
the follow itself; if the user was already following, it stays `false` so Stop
leaves their follow running.

`stopNavigation()` ([`index.js:235`](../src/features/routes/index.js#L235))
clears navigation state and removes the connector, then persists `routeId: null`
and `followOwned: false` without touching `visible`. It stops Locate only when
navigation itself started the follow (`followOwned`). Navigation also ends when:

- the navigating route is hidden or deleted
  ([`index.js:250`](../src/features/routes/index.js#L250),
  [`index.js:265`](../src/features/routes/index.js#L265));
- Locate leaves the following state for any reason — a geolocation error, the
  Locate chip stopping the watch, or the user stopping Locate
  ([`index.js:462`](../src/features/routes/index.js#L462)). Navigation clears
  without calling `locate.stop()` again.

The feature's `onCleanup` registrations stop the navigation indicator and locate-mode watcher and unbind the map-bearing listeners on app destroy ([`index.js:468-470`](../src/features/routes/index.js#L468-L470)). `RoutesFeature.install` also returns a teardown ([`index.js:517`](../src/features/routes/index.js#L517)) that stops the navigation indicator, unregisters the `navigate` mode, stops navigation, unbinds the map-bearing listeners and clears menu navigation. `installFeature` registers that returned function through the same cleanup registry as `onCleanup`, so it runs on app destroy rather than during install ([`boot.js:120-132`](../src/resilience/boot.js#L120-L132)). See [State and resilience — Feature install isolation](./16.state-and-resilience.md#feature-install-isolation).

### Navigation restore

Navigation is restored across a reload, not discarded:

1. Route visibility restores during install, without fitting or claiming the
   camera.
2. `restoreNavigation()` ([`index.js:372`](../src/features/routes/index.js#L372))
   runs non-blocking and awaits `locate.restoreComplete`.
3. Navigation resumes only when locate re-entered `following`, the route still
   exists and it has usable line geometry.
4. A navigation action while the restore is pending wins; the restore leaves
   that state alone.
5. A restored navigation never fits or claims the camera — the normal follow
   restore owns the camera path.

Failures are silent. A missing route, no usable line geometry, a denied
permission or locate not re-entering following clears `routeId`/`followOwned`
but leaves the visibility list untouched (a missing route id is pruned). A
restored navigation that owned follow stops locate when navigation stops; a
user-owned follow survives Stop.

### Top-centre navigation card

Navigation status is core chrome in the top-centre corner cluster
(`.ogis-corner--tc`): [`NavigationControl.vue`](../src/features/routes/NavigationControl.vue)
renders a full-size frosted-glass card (`.ogis-nav-control`). Routes publishes its
state through `useUI().setMenuNavigation`
([`index.js:458`](../src/features/routes/index.js#L458)). The menu chip is back to
the recording badge only — it no longer carries navigation status.

The card is visual only: `pointer-events: none`, with `role="status"`,
`aria-live="off"` and the status text exposed through `aria-label`
(`navigation.title`).

| State     | Top-centre card                                                                       |
| --------- | ------------------------------------------------------------------------------------- |
| Locating  | Dimmed arrow and ellipsis until the first fix; the accessible label reads `Locating…` |
| Off route | Arrow rotated relative to the current map bearing, plus a compact distance            |
| On route  | Check and `On route`, within `ON_ROUTE_METRES` (5 m) of the route                     |

Off-route distances use the compact `formatCompactDistance` formatter so the card
stays short; the card's accessible label carries the full localised distance
(`navigationOffRoute`). When off route and within 1 km, a green dashed SVG
connector (`.ogis-nav-connector`) joins the locate marker to the nearest point on
the route: it is a screen-space overlay teleported to `<body>`, projected along a
geodesic ([`geodesicLine`](../src/utils/track/navigation.js#L56)) and re-projected
on map move and resize. It starts at the locate marker's centre and ends at the
projected nearest route point — there is no separate target marker. The stroke is
the theme primary green (`var(--bs-primary)`, `#39d353`), 3 px at 0.9 opacity,
dashed `6 6` with butt caps. Because it is drawn above the map canvas it is never
occluded by terrain or 3D buildings; it is not a GeoJSON feature, so it adds no
route-navigation feature to the map.

The connector is removed when on route, when the nearest point is farther than
1 km away, and when navigation stops. Beyond 1 km the card still shows the
compact distance, but no connector is drawn.

Navigation works offline because it is entirely client-side (GPS + stored
geometry); the map background still relies on the [Offline](./12.offline.md) tile
download. Far-away fixes are also the hardest case for Locate's HTML markers: a
terrain DEM error can abort MapLibre's move dispatch, so `useLocate` re-syncs the
marker on map `idle` and `moveend` with a bounded 120 s retry (see
[Testing — Routes navigation coverage](./9.testing.md#routes-navigation-coverage)).

## Shared geo helpers

`src/utils/geo.js` holds the distance/format helpers shared by Recordings and
Routes:

| Function                                                 | Returns                                                            |
| -------------------------------------------------------- | ------------------------------------------------------------------ |
| `haversine(a, b)`                                        | Great-circle distance between two `{ lat, lng }` points, in metres |
| `totalDistance(points)`                                  | Sum of haversine segments, in metres                               |
| `formatDuration(ms)`                                     | `H:MM:SS` or `M:SS`                                                |
| `formatDistance(metres, isMetric = true, locale = "en")` | `km`/`m` or `mi`/`ft` string, formatted for `locale`               |
| `formatCompactDistance(metres, isMetric = true, locale)` | Short `km`/`m` or `mi`/`ft` string for the top-centre card         |

The track model adds multi-segment helpers on top:
`documentDistance` (per-segment distance), `documentBounds`, `lineGeometry`,
`documentPointCount` and `waypointCount`
([`src/utils/track/model.js`](../src/utils/track/model.js)), plus
`nearestPointOnTrack` and `ON_ROUTE_METRES` for navigation status
([`src/utils/track/navigation.js`](../src/utils/track/navigation.js)).
Recordings re-exports `formatDuration`/`formatDistance` for its panel
([`src/features/recordings/index.js:27`](../src/features/recordings/index.js#L27));
Routes imports `formatCompactDistance` and `formatDistance`
([`index.js:7`](../src/features/routes/index.js#L7)).

## Panel UI

`RoutesPanel.vue` provides:

- a file input accepting `.gpx`, `.geojson`, `.json` and their MIME types,
  with multiple selection; each file goes through `importTracks`
- an error line translating the importer's sentinel code to a
  `panel.routes.error*` message, falling back to the generic
  `panel.routes.errorImport` — never the raw error
- a row per document with a colour swatch, name (falling back to
  `panel.routes.defaultName`), locale-formatted distance, waypoint count when
  present, Show/Hide, Navigate/Stop where the document has a line, a Share menu
  (GPX or GeoJSON) and Delete behind a native `window.confirm`
- Navigate is disabled while the route is hidden (`navigateHidden`) or while
  another route is navigating (`navigateBusy`); its title explains why. The
  navigating row shows Stop in place of Navigate.

The panel does not carry a navigation banner — status lives in the top-centre
navigation card (see [Navigation](#navigation)). Every string in the panel
resolves through `t()` —
`menu.routes` for the tab and heading, `panel.routes.*` for the rest. Import
errors surface through the importer's sentinel codes, mapped to
`panel.routes.errorInvalidGpx`,
`panel.routes.errorInvalidGeoJSON`, `panel.routes.errorUnsupported`,
`panel.routes.errorTooLarge` and `panel.routes.errorNoRoutes` (see
[Locale — Message codes and sentinel errors](./7.locale.md#message-codes-and-sentinel-errors)).

Sharing uses [`shareTrack`](../src/features/routes/index.js#L476), which builds
GPX or GeoJSON with `toGPX`/`toGeoJSON`, names the file with `trackFilename`,
and calls `shareFile` (Web Share API, otherwise a download). A non-abort share
failure is reported through `reportError` and falls back to the download; an
`AbortError` stays silent. See [Tracks — Export](./15.tracks.md#export) for the
download-failure path. GPX/GeoJSON round-trip caveats are covered in
[Tracks — Round-trip caveats](./15.tracks.md#round-trip-caveats).

## Limitations

- **Storage quota.** Documents are stored as-is in `localStorage` (5 MB per
  origin); large tracks may not fit.
- **No editing.** Points cannot be reordered, trimmed or edited in the UI.
- **GPX/GeoJSON subset.** GPX extensions and several optional elements are not
  modelled; unsupported GeoJSON geometry types reject the file. See
  [Tracks — Round-trip caveats](./15.tracks.md#round-trip-caveats).
- **Visibility is persisted per route.** Imported routes still start hidden,
  but a visible route reappears after a reload without moving the camera.
- **Separate sharing.** A multi-document import exports one file per row.
- **No turn-by-turn guidance.** Navigation follows the user and indicates the
  distance back to the route; it has no turn instructions, arrival estimates,
  progress along the route or re-routing.
- **Navigation restore is conditional.** Navigation resumes after a reload in
  the same tab only when locate restores into following; a denied or unavailable
  geolocation session clears navigation and keeps route visibility. Another tab
  never restores it.
- **Route content is shared and live; navigation is tab-owned.** Route
  documents live in `localStorage` and sync between tabs, while visibility and
  navigation ownership live in `sessionStorage` per tab. Restore uses the last
  successful write: a normal reload restores visibility and navigation, while a
  hard kill or force-quit can lose the most recent debounced route change. See
  [State and resilience — Limitations and deliberate exclusions](./16.state-and-resilience.md#limitations-and-deliberate-exclusions).
- **Offline map background** depends on the Offline feature's downloaded tiles.

> [!NOTE]
> At very distant locations the basemap can render with partial tiles or
> "Map data not available". This comes from a pre-existing MapLibre terrain/DEM
> tile error and slow external tiles, not from the navigation connector or
> control. The locate marker re-syncs on `idle`/`moveend` with the bounded 120 s
> retry, but slow external tile loading can still delay it.
