# Routes — GPX/GeoJSON import and navigation

The Routes feature imports GPX and GeoJSON files, renders each route or waypoint
document on the map, and provides offline follow-mode navigation via Locate,
with a direction and distance readout in the core top-centre navigation card.
It is a panel-only feature: its panel is registered with `addPanel` and it ships
no corner control chip — a chip is optional feature UI, not a requirement.

---

## Overview

Routes consumes the canonical [`v: 2` track model](./15.tracks.md): imported
GPX/GeoJSON is parsed into route documents (and, when needed, a waypoint-only
document), persisted in `localStorage`, and projected to GeoJSON only for
rendering. Imported routes start hidden; visibility and navigation ownership
are persisted in a separate durable navigation store in `localStorage` and
restored without moving the camera.

| File                                                                            | Purpose                                                    |
| ------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| [`src/features/routes/index.js`](../src/features/routes/index.js)               | Feature object, storage, rendering, visibility, navigation |
| [`src/features/routes/RoutesPanel.vue`](../src/features/routes/RoutesPanel.vue) | Side panel UI                                              |
| [`src/utils/track/index.js`](../src/utils/track/index.js)                       | Canonical model, import/export and document helpers        |
| [`src/utils/share.js`](../src/utils/share.js)                                   | Web Share API with download fallback                       |
| [`src/utils/geo.js`](../src/utils/geo.js)                                       | Shared distance and formatting helpers                     |

Registered in [`src/main.js:185`](../src/main.js#L185) — the only core feature
installed in SPA front-end only mode. The panel is registered via `addPanel`
([`index.js:550`](../src/features/routes/index.js#L550)) and appears as a tab in
the side panel navigation — Routes registers no feature corner chip; the
top-left menu chip is core chrome and shares the `menu.routes` label.

## Storage

Routes are stored as an array of v2 documents under the standard instance-scoped
key:

```
ogis_routes_{instanceId}
```

```js
const routes = useStorage("routes", {
  version: 1,
  defaults: [],
  hydrate: hydrateRoutes,
  crossTab: true,
  onSync: () => reconcileRoutes(),
}).state; // src/features/routes/index.js:47
```

Values are written as a versioned envelope, not a bare array. `hydrateRoutes`
migrates legacy route shapes, sanitises every document and point, drops invalid
documents and keeps the **first** document when two share an id
([`hydrateRoutes`](../src/resilience/hydrators/routes.js#L14)). A stored route
is a track document; the full field reference is in
[Tracks — Document shape](./15.tracks.md#document-shape). The common fields
are:

```js
{
  v: 2,
  id: "m1abc2d-x9k2p1q7",
  kind: "route",              // or "waypoints"
  name: "Morning Loop",
  gpxType: "trk",             // or "rte" / null
  createdAt: null,
  source: { format: "gpx", filename: "morning.gpx", groupId: "…", index: 0 },
  segments: [{ points: [{ lat: 48.949011, lng: -55.652574, ele: 42 }] }],
  waypoints: [],
  color: "#3498db",
}
```

On hydrate, legacy route shapes are migrated with
[`migrateRoute`](../src/utils/track/model.js#L34) and sanitised with
`sanitiseTrackDocument`; missing colours are then assigned
([`index.js:54`](../src/features/routes/index.js#L54)). The storage key is
unchanged. A legacy bare array remains bare until the first mutation, then the
normal write path emits an envelope. Only routes recorded as visible are
re-rendered on install; see [Visibility](#visibility).

Route visibility and navigation ownership are stored in a separate durable
`localStorage` store, `ogis_navigation_{instanceId}` (version 2). It is created
after the one-time session-storage migration and never opts into cross-tab sync
([`index.js:56-70`](../src/features/routes/index.js#L56-L70)):

```js
migrateSessionToLocal("navigation", instanceId);

const navigationStore = useStorage("navigation", {
  version: 2,
  storage: "local",
  defaults: {
    routeId: null,
    visible: [],
    followOwned: false,
    ownerId: null,
  },
  hydrate: hydrateNavigation,
});
```

Its persisted shape is:

```js
{
  routeId: "m1abc2d-x9k2p1q7",
  visible: ["m1abc2d-x9k2p1q7"],
  followOwned: true,
  ownerId: "1f0c9c4e-6b2a-4f7e-9f1e-2a3b4c5d6e7f"
}
```

`routeId` is `null` when nothing is navigating, `visible` is the set of shown
route ids, `followOwned` records whether navigation started the follow session,
and `ownerId` names the tab that owns the navigating session. The hydrator
trims ids, dedupes `visible`, adds a navigated route to `visible`, and keeps
`followOwned` and a non-empty `ownerId` only alongside a route. See
[State and resilience — Route visibility and navigation restore](./16.state-and-resilience.md#route-visibility-and-navigation-restore).

## Import

[`importTracks(files)`](../src/features/routes/index.js#L328) parses files
sequentially with
[`parseTrackFile`](../src/utils/track/import.js#L568). A failure in one file
does not discard successful imports from the others; the last failure is kept
in `error` for the panel.

- Supported formats: GPX and GeoJSON, detected from content rather than file
  extension.
- Multiple files can be selected at once.
- A file may produce several documents: multiple lines become separate route
  rows, and waypoints become a sibling waypoint document when there is more
  than one line.
- Files are capped at 10 MB.
- Imported documents are appended to the stored array but are **not** shown on
  the map until the user presses Show.

Parsing details and the supported subset are documented in
[Tracks — Import](./15.tracks.md#import).

## Rendering

`renderRoute(route)` ([`index.js:148`](../src/features/routes/index.js#L148))
projects the document to map features:

```js
geoJSON.setFeature({
  type: "Feature",
  id: `routes-route-${route.id}`,
  geometry: lineGeometry(route), // LineString or MultiLineString
  properties: {
    "ogis.color": route.color,
    "ogis.width": 4,
    "ogis.opacity": 0.85,
    "ogis.direction": true,
  },
});
```

- The line geometry is built with `lineGeometry`; segments with fewer than two
  valid points are omitted, and multiple usable segments become a
  `MultiLineString`.
- Waypoints are rendered as separate point features with a 5 px radius in the
  same colour.
- The stored colour is used, so a route keeps its swatch and map colour across
  sessions.
- `ogis.direction: true` renders the static direction chevrons described in
  [GeoJSON — Direction chevrons](./6.geojson.md#direction-chevrons). Direction
  follows point order, not timestamps or bearing data.

`showOnMap(id, options)` ([`index.js:213`](../src/features/routes/index.js#L213))
takes `{ fit = true, claim = true, persist = true }`. A normal Show claims the
map (`claimMap()`) — ending any active follow or navigation mode as a
hand-off — then renders the route, persists visibility and fits the map to its
bounds, including waypoints, with 40 px padding. A normal Show claims the map
first, so an active follow is ended as a hand-off before the fit. Locate keeps
tracking, but its chip returns to the active presentation (Located once a fix exists) while the camera moves to the route.

Restore calls the same function with `{ fit: false, claim: false, persist: false }`,
so it renders without moving the camera, taking ownership or rewriting storage.
`hideOnMap(id)` ([`index.js:267`](../src/features/routes/index.js#L267))
removes the line and waypoint features and updates the store. Hiding or deleting
the route that is currently navigating also ends navigation
([`index.js:267`](../src/features/routes/index.js#L267),
[`index.js:282`](../src/features/routes/index.js#L282)). See
[UI actions and map modes](./5.ui.md#ui-actions-and-map-modes).

### Visibility

Visibility is a `Set` of document ids mirrored into `navigation.visible`
([`index.js:74`](../src/features/routes/index.js#L74),
[`index.js:192`](../src/features/routes/index.js#L192)):

- Imported routes start hidden.
- `toggleVisibility(id)` drives the row's Show/Hide button.
- Show/Hide and delete persist the new set; a stale id with no matching route
  document is pruned when visibility is restored.
- Visible routes are re-rendered on install **without** fitting the camera,
  claiming the map or changing the stored view.
- `navigation` is version 2 and instance-scoped; its `visible` list is the
  source of truth for the next load.

### Cross-tab sync

Route documents are shared content and sync live between tabs. When another tab
writes `ogis_routes_{instanceId}`, the receiving store replaces the array
contents and [`reconcileRoutes()`](../src/features/routes/index.js#L298) runs
([`index.js:51-52`](../src/features/routes/index.js#L51-L52)):

- colours are filled for any document that lacks one;
- a visible route that no longer exists has its line and waypoint features
  removed and leaves the in-memory `visible` set, persisting the pruned set;
- a visible route that still exists is re-rendered from its new document,
  removing its previously rendered features first so no duplicate ids remain;
- navigation stops when its route disappears, which also releases an owned
  follow and persists `routeId: null`.

Last-writer-wins applies: the replacement array contents are not merged with the
local ones. The navigation store never opts into live cross-tab sync. Route
visibility is durable per instance and restored on install in every tab. Active
navigation is tab-owned through `ownerId`: a second live tab restores
visibility, checks the owner's liveness — the owner's Web Lock first, with a
`BroadcastChannel` fallback — and does not restore or clear the owner's
navigation session. A restore deferred because another live tab owns the locate
session normally leaves the navigation document untouched too; only a stale
entry this tab can claim is cleared.

## Navigation

Navigation is follow-mode guidance, not turn-by-turn routing. It reuses Locate's
existing [following state](./4.map.md#view-orientation) and follow camera rather
than fitting or recentring the map. Navigation follows the user, so it requires
a compass-capable device: on an incapable device Navigate is visible but
disabled with the `panel.routes.navigateNoCompass` title, and `startNavigation`
refuses before any side effect — no map claim, no permission prompt and no
navigation state. Routes remain viewable and editable. The feature registers a
`navigate` mode
with [`useActions`](../src/features/routes/index.js#L564), alongside `follow`,
and `startNavigation(id)` claims the map with `navigate` excluded so the mode
about to start is not stopped.

`startNavigation(id)` ([`index.js:349`](../src/features/routes/index.js#L349))
requires the route to have a renderable line and to be visible. Line-less rows
have no Navigate button, and the button is disabled while the route is hidden
(see [Panel UI](#panel-ui)). It calls
[`locate.startFollowing`](../src/composables/useLocate.js), which:

- enters following immediately when Locate is already active, even before the
  first fix;
- shows the first-use permission confirmation, then starts watching and enters
  following straight away when Locate is inactive, without waiting for a fix;
- re-opens the error modal instead of starting when Locate is in its error
  state.

On an incapable device the call is refused before any side effect:
`startFollowing` returns false, never calls `onStarted`, and navigation cannot
claim a follow the device cannot support. On a capable device with no live
heading, navigation still runs: the follow camera stays flat and north-up until
a heading arrives.

Navigation becomes active when following actually begins, which may be before
the first position fix; the top-centre card then shows its own Locating… state
until a position exists. A cancelled permission prompt, an unsupported
geolocation API or a synchronous watcher failure that prevents following from
starting leaves the route rows untouched. Once following has begun, a later
geolocation error ends Locate and therefore navigation by design; the stop path
does not call `locate.stop()` again. On start the side panel closes, and the
existing follow camera takes over unchanged; there is no route fit or recentre.
While one route is navigating, Navigate is disabled on every other route.

When following starts, the feature writes `navigation.routeId` and
`navigation.followOwned`. `followOwned` is `true` only when navigation started
the follow itself; if the user was already following, it stays `false` so Stop
leaves their follow running.

`stopNavigation()` ([`index.js:247`](../src/features/routes/index.js#L247))
clears navigation state and removes the connector, then persists `routeId: null`
and `followOwned: false` without touching `visible`. It stops Locate only when
navigation itself started the follow (`followOwned`). Navigation also ends when:

- the navigating route is hidden or deleted
  ([`index.js:267`](../src/features/routes/index.js#L267),
  [`index.js:282`](../src/features/routes/index.js#L282));
- Locate leaves the following state for any reason — a geolocation error, the
  Locate chip stopping the watch, or the user stopping Locate
  ([`index.js:531`](../src/features/routes/index.js#L531)). Navigation clears
  without calling `locate.stop()` again.

The feature's `onCleanup` registrations stop the navigation indicator and locate-mode watcher, unbind the map-bearing listeners and stop the session-probe listener on app destroy ([`index.js:543-546`](../src/features/routes/index.js#L543-L546)). `RoutesFeature.install` also returns a teardown ([`index.js:593`](../src/features/routes/index.js#L593)) that stops the navigation indicator, unregisters the `navigate` mode, stops navigation, unbinds the map-bearing listeners and clears menu navigation. `installFeature` registers that returned function through the same cleanup registry as `onCleanup`, so it runs on app destroy rather than during install ([`boot.js:127-132`](../src/resilience/boot.js#L127-L132)). See [State and resilience — Feature install isolation](./16.state-and-resilience.md#feature-install-isolation).

### Navigation restore

Navigation is restored after a reload or app quit, not discarded:

1. Route visibility restores during install, without fitting or claiming the
   camera. IDs with no matching route document are pruned.
2. `restoreNavigation()` ([`index.js:392`](../src/features/routes/index.js#L392))
   runs non-blocking. A stored owner from another tab is checked for liveness —
   the owner's Web Lock first, with a per-instance `BroadcastChannel` fallback;
   while it is alive, the restore stops and leaves the stored session untouched.
3. It validates the stored route and line geometry before touching storage, so a
   missing route or unusable line clears navigation rather than leaving a
   dangling entry.
4. It shows the stored route with
   `showOnMap(id, { fit: false, claim: false, persist: false })`: the line and
   waypoints render in memory, without fitting the camera, claiming it or
   writing ownership.
5. It awaits `locate.restoreComplete`.
6. It re-checks whether the user navigated or changed state while the restore
   was pending; if so, the restore leaves that state alone.
7. When locate reports `restoreDeferred` because another live tab owns the
   locate session, the route restore does not claim navigation. It leaves the
   live owner's navigation document alone, except to clear a stale entry when
   this tab can claim the document (no owner, its own id, or a dead owner) and
   it still points at the stored route. The visibility shown in step 4 stays in
   memory only and is not persisted.
8. Otherwise it persists the visibility it showed. If locate is not following —
   including when an incapable device restored the stored Following session as
   Located — it clears navigation. Only when locate actually re-entered
   `following` does it claim navigation ownership by writing this tab's id and
   start navigation with the restored `followOwned`; a dead owner's session is
   claimed at that point, not during the liveness check. If navigation fails to
   start, the document is cleared. Because routes await `locate.restoreComplete`,
   the compass-capability decision settles first and no navigation card flashes
   before the clear.
9. A restored navigation never fits or claims the camera — the normal follow
   restore owns the camera path.

Failures are silent. A missing route, no usable line geometry, a denied
permission or locate not re-entering following clears `routeId`/`followOwned`
but leaves the visibility list untouched (a missing route id is pruned). A
deferred restore is not a failure: it normally leaves the navigation document
for the live owner, and only a stale entry this tab can claim is cleared; it
never persists the visibility it showed. A restored navigation that owned
follow stops locate when navigation stops; a user-owned follow survives Stop.

### Top-centre navigation card

Navigation status is core chrome in the top-centre corner cluster
(`.ogis-corner--tc`): [`NavigationControl.vue`](../src/features/routes/NavigationControl.vue)
renders a full-size frosted-glass card (`.ogis-nav-control`). Routes publishes its
state through `useUI().setMenuNavigation`
([`index.js:527`](../src/features/routes/index.js#L527)). Navigation status lives
only in this card; the menu chip does not carry it.

The card is visual only: `pointer-events: none`, with `role="status"`,
`aria-live="off"` and the status text exposed through `aria-label`
(`navigation.title`).

| State     | Top-centre card                                                                       |
| --------- | ------------------------------------------------------------------------------------- |
| Locating  | Dimmed arrow and ellipsis until the first fix; the accessible label reads `Locating…` |
| Off route | Arrow rotated relative to the current map bearing, plus a compact distance            |
| On route  | Check and `On route`, within `ON_ROUTE_METRES` (5 m) of the route                     |

Navigation can begin before the first fix, because following may start while Locate is still Locating…; the card remains in its Locating state until a position exists, then switches to off route or on route.

Off-route distances use the compact `formatCompactDistance` formatter so the card
stays short; the card's accessible label carries the full localised distance
(`navigationOffRoute`). When off route and within 1 km, a green dashed SVG
connector (`.ogis-nav-connector`) joins the locate marker to the nearest point on
the route: it is a screen-space overlay teleported to `<body>`, projected along a
geodesic ([`geodesicLine`](../src/utils/track/navigation.js#L56)) and re-projected
on map move and resize. It starts at the locate marker's centre and ends at the
projected nearest route point — there is no separate target marker. The stroke is
the theme primary green (`var(--bs-primary)`, `#39d353`), 3 px at 0.9 opacity,
dashed `6 6` with butt caps. Because it is drawn above the map canvas it is never
occluded by terrain or 3D buildings; it is not a GeoJSON feature, so it adds no
route-navigation feature to the map.

The connector is removed when on route, when the nearest point is farther than
1 km away, and when navigation stops. Beyond 1 km the card still shows the
compact distance, but no connector is drawn.

Navigation works offline because it is entirely client-side (GPS + stored
geometry); the compass-capability gate is local too, so an incapable device
still disables Navigate offline, and a capable device with no live heading runs
the follow camera flat until one arrives. The basemap depends on the service
worker's [opportunistic map cache](./12.offline.md), so only previously viewed
areas are available. Far-away fixes are also the hardest case for Locate's HTML markers: a
terrain DEM error can abort MapLibre's move dispatch, so `useLocate` re-syncs the
marker on map `idle` and `moveend` with a bounded 120 s retry (see
[Testing — Routes navigation coverage](./9.testing.md#routes-navigation-coverage)).

## Shared geo helpers

`src/utils/geo.js` holds the shared distance/format helpers used by the Routes
feature and the track model:

| Function                                                 | Returns                                                            |
| -------------------------------------------------------- | ------------------------------------------------------------------ |
| `haversine(a, b)`                                        | Great-circle distance between two `{ lat, lng }` points, in metres |
| `totalDistance(points)`                                  | Sum of haversine segments, in metres                               |
| `formatDuration(ms)`                                     | `H:MM:SS` or `M:SS`                                                |
| `formatDistance(metres, isMetric = true, locale = "en")` | `km`/`m` or `mi`/`ft` string, formatted for `locale`               |
| `formatCompactDistance(metres, isMetric = true, locale)` | Short `km`/`m` or `mi`/`ft` string for the top-centre card         |

The track model adds multi-segment helpers on top:
`documentDistance` (per-segment distance), `documentBounds`, `lineGeometry`,
`documentPointCount` and `waypointCount`
([`src/utils/track/model.js`](../src/utils/track/model.js)), plus
`nearestPointOnTrack` and `ON_ROUTE_METRES` for navigation status
([`src/utils/track/navigation.js`](../src/utils/track/navigation.js)).
The track model uses `totalDistance` for per-segment distance, while Routes
imports `formatCompactDistance` and `formatDistance`
([`index.js:7`](../src/features/routes/index.js#L7)). `formatDuration` remains a
general-purpose helper in `src/utils/geo.js`.

## Panel UI

`RoutesPanel.vue` provides:

- a file input accepting `.gpx`, `.geojson`, `.json` and their MIME types,
  with multiple selection; each file goes through `importTracks`
- an error line translating the importer's sentinel code to a
  `panel.routes.error*` message, falling back to the generic
  `panel.routes.errorImport` — never the raw error
- a row per document with a colour swatch, name (falling back to
  `panel.routes.defaultName`), locale-formatted distance, waypoint count when
  present, Show/Hide, Navigate/Stop where the document has a line, a Share menu
  (GPX or GeoJSON) and Delete behind a native `window.confirm`
- Navigate is disabled while the route is hidden (`navigateHidden`), while
  another route is navigating (`navigateBusy`), or on a device without a compass
  (`navigateNoCompass`); its title explains why. The navigating row shows Stop
  in place of Navigate. Compass capability gates navigation only: Show/Hide,
  Share and Delete stay available.

The panel does not carry a navigation banner — status lives in the top-centre
navigation card (see [Navigation](#navigation)). The panel content has no
heading of its own: the tab labels the panel, and `menu.routes` is shared by
that tab and the top-left menu chip. Every string inside the panel resolves
through `t()` and the `panel.routes.*` keys. Import errors surface through the
importer's sentinel codes, mapped to
`panel.routes.errorInvalidGpx`,
`panel.routes.errorInvalidGeoJSON`, `panel.routes.errorUnsupported`,
`panel.routes.errorTooLarge` and `panel.routes.errorNoRoutes` (see
[Locale — Message codes and sentinel errors](./7.locale.md#message-codes-and-sentinel-errors)).

Sharing uses [`shareTrack`](../src/features/routes/index.js#L516), which builds
GPX or GeoJSON with `toGPX`/`toGeoJSON`, names the file with `trackFilename`,
and calls `shareFile` (Web Share API, otherwise a download). A non-abort share
failure is reported through `reportError` and falls back to the download; an
`AbortError` stays silent. See [Tracks — Export](./15.tracks.md#export) for the
download-failure path. GPX/GeoJSON round-trip caveats are covered in
[Tracks — Round-trip caveats](./15.tracks.md#round-trip-caveats).

## Limitations

- **Storage quota.** Documents are stored as-is in `localStorage` (5 MB per
  origin); large tracks may not fit.
- **No editing.** Points cannot be reordered, trimmed or edited in the UI.
- **GPX/GeoJSON subset.** GPX extensions and several optional elements are not
  modelled; unsupported GeoJSON geometry types reject the file. See
  [Tracks — Round-trip caveats](./15.tracks.md#round-trip-caveats).
- **Visibility is persisted per route.** Imported routes still start hidden,
  but a visible route reappears after a reload without moving the camera.
- **Separate sharing.** A multi-document import exports one file per row.
- **No turn-by-turn guidance.** Navigation follows the user and indicates the
  distance back to the route; it has no turn instructions, arrival estimates,
  progress along the route or re-routing.
- **Navigation restore is conditional.** Navigation requires a compass-capable
  device and resumes after a reload or app quit only when locate restores into
  following; a stored Following session restores as Located on an incapable
  device, clearing navigation without showing the navigation card. A denied or
  unavailable geolocation session clears navigation and keeps route visibility. A second
  live tab checks the stored `ownerId` — a bounded shared-mode Web Lock probe,
  with a starvation-tolerant `BroadcastChannel` fallback — and does not restore
  or clear the owner's navigation. A deferred restore leaves the live owner's
  navigation document untouched, except to clear a stale entry this tab can
  claim.
- **Route content is shared and live; navigation is durably tab-owned.** Route
  documents live in `localStorage` and sync between tabs, while visibility and
  navigation ownership live in the separate `localStorage` navigation store with
  an `ownerId` and a bounded Web Lock liveness probe (secure contexts only),
  with a `BroadcastChannel` fallback. Restore uses the last successful write: a
  normal reload or app quit restores visibility and navigation, while a hard kill
  or force-quit can lose the most recent debounced route change. See
  [State and resilience — Limitations and deliberate exclusions](./16.state-and-resilience.md#limitations-and-deliberate-exclusions).
- **Offline map background** comes from the service worker's opportunistic
  cache: only tiles and glyphs already viewed online are available, and there is
  no region download.

> [!NOTE]
> At very distant locations the basemap can render with partial tiles or
> "Map data not available". This comes from a pre-existing MapLibre terrain/DEM
> tile error and slow external tiles, not from the navigation connector or
> control. The locate marker re-syncs on `idle`/`moveend` with the bounded 120 s
> retry, but slow external tile loading can still delay it.
