# Testing

ogis.app has two test layers:

- **Unit tests** (Vitest) — test pure composable logic in milliseconds
- **E2E tests** (Playwright) — test full browser integration

```bash
npm run test:unit                                     # Vitest — < 10 s
npm run test:e2e -- tests/e2e/core.spec.js            # single spec (recommended during development)
npm run test:e2e -- --workers=4                       # full E2E suite incl. screenshots — local final verification
npm test                                              # unit tests only (rapid development)
```

- Unit tests complete in under 10 seconds — use `npm test` and targeted spec runs during rapid development.
- The full local E2E run, in the default GPU rendering mode with `--workers=4`, is the final verification before declaring a task complete. It includes the `@screenshots` matrix and regenerates the committed `screenshots/` artefacts; seconds to a few minutes per test subset, with the screenshot matrix dominating.
- SwiftShader is the CI renderer. Set `E2E_SWIFTSHADER=1` to reproduce CI rendering locally; it is much slower, so keep it for renderer-specific checks rather than everyday runs.
- CI runs the **functional** E2E suite only — the screenshot matrix is excluded via `--grep-invert @screenshots` (see [CI](./11.ci.md)). CI splits the functional suite across three shards; within a shard Playwright runs serially and retries twice (`CI=1` in `playwright.config.js`).
- `playwright.config.js` sets no `actionTimeout` override. A tight bound was tried and reverted because software-rendered (SwiftShader) actionability stalls can exceed several seconds under load, causing false failures. Actions therefore fall back to Playwright's default bound (the test timeout).

## E2E rendering modes

`playwright.config.js` selects the renderer from the environment:

| Mode                | Trigger                          | Browser                                     | GPU flags                                                        |
| ------------------- | -------------------------------- | ------------------------------------------- | ---------------------------------------------------------------- |
| GPU (local default) | `CI` and `E2E_SWIFTSHADER` unset | Full Chromium build (`channel: "chromium"`) | `--use-angle=metal` on macOS; default backend on other platforms |
| SwiftShader         | `CI=1` or `E2E_SWIFTSHADER=1`    | Bundled Chromium                            | `--use-angle=swiftshader`, `--enable-unsafe-swiftshader`         |

- GPU is the local default and keeps test subsets fast. Measured: 61–62-test subsets complete in 1.5–4.7 min headed. GPU mode also runs the screenshot matrix — the local final-verification step — where a capture takes ~15 s. On a fresh machine, `npx playwright install chromium` installs the full build; CI installs `chromium --with-deps`.
- SwiftShader is the deterministic software renderer CI has always used. `E2E_SWIFTSHADER=1` reproduces it locally, while `CI=1` implies it. It is much slower (measured: 61 tests at 2 workers in ~10.4 min), and screenshot captures cost ~50–60 s each — the full matrix would need ~60–75 minutes of runner CPU, which is why CI now runs functional specs only and the matrix stays local.
- `--deny-permission-prompts` is passed in **both** modes, so headed runs deny un-granted permissions (e.g. geolocation) deterministically instead of hanging on an interactive prompt. Specs that need a position grant it explicitly via CDP — `context.grantPermissions()` plus `setGeolocation()` — and the CDP grant overrides the deny switch.

## E2E structure

E2E specs live in `tests/e2e/` and test behaviour in the real browser:

```
tests/
  unit/                    ← Vitest unit tests
  e2e/
    core.spec.js           ← core UI: first load, welcome, Info panel, attribution chip, panel geometry (capped width, safe-area insets)
    sw.spec.js             ← service worker registers on load + reload boots under SW control
    helpers/panel.js       ← shared map/panel waits: waitForMapReady, waitForPanelSettled, openMenuPanel
    features/
      locate.spec.js       ← GPS locate
      recordings.spec.js   ← recordings feature
      routes.spec.js       ← GPX routes: import, delete, navigate
      settings.spec.js     ← theme, OS-derived units + language (settings panel removed)
      offline.spec.js      ← offline region download
      account.spec.js      ← skipped (feature disabled in src/main.js)
      collections.spec.js  ← skipped (feature disabled)
      maps.spec.js         ← skipped (feature disabled)
    screenshots/
      readme.spec.js       ← screenshots/readme/{dark,light}.jpg (README heroes)
      ui-states.spec.js    ← screenshots/{device}/{orientation}/*.jpg (committed matrix)
```

> [!NOTE]
> `account`, `collections` and `maps` specs are marked `test.describe.skip` while their features are commented out in `src/main.js` (lines 16–20, 113–116). Remove the skip when the features ship.

## Writing E2E tests

```js
import { test, expect } from "@playwright/test";

test.describe("My feature / My heading", () => {
  test("does the thing", async ({ page }) => {
    await page.goto("/");
    await expect(page.locator(".my-element")).toBeVisible();
  });
});
```

- Use `page.addInitScript` to seed `localStorage` before navigation
- Storage keys: `ogis_{namespace}_{instanceId}` — the default id is `'app'`, so the view key is `ogis_view_app`
- Settings are OS-derived and write nothing — there is no `ogis_settings_*` key to seed or assert
- Poll for throttled async side-effects with `expect.poll()` rather than `waitForTimeout`

### Waiting for the map

The map and panel waits are shared — [`tests/e2e/helpers/panel.js`](../tests/e2e/helpers/panel.js) exports `waitForMapReady`, `waitForPanelSettled` and `openMenuPanel`, and the map-focused specs (`core`, `locate`, `recordings`, `routes`) import them.

`waitForMapReady(page)` waits on three cheap, deterministic conditions:

1. the `#menu-button` chip is visible;
2. `.ogis-map` has `data-map-ready="true"` (explicit 30 s backstop);
3. `.ogis-panel` carries neither the offcanvas `showing` nor `hiding` class — a defensive guard, since the app has no Bootstrap JS and those transitional classes are not expected to appear.

`waitForPanelSettled(page)` additionally waits for the panel's CSS `transform` to reach `none` (the 0.25 s offcanvas slide), so geometry is measured only after it has settled; `openMenuPanel(page)` clicks the menu chip, asserts the `show` class, then waits for that settle. Both use explicit 30 s timeouts.

`data-map-ready` is set by `useMap` at MapLibre `style.load` — the same point the map instance is published and `map:ready` is emitted — so the map is usable and its features are wired up. It deliberately does **not** wait for MapLibre's render-bound `load` or the `data-map-idle` settle; `data-map-idle` is set on MapLibre `idle` and is reserved for the screenshot specs and `sw.spec.js`.

All former `waitForLoadState("networkidle")` calls were replaced by `waitForMapReady`: network idle is slower and non-deterministic (tiles and glyphs can keep streaming), whereas the app-ready signal is a definite point in app state.

For camera moves, wait on the expected URL hash rather than a tile render. Locate's `waitForCameraSettle(page, expectedHash)` polls the URL (written on MapLibre `moveend`) until it matches the target view; anchoring on the _expected_ hash is race-safe, since a pending move's pre-move hash differs and the wait cannot resolve early. A full tile-render wait (`data-map-idle`) after a locate fly-to (z16 + terrain/hillshade) measured ~246–275 s under SwiftShader + load, but no locate assertion inspects a rendered tile set. Even locate's cold load uses `waitForMapReady` — the locate spec has no full map-idle wait. Locate budgets: `CAMERA_SETTLE_TIMEOUT` 30000 ms, `LOCATE_TIMEOUT` 60000 ms, file-level `test.setTimeout(420000)`.

## Colour scheme (dark by default)

`playwright.config.js` sets `colorScheme: 'dark'` in the shared `use`, so every spec and screenshot inherits dark. The app has no in-app theme toggle — it follows the OS/browser `prefers-color-scheme` setting via `useSettings` — so dark-by-default is a test convention, not an app default.

Light mode is verified explicitly by `readme.spec.js`: the light hero requests `colorScheme: 'light'` and asserts `data-bs-theme="light"` on `<html>` (the app's theme application point), while the dark captures assert the complementary `data-bs-theme="dark"`, proving both directions of the downstream OS/browser setting. `settings.spec.js` keeps its own explicit light/dark behaviour tests for the runtime `prefers-color-scheme` change, plus a regression test that the first-load welcome modal — teleported outside `.ogis-root` — resolves the same dark background as the app root.

## Screenshots

Playwright generates the committed screenshot artefacts under `screenshots/`:

| Path                                                                  | Spec                                      | Contents                                                                    |
| --------------------------------------------------------------------- | ----------------------------------------- | --------------------------------------------------------------------------- |
| `screenshots/readme/{dark,light}.jpg`                                 | `tests/e2e/screenshots/readme.spec.js`    | 1280×720 README heroes with the Info panel open                             |
| `screenshots/{phone,tablet,desktop}/{portrait,landscape}/<state>.jpg` | `tests/e2e/screenshots/ui-states.spec.js` | 8 core chrome states × 6 viewports = 48 JPEGs                               |
| `screenshots/desktop/landscape/feature-*.jpg`                         | `tests/e2e/screenshots/ui-states.spec.js` | 4 feature states: routes, route navigation, offline region, saved recording |

Regenerate both with the `@screenshots` tag:

```bash
npm run test:e2e -- --grep @screenshots
```

Or target a single spec:

```bash
npm run test:e2e -- tests/e2e/screenshots/readme.spec.js
npm run test:e2e -- tests/e2e/screenshots/ui-states.spec.js
```

Screenshots are committed so the README and docs render on GitHub. They are generated only by local runs — the `@screenshots` specs are excluded from CI (see [CI](./11.ci.md)) — and the full local suite regenerates them as its final-verification step. They are **not** pixel-diff baselines — live map tiles make comparisons brittle, so the specs snapshot without comparing (an explicit project decision). Every capture also asserts zero console/page errors.

Captures are written as JPEG at quality 80 — chosen for the photographic map imagery, which compresses well without visible artefacts, keeping the committed matrix low-weight.

**Conventions:**

- README heroes are 1280×720; the matrix uses each device's viewport from `VIEWPORTS` in `ui-states.spec.js`
- Dark is the suite default (`colorScheme: 'dark'` in `playwright.config.js`); the light hero opts in explicitly
- Test names describe the UI state being captured
- Add a screenshot when the visual output meaningfully illustrates the behaviour

The matrix specs carry generous file-level timeout budgets, sized for SwiftShader's slow stability checks — the renderer CI uses, and `E2E_SWIFTSHADER=1` reproduces (the matrix itself now runs locally in GPU mode): `ui-states.spec.js` uses `test.setTimeout(300000)`, while `readme.spec.js` and `sw.spec.js` use `120000`. `tests/e2e/core.spec.js` and `tests/e2e/features/recordings.spec.js` carry the same `120000` budget for their chip-click and reload interactions.
