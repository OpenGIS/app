# Testing

On Route has two test layers:

- **Unit tests** (Vitest) — test pure composable logic in milliseconds
- **E2E tests** (Playwright) — test full browser integration

```bash
npm run test:unit                                     # Vitest — < 10 s
npm run test:e2e -- tests/e2e/core.spec.js            # single spec (recommended)
npm run test:e2e -- --workers=4                       # full E2E suite (manual run)
npm test                                              # unit tests only (final check)
```

- Unit tests complete in under 10 seconds — run `npm test` as the final check on every change.
- Locally, run E2E against the default GPU rendering mode and use `--workers=4` for the full suite — seconds to a few minutes per test subset, with the screenshot matrix dominating. Prefer targeted single-spec runs while developing.
- SwiftShader remains the CI renderer. Set `E2E_SWIFTSHADER=1` to reproduce CI rendering locally; it is much slower, so keep it for renderer-specific checks rather than everyday runs.
- E2E runs in CI alongside the unit suite (see [CI](./11.ci.md)). CI splits the suite across three shards; within a shard Playwright runs serially and retries twice (`CI=1` in `playwright.config.js`).
- `playwright.config.js` sets no `actionTimeout` override. A tight bound was tried and reverted because software-rendered (SwiftShader) actionability stalls can exceed several seconds under load, causing false failures. Actions therefore fall back to Playwright's default bound (the test timeout).

## E2E rendering modes

`playwright.config.js` selects the renderer from the environment:

| Mode                | Trigger                          | Browser                                     | GPU flags                                                        |
| ------------------- | -------------------------------- | ------------------------------------------- | ---------------------------------------------------------------- |
| GPU (local default) | `CI` and `E2E_SWIFTSHADER` unset | Full Chromium build (`channel: "chromium"`) | `--use-angle=metal` on macOS; default backend on other platforms |
| SwiftShader         | `CI=1` or `E2E_SWIFTSHADER=1`    | Bundled Chromium                            | `--use-angle=swiftshader`, `--enable-unsafe-swiftshader`         |

- GPU is the local default and keeps test subsets fast. Measured: 61–62-test subsets complete in 1.5–4.7 min headed. On a fresh machine, `npx playwright install chromium` installs the full build; CI installs `chromium --with-deps`.
- SwiftShader is the deterministic software renderer CI has always used. `E2E_SWIFTSHADER=1` reproduces it locally, while `CI=1` implies it. It is much slower (measured: 61 tests at 2 workers in ~10.4 min).
- `--deny-permission-prompts` is passed in **both** modes, so headed runs deny un-granted permissions (e.g. geolocation) deterministically instead of hanging on an interactive prompt. Specs that need a position grant it explicitly via CDP — `context.grantPermissions()` plus `setGeolocation()` — and the CDP grant overrides the deny switch.

## E2E structure

E2E specs live in `tests/e2e/` and test behaviour in the real browser:

```
tests/
  unit/                    ← Vitest unit tests
  e2e/
    core.spec.js           ← core UI: first load, welcome, Info panel, attribution chip
    sw.spec.js             ← service worker registers on load + reload boots under SW control
    features/
      locate.spec.js       ← GPS locate
      recordings.spec.js   ← recordings feature
      routes.spec.js       ← GPX routes: import, delete, navigate
      settings.spec.js     ← theme, OS-derived units + language (settings panel removed)
      offline.spec.js      ← offline region download
      account.spec.js      ← skipped (feature disabled in src/main.js)
      collections.spec.js  ← skipped (feature disabled)
      maps.spec.js         ← skipped (feature disabled)
    screenshots/
      readme.spec.js       ← screenshots/readme/{dark,light}.jpg (README heroes)
      ui-states.spec.js    ← screenshots/{device}/{orientation}/*.jpg (committed matrix)
```

> [!NOTE]
> `account`, `collections` and `maps` specs are marked `test.describe.skip` while their features are commented out in `src/main.js` (lines 17–21, 114–117). Remove the skip when the features ship.

## Writing E2E tests

```js
import { test, expect } from "@playwright/test";

test.describe("My feature / My heading", () => {
  test("does the thing", async ({ page }) => {
    await page.goto("/");
    await expect(page.locator(".my-element")).toBeVisible();
  });
});
```

- Use `page.addInitScript` to seed `localStorage` before navigation
- Storage keys: `onrte_{namespace}_{instanceId}` — the default id is `'app'`, so the view key is `onrte_view_app`
- Settings are OS-derived and write nothing — there is no `onrte_settings_*` key to seed or assert
- Poll for throttled async side-effects with `expect.poll()` rather than `waitForTimeout`

### Waiting for the map

The heavier map specs use a per-spec `waitForMapReady(page)` helper (helpers are duplicated per spec by project convention). It waits on three cheap, deterministic conditions:

1. the `#menu-button` chip is visible;
2. `.onrte-map` has `data-map-ready="true"` (broad 30 s backstop);
3. `.onrte-panel` has settled out of its Bootstrap `showing`/`hiding` transition.

`data-map-ready` is set by `useMap` at MapLibre `style.load` — the same point the map instance is published and `map:ready` is emitted — so the map is usable and its features are wired up. It deliberately does **not** wait for MapLibre's render-bound `load` or the `data-map-idle` settle; `data-map-idle` is set on MapLibre `idle` and is reserved for the screenshot specs and `sw.spec.js`.

All former `waitForLoadState("networkidle")` calls were replaced by `waitForMapReady`: network idle is slower and non-deterministic (tiles and glyphs can keep streaming), whereas the app-ready signal is a definite point in app state.

For camera moves, wait on the expected URL hash rather than a tile render. Locate's `waitForCameraSettle(page, expectedHash)` polls the URL (written on MapLibre `moveend`) until it matches the target view; anchoring on the _expected_ hash is race-safe, since a pending move's pre-move hash differs and the wait cannot resolve early. A full tile-render wait (`data-map-idle`) after a locate fly-to (z16 + terrain/hillshade) measured ~246–275 s under SwiftShader + load, but no locate assertion inspects a rendered tile set. Even locate's cold load uses `waitForMapReady` — the locate spec has no full map-idle wait. Locate budgets: `CAMERA_SETTLE_TIMEOUT` 30000 ms, `LOCATE_TIMEOUT` 60000 ms, file-level `test.setTimeout(420000)`.

## Colour scheme (dark by default)

`playwright.config.js` sets `colorScheme: 'dark'` in the shared `use`, so every spec and screenshot inherits dark. The app has no in-app theme toggle — it follows the OS/browser `prefers-color-scheme` setting via `useSettings` — so dark-by-default is a test convention, not an app default.

Light mode is verified explicitly by `readme.spec.js`: the light hero requests `colorScheme: 'light'` and asserts `.onrte-root[data-bs-theme="light"]`, while the dark captures assert the complementary `data-bs-theme="dark"`, proving both directions of the downstream OS/browser setting. `settings.spec.js` keeps its own explicit light/dark behaviour tests for the runtime `prefers-color-scheme` change.

## Screenshots

Playwright generates the committed screenshot artefacts under `screenshots/`:

| Path                                                                  | Spec                                      | Contents                                                                    |
| --------------------------------------------------------------------- | ----------------------------------------- | --------------------------------------------------------------------------- |
| `screenshots/readme/{dark,light}.jpg`                                 | `tests/e2e/screenshots/readme.spec.js`    | 1280×720 README heroes with the Info panel open                             |
| `screenshots/{phone,tablet,desktop}/{portrait,landscape}/<state>.jpg` | `tests/e2e/screenshots/ui-states.spec.js` | 9 core chrome states × 6 viewports = 54 JPEGs                               |
| `screenshots/desktop/landscape/feature-*.jpg`                         | `tests/e2e/screenshots/ui-states.spec.js` | 4 feature states: routes, route navigation, offline region, saved recording |

Regenerate both with the `@screenshots` tag:

```bash
npm run test:e2e -- --grep @screenshots
```

Or target a single spec:

```bash
npm run test:e2e -- tests/e2e/screenshots/readme.spec.js
npm run test:e2e -- tests/e2e/screenshots/ui-states.spec.js
```

Screenshots are committed so the README and docs render on GitHub, and CI uploads the same directory as a build artefact (see [CI](./11.ci.md)). They are **not** pixel-diff baselines — live map tiles make comparisons brittle, so the specs snapshot without comparing (an explicit project decision). Every capture also asserts zero console/page errors.

Captures are written as JPEG at quality 80 — chosen for the photographic map imagery, which compresses well without visible artefacts, keeping the committed matrix low-weight.

**Conventions:**

- README heroes are 1280×720; the matrix uses each device's viewport from `VIEWPORTS` in `ui-states.spec.js`
- Dark is the suite default (`colorScheme: 'dark'` in `playwright.config.js`); the light hero opts in explicitly
- Test names describe the UI state being captured
- Add a screenshot when the visual output meaningfully illustrates the behaviour

The matrix specs carry generous file-level timeout budgets, sized for SwiftShader's slow stability checks under CI load: `ui-states.spec.js` uses `test.setTimeout(300000)`, while `readme.spec.js` and `sw.spec.js` use `120000`. `tests/e2e/core.spec.js` and `tests/e2e/features/recordings.spec.js` carry the same `120000` budget for their chip-click and reload interactions.
