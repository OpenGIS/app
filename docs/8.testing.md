# Testing

ogis.app has two test layers:

- **Unit tests** (Vitest) — test pure composable logic in milliseconds
- **E2E tests** (Playwright) — test full browser integration

```bash
npm run test:unit                                     # Vitest — < 10 s
npm run test:e2e -- tests/e2e/core.spec.js            # single spec (recommended during development)
npm run test:e2e -- --workers=4                       # full E2E suite incl. screenshots — local final verification
npm test                                              # unit tests only (rapid development)
```

- Unit tests complete in under 10 seconds — use `npm test` and targeted spec runs during rapid development.
- The full local E2E run, in the default GPU rendering mode with `--workers=4`, is the final verification before declaring a task complete. It includes the `@screenshots` matrix and regenerates the committed `screenshots/` artefacts; seconds to a few minutes per test subset, with the screenshot matrix dominating.
- SwiftShader is the CI renderer. Set `E2E_SWIFTSHADER=1` to reproduce CI rendering locally; it is much slower, so keep it for renderer-specific checks rather than everyday runs.
- CI runs the **functional** E2E suite only — the screenshot matrix is excluded via `--grep-invert @screenshots` (see [CI](./11.ci.md)). CI splits the functional suite across three shards; within a shard Playwright runs serially and retries twice (`CI=1` in `playwright.config.js`).
- `playwright.config.js` sets no `actionTimeout` override. A tight bound was tried and reverted because software-rendered (SwiftShader) actionability stalls can exceed several seconds under load, causing false failures. Actions therefore fall back to Playwright's default bound (the test timeout).

## E2E rendering modes

`playwright.config.js` selects the renderer from the environment:

| Mode                | Trigger                          | Browser                                     | GPU flags                                                        |
| ------------------- | -------------------------------- | ------------------------------------------- | ---------------------------------------------------------------- |
| GPU (local default) | `CI` and `E2E_SWIFTSHADER` unset | Full Chromium build (`channel: "chromium"`) | `--use-angle=metal` on macOS; default backend on other platforms |
| SwiftShader         | `CI=1` or `E2E_SWIFTSHADER=1`    | Bundled Chromium                            | `--use-angle=swiftshader`, `--enable-unsafe-swiftshader`         |

- GPU is the local default and keeps test subsets fast. Measured: 61–62-test subsets complete in 1.5–4.7 min headed. GPU mode also runs the screenshot matrix — the local final-verification step — where a capture takes ~15 s. On a fresh machine, `npx playwright install chromium` installs the full build; CI installs `chromium --with-deps`.
- SwiftShader is the deterministic software renderer CI has always used. `E2E_SWIFTSHADER=1` reproduces it locally, while `CI=1` implies it. It is much slower (measured: 61 tests at 2 workers in ~10.4 min), and screenshot captures cost ~50–60 s each — the full matrix would need ~60–75 minutes of runner CPU, which is why CI now runs functional specs only and the matrix stays local.
- `--deny-permission-prompts` is passed in **both** modes, so headed runs deny un-granted permissions (e.g. geolocation) deterministically instead of hanging on an interactive prompt. Specs that need a position grant it explicitly via CDP — `context.grantPermissions()` plus `setGeolocation()` — and the CDP grant overrides the deny switch.

## E2E structure

E2E specs live in `tests/e2e/` and test behaviour in the real browser:

```
tests/
  unit/                    ← Vitest unit tests
  e2e/
    helpers/
      test.js              ← shared test/expect; installs the map-asset stubs via a context fixture (plus the `liveGlyphRelay` option) and the pending-request tracker via a `page` fixture
      mapAssets.js         ← MapLibre style + www.ogis.org route stubs, served from the vendored fixtures; missing glyph ranges default to an empty 200
      mapIdle.js           ← shared map-idle wait: waitForMapIdle (60 s) + trackPendingRequests; on timeout attaches map-idle diagnostics before rethrowing
      console.js           ← trackConsoleErrors / expectNoConsoleErrors (E2E-test only, shared)
      panel.js             ← shared map/panel waits: waitForMapReady, waitForPanelSettled, openMenuPanel
    fixtures/
      route.gpx            ← GPX import fixture
      map/                 ← vendored style, sprites and glyphs (see Map-asset fixtures)
    core.spec.js           ← core UI: cold-start country focus (timezone cascade + ?country override), Info panel, attribution chip, panel geometry (capped width, safe-area insets)
    sw.spec.js             ← service worker registers on load + reload boots under SW control
    features/
      locate.spec.js       ← GPS locate
      recordings.spec.js   ← recordings feature
      routes.spec.js       ← GPX routes: import, delete, navigate
      settings.spec.js     ← theme, OS-derived units + language (settings panel removed)
      offline.spec.js      ← offline region download
      account.spec.js      ← skipped (feature disabled in src/main.js)
      collections.spec.js  ← skipped (feature disabled)
      maps.spec.js         ← skipped (feature disabled)
    screenshots/
      readme.spec.js       ← screenshots/readme/{dark,light}.jpg (README heroes)
      ui-states.spec.js    ← screenshots/{device}/{orientation}/*.jpg (committed matrix)
```

Every spec imports `test`/`expect` from `helpers/test.js` (`../helpers/test.js` from subdirectories), which installs the [map-asset stubs](#map-asset-fixtures) on each context. The helper also exposes the `liveGlyphRelay` option (default `false`), which the `context` fixture threads into the stub installer. Helper modules that need only assertions — `helpers/panel.js` and `helpers/console.js` — continue to import `expect` from `@playwright/test`. [`helpers/console.js`](../tests/e2e/helpers/console.js) is E2E-test-only tooling: `trackConsoleErrors(page)` collects errors on `page.__consoleErrors`, and `expectNoConsoleErrors(page)` asserts the array empty with Playwright's `expect`; nothing in `src/` imports or uses it.

> [!NOTE]
> `account`, `collections` and `maps` specs are marked `test.describe.skip` while their features are commented out in `src/main.js` (lines 16–20, 113–116). Remove the skip when the features ship.

## Map-asset fixtures

MapLibre previously loaded the style, sprites and glyphs from live origins during E2E runs. Under load, `https://www.ogis.org` returned HTTP 429 without CORS headers, which surfaced as browser console errors and made `expectNoConsoleErrors` fail intermittently in the `ui-states` and `sw` specs. The suite now serves those assets from committed fixtures, so a run never depends on the live origin; the only live-origin contact is the README hero spec's opt-in glyph relay, which still degrades gracefully (see below).

Vendored under [`tests/e2e/fixtures/map/`](../tests/e2e/fixtures/map/):

- `style.json` — a pinned copy of the style declared in [`src/defaults/maplibre.js`](../src/defaults/maplibre.js)
- `www.ogis.org/basemap/sprite.{json,png}` and `www.ogis.org/outdoors/sprite.{json,png}` — 1× sprites only; the suite runs at devicePixelRatio 1, so the @2x variants are deliberately omitted
- `www.ogis.org/basemap/fonts/<stack>/0-255.pbf` — glyphs for all 12 font stacks in the style (directory names URL-encoded)

Every spec imports `test` from [`tests/e2e/helpers/test.js`](../tests/e2e/helpers/test.js); its `context` fixture installs the stubs ([`tests/e2e/helpers/mapAssets.js`](../tests/e2e/helpers/mapAssets.js)) before any page exists, so stubbed responses also cover service-worker requests. The stub serves the style URL from the pinned fixture and mirrors everything under `https://www.ogis.org/**` from the fixture tree, with permissive CORS headers on served assets.

Unvendored glyph ranges never reach the network by default: the stub fulfils them with an instant, CORS-permissive empty HTTP 200, so a missing range becomes neither a console error nor a live request. This keeps the offline-download spec fast — it deliberately prefetches all 256 ranges per fontstack, and none may take a relay round-trip. The README hero spec ([`readme.spec.js`](../tests/e2e/screenshots/readme.spec.js)) is the sole opt-in to the live relay (`test.use({ liveGlyphRelay: true })`): a `?country=random` capture can land on a country whose labels need glyph ranges beyond the vendored `0-255` (e.g. CJK), so the relay fetches those server-side with a 5 s timeout and falls back to the same empty HTTP 200 on any failure. A missing sprite or style fixture, by contrast, returns 404 so drift fails loudly.

[`refresh.mjs`](../tests/e2e/fixtures/map/refresh.mjs) re-downloads everything from live, deriving the sprite and glyph URLs from the style itself:

```bash
npm run fixtures:refresh
```

The refresh is a manual local step, deliberately **not** run in CI — CI uses the committed fixtures. Run it locally when the upstream style changes materially, review the diff and commit. `.prettierignore` excludes `tests/e2e/fixtures/` (generated/vendored).

## Writing E2E tests

```js
import { test, expect } from "./helpers/test.js";

test.describe("My feature / My heading", () => {
  test("does the thing", async ({ page }) => {
    await page.goto("/");
    await expect(page.locator(".my-element")).toBeVisible();
  });
});
```

- Import `test`/`expect` from `./helpers/test.js` so the map-asset stubs are installed on the context (see [Map-asset fixtures](#map-asset-fixtures)); a spec should never import the base `test` from `@playwright/test` directly
- Track and assert a clean console with `trackConsoleErrors(page)` / `expectNoConsoleErrors(page)` from `helpers/console.js` — shared by the `sw`, `ui-states` and `routes` specs, and filters Mapterhorn tile 404 noise
- Use `page.addInitScript` to seed `localStorage` before navigation
- Storage keys: `ogis_{namespace}_{instanceId}` — the default id is `'app'`, so the view key is `ogis_view_app`
- Settings are OS-derived and write nothing — there is no `ogis_settings_*` key to seed or assert
- Pin the browser timezone with `test.use({ timezoneId })` when a test depends on cold-start country focus — timezone resolution sits above locale in the cascade, so the fitted country is deterministic on any host machine (`core.spec.js` uses `Europe/London`)
- Poll for throttled async side-effects with `expect.poll()` rather than `waitForTimeout`

### Waiting for the map

The map and panel waits are shared — [`tests/e2e/helpers/panel.js`](../tests/e2e/helpers/panel.js) exports `waitForMapReady`, `waitForPanelSettled` and `openMenuPanel`, and the map-focused specs (`core`, `locate`, `recordings`, `routes`) import them.

`waitForMapReady(page)` waits on three cheap, deterministic conditions:

1. the `#menu-button` chip is visible;
2. `.ogis-map` has `data-map-ready="true"` (explicit 30 s backstop);
3. `.ogis-panel` carries neither the offcanvas `showing` nor `hiding` class — a defensive guard, since the app has no Bootstrap JS and those transitional classes are not expected to appear.

`waitForPanelSettled(page)` additionally waits for the panel's CSS `transform` to reach `none` (the 0.25 s offcanvas slide), so geometry is measured only after it has settled; `openMenuPanel(page)` clicks the menu chip, asserts the `show` class, then waits for that settle. Both use explicit 30 s timeouts.

`data-map-ready` is set by `useMap` at MapLibre `style.load` — the same point the map instance is published and `map:ready` is emitted — so the map is usable and its features are wired up. It deliberately does **not** wait for MapLibre's render-bound `load` or the `data-map-idle` settle; `data-map-idle` is set on MapLibre `idle` and is used only where a rendered tile set is actually asserted: the screenshot specs (through the shared wait helper), `sw.spec.js`, and a few cold-start checks in `core.spec.js`.

Screenshot specs wait on that idle settle through `waitForMapIdle(page, testInfo, { timeout = 60000 })` in [`helpers/mapIdle.js`](../tests/e2e/helpers/mapIdle.js), which asserts `data-map-idle="true"` and, on timeout, attaches a `map-idle-diagnostics` text attachment to the test report before rethrowing the original error. The attachment records page state (URL, `navigator.onLine`, the map's `data-map-ready`/`data-map-idle` values), the in-flight requests held by `trackPendingRequests(page)`, and failed or aborted resources from the Performance Resource Timing API — both capped so a pathological run cannot attach an unbounded blob. The tracker must be installed before navigation, which the `page` fixture in `helpers/test.js` guarantees for every spec. This exists because a stalled live raster or TileJSON request blocks MapLibre's `idle` event and MapLibre applies no per-request timeout, so a flaky origin otherwise fails as a bare "attribute did not become true" with nothing pointing at the culprit. The tracker is the primary signal: resource timing only records completed responses, so a request still stalled at timeout may not appear there at all.

All former `waitForLoadState("networkidle")` calls were replaced by `waitForMapReady`: network idle is slower and non-deterministic (tiles and glyphs can keep streaming), whereas the app-ready signal is a definite point in app state.

For camera moves, wait on the expected URL hash rather than a tile render. Locate's `waitForCameraSettle(page, expectedHash)` polls the URL (written on MapLibre `moveend`) until it matches the target view; anchoring on the _expected_ hash is race-safe, since a pending move's pre-move hash differs and the wait cannot resolve early. A full tile-render wait (`data-map-idle`) after a locate fly-to (z16 + terrain/hillshade) measured ~246–275 s under SwiftShader + load, but no locate assertion inspects a rendered tile set. Even locate's cold load uses `waitForMapReady` — the locate spec has no full map-idle wait. Locate budgets: `CAMERA_SETTLE_TIMEOUT` 30000 ms, `LOCATE_TIMEOUT` 60000 ms, file-level `test.setTimeout(420000)`.

## Colour scheme (dark by default)

`playwright.config.js` sets `colorScheme: 'dark'` in the shared `use`, so every spec and screenshot inherits dark. The app has no in-app theme toggle — it follows the OS/browser `prefers-color-scheme` setting via `useSettings` — so dark-by-default is a test convention, not an app default.

Light mode is verified explicitly by `readme.spec.js`: the light hero requests `colorScheme: 'light'` and asserts `data-bs-theme="light"` on `<html>` (the app's theme application point), while the dark captures assert the complementary `data-bs-theme="dark"`, proving both directions of the downstream OS/browser setting. `settings.spec.js` keeps its own explicit light/dark behaviour tests for the runtime `prefers-color-scheme` change, plus a regression test that the locate-confirm modal — teleported outside `.ogis-root` — resolves the same dark background as the app root.

## Screenshots

Playwright generates the committed screenshot artefacts under `screenshots/`:

| Path                                                                  | Spec                                      | Contents                                                                     |
| --------------------------------------------------------------------- | ----------------------------------------- | ---------------------------------------------------------------------------- |
| `screenshots/readme/{dark,light}.jpg`                                 | `tests/e2e/screenshots/readme.spec.js`    | 1280×720 README heroes (cold start, random country) with the Info panel open |
| `screenshots/{phone,tablet,desktop}/{portrait,landscape}/<state>.jpg` | `tests/e2e/screenshots/ui-states.spec.js` | 7 core chrome states × 6 viewports = 42 JPEGs                                |
| `screenshots/desktop/landscape/feature-*.jpg`                         | `tests/e2e/screenshots/ui-states.spec.js` | 4 feature states: routes, route navigation, offline region, saved recording  |

Regenerate both with the `@screenshots` tag:

```bash
npm run test:e2e -- --grep @screenshots
```

Or target a single spec:

```bash
npm run test:e2e -- tests/e2e/screenshots/readme.spec.js
npm run test:e2e -- tests/e2e/screenshots/ui-states.spec.js
```

Screenshots are committed so the README and docs render on GitHub. They are generated only by local runs — the `@screenshots` specs are excluded from CI (see [CI](./11.ci.md)) — and the full local suite regenerates them as its final-verification step. They are **not** pixel-diff baselines — live map tiles make comparisons brittle, so the specs snapshot without comparing (an explicit project decision). Every capture also asserts zero console/page errors.

Captures are written as JPEG at quality 80 — chosen for the photographic map imagery, which compresses well without visible artefacts, keeping the committed matrix low-weight.

**Conventions:**

- README heroes are 1280×720; the matrix uses each device's viewport from `VIEWPORTS` in `ui-states.spec.js`
- README heroes are captured from a cold start that fits a random country — the spec requests `?country=random`, which outranks timezone and locale, so the country shown changes on every regeneration
- Dark is the suite default (`colorScheme: 'dark'` in `playwright.config.js`); the light hero opts in explicitly
- Test names describe the UI state being captured
- Add a screenshot when the visual output meaningfully illustrates the behaviour

The matrix specs carry generous file-level timeout budgets, sized for SwiftShader's slow stability checks — the renderer CI uses, and `E2E_SWIFTSHADER=1` reproduces (the matrix itself now runs locally in GPU mode): `ui-states.spec.js` uses `test.setTimeout(300000)`, while `readme.spec.js` and `sw.spec.js` use `120000`. `tests/e2e/core.spec.js` and `tests/e2e/features/recordings.spec.js` carry the same `120000` budget for their chip-click and reload interactions. `tests/e2e/features/routes.spec.js` uses `60000`: a software-rendered (SwiftShader) click-actionability stall can exceed the default 30 s budget even when the target is visible.

Both screenshot specs — `ui-states.spec.js` and `readme.spec.js` — use the shared 60 s `waitForMapIdle` (see [Waiting for the map](#waiting-for-the-map)) and configure file-scope `retries: 1`: a stalled live raster or TileJSON request under full-suite load can delay map-idle, so this guards local regenerations across every test in each file, not just the six matrix viewports. CI is unaffected — it excludes the `@screenshots` specs and applies its own global `retries: 2`.
