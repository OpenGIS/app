# Testing

ogis.app has two test layers:

- **Unit tests** (Vitest) — test pure composable logic in milliseconds
- **E2E tests** (Playwright) — test full browser integration

```bash
npm run test:unit                                     # Vitest — < 10 s
npm run test:e2e -- tests/e2e/core.spec.js            # single spec (recommended during development)
npm run test:e2e -- --workers=4                       # full E2E suite incl. screenshots — local final verification
npm test                                              # unit tests only (rapid development)
```

- Unit tests complete in under 10 seconds — use `npm test` and targeted spec runs during rapid development. **Unit tests need Node 24** (CI uses Node 24); on Node 22.18 six `tests/unit/countries.test.js` tests fail because `countryCodeFromTimeZone` deliberately returns null when `Intl.Locale.prototype.getTimeZones` is unavailable.
- The full local E2E run with `--workers=4` is the final verification before declaring a task complete. Functional specs run on the local GPU path; the `@screenshots` matrix runs in the dedicated, always-SwiftShader `screenshots` project and regenerates the committed `screenshots/` artefacts deterministically; seconds to a few minutes per test subset, with the screenshot matrix dominating (~18–20 min end to end).
- SwiftShader is the CI renderer for functional specs. Set `E2E_SWIFTSHADER=1` to reproduce CI rendering locally; it is much slower, so keep it for renderer-specific checks rather than everyday runs. The `screenshots` project **always** uses SwiftShader regardless of this switch — see [E2E rendering modes](#e2e-rendering-modes).
- CI runs the **functional** E2E suite only — the screenshot matrix is excluded via `--grep-invert @screenshots` (see [CI](./13.ci.md)). CI splits the functional suite across three shards; within a shard Playwright runs serially and retries twice (`CI=1` in `playwright.config.js`).
- `playwright.config.js` sets no `actionTimeout` override. A tight bound was tried and reverted because software-rendered (SwiftShader) actionability stalls can exceed several seconds under load, causing false failures. Actions therefore fall back to Playwright's default bound (the test timeout).

## E2E rendering modes

`playwright.config.js` defines two Playwright projects with different rendering requirements:

| Project       | Specs collected                                                | Renderer                                                                                             | Renderer trigger                                           |
| ------------- | -------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| `chromium`    | Functional specs + README heroes (`ui-states.spec.js` ignored) | Full Chromium build (`channel: "chromium"`); `--use-angle=metal` on macOS, default backend elsewhere | GPU locally; SwiftShader when `CI=1` / `E2E_SWIFTSHADER=1` |
| `screenshots` | `tests/e2e/screenshots/**/*.spec.js` except `readme.spec.js`   | Bundled Chromium (no `channel`), pinned SwiftShader                                                  | Always software-rendered, regardless of environment        |

The functional project (`chromium`) keeps GPU as its local default so test subsets stay fast — measured: 61–62-test subsets complete in 1.5–4.7 min headed. CI (`CI=1`) and `E2E_SWIFTSHADER=1` swap it to SwiftShader, the deterministic software renderer CI has always used. SwiftShader is much slower locally (measured: 61 tests at 2 workers in ~10.4 min), so keep `E2E_SWIFTSHADER=1` for renderer-specific checks rather than everyday runs. On a fresh machine, `npx playwright install chromium` installs the full build; CI installs `chromium --with-deps`.

The `screenshots` project captures the committed matrix and is **always** software-rendered with the bundled Chromium build, whatever the environment. GPU rasterisation (ANGLE/Metal) is not byte-stable across browser launches: repeated full-matrix runs drifted sub-perceptually with no code, version or fixture change (edge-localised anti-aliasing, mean Δ≈0.167 per channel, max Δ129). Pinning the capture renderer to SwiftShader makes the raster reproducible. It passes `--use-angle=swiftshader --enable-unsafe-swiftshader` plus `--force-color-profile=srgb --disable-lcd-text --font-render-hinting=none --disable-gpu-rasterization --disable-partial-raster --num-raster-threads=1`, which pin the colour pipeline and text rasterisation. The README heroes are deliberately excluded from this project (`testIgnore`) — they cold-start on a random country against live tiles and are meant to differ every run — so they stay on the GPU `chromium` path.

`--deny-permission-prompts` is passed in **all** rendering paths, so headed runs deny un-granted permissions (e.g. geolocation) deterministically instead of hanging on an interactive prompt. Specs that need a position grant it explicitly via CDP — `context.grantPermissions()` plus `setGeolocation()` — and the CDP grant overrides the deny switch.

## Map-asset fixtures

MapLibre previously loaded the style, sprites and glyphs from live origins during E2E runs. Under load, `https://www.ogis.org` returned HTTP 429 without CORS headers, which surfaced as browser console errors and made `expectNoConsoleErrors` fail intermittently in the `ui-states` and `sw` specs. The suite now serves those assets from committed fixtures, so every spec except the README hero captures runs without touching the live origin.

Vendored under [`tests/fixtures/map/`](../tests/fixtures/map/):

- `style.json` — the canonical fixture style. The generator fetches the live style and rewrites every committable-host URL (sources, glyphs, sprites) into the `__E2E_MAP_BASE__/<host>/<path>` placeholder form; excluded hosts stay live.
- `demoArea.mjs` — the area and policy single source of truth: centre, bounds, screenshot zoom, coverage zooms, the excluded sources (with reasons), the committable-host allowlist, committed glyph ranges and sprite policy.
- `assets/**` — the vendored assets, keyed by host and path (`assets/www.ogis.org/basemap/sprite.{json,png}`, `assets/www.ogis.org/basemap/fonts/<stack>/0-255.pbf`, `assets/tile.ogis.app/…`). Sprites are 1× only — the suite runs at devicePixelRatio 1, so the @2x variants are deliberately omitted. Glyph directory names are URL-encoded.
- `assets.manifest.json` — every stored path with its byte count, source id and zoom, plus the expected-but-absent (`204`/`404`) tiles, used by the manifest-completeness unit test.
- `enumerate.mjs` — the pure `paddedTiles()` enumeration shared by the generator and its unit test, so the manifest-completeness assertion derives exactly the tile set the generator fetched.

Every spec except the README hero spec imports `test` from [`tests/e2e/helpers/test.js`](../tests/e2e/helpers/test.js); its `context` fixture installs the stubs ([`tests/e2e/helpers/mapAssets.js`](../tests/e2e/helpers/mapAssets.js)) before any page exists, so stubbed responses also cover service-worker requests. The stub serves the style URL from the pinned fixture (substituting the placeholder with the page origin) and blocks any unexpected external request; tiles, glyphs and sprites load same-origin from the [E2E Vite middleware](../tests/fixtures/map/vitePlugin.mjs) at `/__e2e_map__/**` with permissive CORS headers.

Unvendored tiles and glyph ranges never reach the network: the middleware fulfils them with an instant, CORS-permissive empty HTTP 200, so a missing range becomes neither a console error nor a live request. This keeps the offline-download spec fast — it deliberately prefetches all 256 ranges per fontstack, and none may take a round-trip. A missing sprite or style fixture, by contrast, returns 404 so drift fails loudly.

[`refresh.mjs`](../tests/fixtures/map/refresh.mjs) is the generator: it fetches the live style, rewrites it to the placeholder form, then derives the fetch list from that generated style — padding the demo bounds by one tile margin at every zoom, so a 1280×720 viewport at the screenshot zoom never hits a gap — and writes the tiles, sprites, glyphs and `assets.manifest.json`:

```bash
npm run fixtures:refresh
```

The refresh is a manual local step, deliberately **not** run in CI — CI uses the committed fixtures. Run it locally when the upstream style changes materially, review the diff and commit. `.prettierignore` excludes `tests/fixtures/` (generated/vendored).

## Writing E2E tests

```js
import { test, expect } from "./helpers/test.js";

test.describe("My feature / My heading", () => {
  test("does the thing", async ({ page }) => {
    await page.goto("/");
    await expect(page.locator(".my-element")).toBeVisible();
  });
});
```

- Import `test`/`expect` from `./helpers/test.js` so the map-asset stubs are installed on the context (see [Map-asset fixtures](#map-asset-fixtures)); a spec should never import the base `test` from `@playwright/test` directly — the README hero spec is the deliberate exception (see [Screenshot determinism](#screenshot-determinism))
- Track and assert a clean console with `trackConsoleErrors(page)` / `expectNoConsoleErrors(page)` from `helpers/console.js` — shared by the `sw`, `ui-states` and `routes` specs, and filters expected network noise: Mapterhorn raster tiles and the deliberately excluded Esri World Imagery are both served 404
- Use `page.addInitScript` to seed `localStorage` before navigation
- Storage keys: `ogis_{namespace}_{instanceId}` — the default id is `'app'`, so the view key is `ogis_view_app`
- Settings are OS-derived and write nothing — there is no `ogis_settings_*` key to seed or assert
- Pin the browser timezone with `test.use({ timezoneId })` when a test depends on cold-start country focus — timezone resolution sits above locale in the cascade, so the fitted country is deterministic on any host machine (`core.spec.js` uses `Europe/London`)
- Poll for throttled async side-effects with `expect.poll()` rather than `waitForTimeout`

### Waiting for the map

The map and panel waits are shared — [`tests/e2e/helpers/panel.js`](../tests/e2e/helpers/panel.js) exports `waitForMapReady`, `waitForPanelSettled` and `openMenuPanel`, and the map-focused specs (`core`, `locate`, `recordings`, `routes`) import them.

`waitForMapReady(page)` waits on three cheap, deterministic conditions:

1. the `#menu-button` chip is visible;
2. `.ogis-map` has `data-map-ready="true"` (explicit 30 s backstop);
3. `.ogis-panel` carries neither the offcanvas `showing` nor `hiding` class — a defensive guard, since the app has no Bootstrap JS and those transitional classes are not expected to appear.

`waitForPanelSettled(page)` additionally waits for the panel's CSS `transform` to reach `none` (the 0.25 s offcanvas slide), so geometry is measured only after it has settled; `openMenuPanel(page)` clicks the menu chip, asserts the `show` class, then waits for that settle. Both use explicit 30 s timeouts.

`data-map-ready` is set by `useMap` at MapLibre `style.load` — the same point the map instance is published and `map:ready` is emitted — so the map is usable and its features are wired up. It deliberately does **not** wait for MapLibre's render-bound `load` or the `data-map-idle` settle; `data-map-idle` is a predicate-driven signal published by `useMap` once `!map.isMoving() && map.areTilesLoaded()` holds: MapLibre's `idle` is the primary trigger, `movestart`/`zoomstart` clear the attribute, and `moveend`/`zoomend`/`sourcedata`/`load` arm a bounded animation-frame retry (MapLibre can skip `idle` entirely when the final render pass schedules no next frame). It is used only where a rendered tile set is actually asserted: the screenshot specs (through the shared wait helper), `sw.spec.js`, and a few cold-start checks in `core.spec.js`.

Screenshot specs wait on that idle settle through `waitForMapIdle(page, testInfo, { timeout = 60000 })` in [`helpers/mapIdle.js`](../tests/e2e/helpers/mapIdle.js), which asserts `data-map-idle="true"` and, on timeout, attaches a `map-idle-diagnostics` text attachment to the test report before rethrowing the original error. The attachment records page state (URL, `navigator.onLine`, the map's `data-map-ready`/`data-map-idle` values), the in-flight requests held by `trackPendingRequests(page)`, and failed or aborted resources from the Performance Resource Timing API — both capped so a pathological run cannot attach an unbounded blob. The tracker must be installed before navigation, which the `page` fixture in `helpers/test.js` guarantees for every spec. This exists because a stalled live raster or TileJSON request blocks MapLibre's `idle` event and MapLibre applies no per-request timeout, so a flaky origin otherwise fails as a bare "attribute did not become true" with nothing pointing at the culprit. The tracker is the primary signal: resource timing only records completed responses, so a request still stalled at timeout may not appear there at all.

All former `waitForLoadState("networkidle")` calls were replaced by `waitForMapReady`: network idle is slower and non-deterministic (tiles and glyphs can keep streaming), whereas the app-ready signal is a definite point in app state.

For camera moves, wait on the expected URL hash rather than a tile render. Locate's `waitForCameraSettle(page, expectedHash)` polls the URL (written on MapLibre `moveend`) until it matches the target view; anchoring on the _expected_ hash is race-safe, since a pending move's pre-move hash differs and the wait cannot resolve early. A full tile-render wait (`data-map-idle`) after a locate fly-to (z16 + terrain/hillshade) measured ~246–275 s under SwiftShader + load, but no locate assertion inspects a rendered tile set. Even locate's cold load uses `waitForMapReady` — the locate spec has no full map-idle wait. Locate budgets: `CAMERA_SETTLE_TIMEOUT` 30000 ms, `LOCATE_TIMEOUT` 60000 ms, file-level `test.setTimeout(420000)`.

## Colour scheme (dark by default)

`playwright.config.js` sets `colorScheme: 'dark'` in the shared `use`, so every spec and screenshot inherits dark. The app has no in-app theme toggle — it follows the OS/browser `prefers-color-scheme` setting via `useSettings` — so dark-by-default is a test convention, not an app default.

Light mode is verified explicitly by `readme.spec.js`: the light hero requests `colorScheme: 'light'` and asserts `data-bs-theme="light"` on `<html>` (the app's theme application point), while the dark captures assert the complementary `data-bs-theme="dark"`, proving both directions of the downstream OS/browser setting. `settings.spec.js` keeps its own explicit light/dark behaviour tests for the runtime `prefers-color-scheme` change, plus a regression test that the locate-confirm modal — teleported outside `.ogis-root` — resolves the same dark background as the app root.

Screenshots are committed so the README and docs render on GitHub. They are generated only by local runs — the `@screenshots` specs are excluded from CI (see [CI](./13.ci.md)) — and the full local suite regenerates them as its final-verification step. They are **not** pixel-diff baselines: the specs snapshot without comparing (an explicit project decision). Every capture also asserts zero console/page errors.

Captures are written as JPEG at quality 80 — chosen for the photographic map imagery, which compresses well without visible artefacts, keeping the committed matrix low-weight.

### Screenshot determinism

The committed matrix is byte-reproducible under the full-suite path. Captures run in the dedicated `screenshots` project, which is always SwiftShader-rendered and pins the colour/text pipeline (see [E2E rendering modes](#e2e-rendering-modes)) — GPU rasterisation is not byte-stable across launches, which is what previously left `closed.jpg` with two anti-aliasing variants.

Determinism rests on deliberate capture measures:

- `ui-states.spec.js` seeds `Math.random` before boot (stable auto-assigned feature colours and route ids) and pins clock-derived values (recording/offline timestamps, the live elapsed timer, the Storage API estimate).
- Map assets come from the committed fixture set pinned to the [demo area](#map-asset-fixtures), so tiles, sprites and glyphs are identical every run.
- `useMap` passes MapLibre `fadeDuration: 0` when `VITE_E2E_FIXTURES === "1"` (a test-only gate; the production bundle is unchanged). The label-collision fade is time-based (`Placement.symbolFadeChange`), the symbol shader culls symbols below 0.1 opacity, and a capture taken after the map stops rendering can freeze a mid-fade frame with missing labels. A zero fade makes every rendered frame show symbols fully opaque; fades are entrance-only, so steady-state rendering and production output are unchanged.
- [`waitForLayoutSettled`](../tests/e2e/helpers/layout.js) waits for every CSS animation/transition inside the app root to finish, the MapLibre canvas drawing buffer to match its container across three consecutive animation frames, the app's `data-map-idle` signal, and the glyph/paint settle below.
- [`waitForMapQuiet`](../tests/e2e/helpers/mapIdle.js) waits for MapLibre's own composite state to hold still (placement and style/source updates idle, no pending layer/source work), then ends with a sustained ~800 ms `renderBurst` plus a presented final frame. A committed placement does not always schedule a render — `Style._updatePlacement` can report "no change" once the new placement has no transitions — and a screenshot never triggers a MapLibre render, so the settle must actively drive renders.
- `waitForGlyphsQuiesce(page, { quietMs = 500 })` holds until no `/fonts/` glyph fetch has been in flight for a sustained window. Glyph ranges can be discovered by a late tile parse after a momentary lull; a placement that runs before the glyph lands skips the symbol, and the follow-up re-placement is not guaranteed a render. [`waitForMapPainted`](../tests/e2e/helpers/mapIdle.js) therefore ends with `waitForGlyphsQuiesce` followed by one more `renderBurst(300)` before capture.
- `capture()` is an active render-then-compare loop: each round drives `renderBurst(300)` + a 250 ms present wait + a screenshot, and the shot is accepted only once two consecutive burst-separated frames are byte-identical (bounded at `MAX_ROUNDS = 12`).
- A reduced capture-time style suppression (`stabilizeCaptureRendering`, applied at the five capture call sites) disables `backdrop-filter` and `box-shadow` via an injected style tag (`*,*::before,*::after{…}`). These GPU-composited layers left ~0.9 % of pixels drifting at max Δ71 under a full 4-worker run even though the underlying page was identical; a full-removal attempt reintroduced the drift, so the suppression stays. It is capture-only — production rendering is untouched — and the earlier border override was removed.
- A terrain depth pin (`pinTerrainDepthFar`, applied only to the `feature offline region` capture) clears the terrain depth framebuffer to the far plane and freezes `painter.maybeDrawDepth`, making the symbol shader's `calculate_visibility()` factor exactly 1. MapLibre multiplies every symbol's alpha by that factor, which samples the terrain depth framebuffer; the framebuffer is redrawn only when the camera matrix changes — not when a raster-DEM tile's _data_ finishes loading — so a symbol on the terrain surface could sample as "in front" (alpha ≈1.0, the committed capture) or, after an unrelated camera change, as "slightly behind" (alpha ≈0.87). That was the intermittent sub-pixel variant on the demo's food POI in `feature-offline`; the pin makes the factor deterministic rather than masking a timing race, and the other 45 captures keep their natural terrain occlusion. Best-effort — a missing map/terrain leaves the capture untouched.
- Each capture writes a diagnostics JSON **after** the write (it never affects the JPEG), and only when `E2E_SCREENSHOTS_DIR` is set — committed in-place runs write nothing — to `${E2E_SCREENSHOTS_DIR}/diag/<E2E_SCREENSHOTS_DIR basename>/<device>-<orientation>-<state>.json`. It records the map camera, canvas size, source ids, symbol-layer pairs, label features from `querySourceFeatures`, tile-cache entries, map-fixture resource timings and the settle flags, so a non-reproducible capture can be diffed to locate the differing input.

**Verification:** the matrix is byte-reproducible under the full-suite path — the full local suite (`npm run test:e2e -- --workers=4`) passes (103 passed, 11 skipped, ~18–20 min) and regenerates all 46 committed JPEGs byte-identically. The last intermittent capture, `desktop/landscape/feature-offline.jpg` (roughly 2 in 10 runs; ~450 pixels differing by more than 8, max channel delta 39, localised to the demo's food POI icon and label), is resolved by the terrain depth pin above: three consecutive full screenshots-project runs each regenerated all 46 JPEGs byte-identically to the committed matrix. That is strong, mechanism-backed evidence rather than a proof of universal determinism — the pin fixes the one symbol-shader input that varied, not every conceivable raster difference. `screenshots/` was re-baselined once from the stable capture set.

The README heroes remain the deliberate exception — **intentionally non-deterministic live captures**. Each is a genuine cold start against `?country=random` over live (un-stubbed) map tiles, so the framed country and imagery differ every run; they are the suite's only live-network output. `readme.spec.js` therefore imports Playwright's base `test` rather than `helpers/test.js`, and stays on the GPU `chromium` project.

**Conventions:**

- README heroes are 1280×720; the matrix uses each device's viewport from `VIEWPORTS` in `ui-states.spec.js`
- README heroes are live captures of a random-country cold start (`?country=random`) and differ every run by design; the matrix view is pinned to the demo area (geometry from `fixtures/demo.mjs`, `screenshotZoom` re-exported via `fixtures/map/demoArea.mjs`)
- Dark is the suite default (`colorScheme: 'dark'` in `playwright.config.js`); the light hero opts in explicitly
- Test names describe the UI state being captured
- Add a screenshot when the visual output meaningfully illustrates the behaviour

The matrix specs carry generous file-level timeout budgets, sized for SwiftShader's slow stability checks — the renderer the `screenshots` project always uses: `ui-states.spec.js` uses `test.setTimeout(900000)` — one matrix test loops all seven states for a single viewport and was measured at >300 s under 4 concurrent SwiftShader workers, so 15 minutes leaves ample headroom — while `readme.spec.js` and `sw.spec.js` use `120000`. `tests/e2e/core.spec.js` and `tests/e2e/features/recordings.spec.js` carry the same `120000` budget for their chip-click and reload interactions. `tests/e2e/features/routes.spec.js` uses `60000`: a software-rendered (SwiftShader) click-actionability stall can exceed the default 30 s budget even when the target is visible.

Both screenshot specs — `ui-states.spec.js` and `readme.spec.js` — use the shared 60 s `waitForMapIdle` (see [Waiting for the map](#waiting-for-the-map)) and configure file-scope `retries: 1`: a stalled live raster or TileJSON request under full-suite load can delay map-idle, so this guards local regenerations across every test in each file, not just the six matrix viewports. CI is unaffected — it excludes the `@screenshots` specs and applies its own global `retries: 2`.
