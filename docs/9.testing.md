# Testing

ogis.app has two test layers:

- **Unit tests** (Vitest) — test pure composable logic in milliseconds
- **E2E tests** (Playwright) — test full browser integration

```bash
npm run test:unit                                     # Vitest
npm run test:e2e -- tests/e2e/core.spec.js            # single spec (recommended during development)
npm run test:e2e                             # functional E2E + README heroes — optional local fallback
npm run test:matrix                          # screenshot matrix only (fast local; temp output)
npm run test:matrix:update                   # in-place re-baseline of the committed matrix (headless, deterministic)
npm run screenshots:diff                     # compare temp captures with the committed matrix (report only)
npm run screenshots:fetch -- --run <run-id>  # CI-sourced re-baseline (manual exception path; --write to apply)
npm test                                              # unit tests only (rapid development)
npm run check                                         # fast pre-push gate: Prettier check + unit tests
```

- Unit tests are fast — use `npm test` and targeted spec runs during rapid development. **Unit tests need Node 24** (CI uses Node 24); on older Node the `tests/unit/countries.test.js` cases that depend on `Intl.Locale.prototype.getTimeZones` fail, because `countryCodeFromTimeZone` deliberately returns null when it is unavailable.
- A task is done when `ci.yml` is green on its pushed commits — unit, commit check and functional E2E. The matrix is deliberately outside the push path: the `Screenshots` workflow runs on pull requests and on a daily schedule (or manual dispatch), and heals a moved `master` baseline by itself. Local habits stay fast: `npm run check` (Prettier check plus unit tests) as the pre-push gate, and the watch loops and spec runs below. The full local E2E run (`npm run test:e2e`) is an optional fallback — offline, or when the local GPU functional path is specifically wanted — not a required step before declaring done. It runs the functional specs plus the README heroes on the local GPU path; the `@screenshots` matrix is outside it and runs separately via `npm run test:matrix`, in the dedicated, always-SwiftShader `screenshots` project. A plain local matrix run is **fast and safe**: it is unpinned, runs parallel workers, and writes captures to a gitignored temp dir (`.opencode/tmp/screenshots/`), so it never touches the committed PNGs and never checks them. The local loop is relative and visual (`npm run screenshots:diff` reports which captures changed), while committed-matrix re-baselining is CI-sourced: a scheduled (or manually dispatched) run self-heals the baseline automatically from the `Screenshots` workflow's own captures, with `npm run screenshots:fetch` as the manual exception path. GitHub's `Screenshots` workflow remains the authority for the committed matrix, which it verifies within a strict pixel tolerance. See [Screenshot determinism](#screenshot-determinism) and [CI-sourced re-baseline](#ci-sourced-re-baseline).
- SwiftShader is the CI renderer for functional specs. Set `E2E_SWIFTSHADER=1` to reproduce CI rendering locally; it is much slower, so keep it for renderer-specific checks rather than everyday runs. The `screenshots` project **always** uses SwiftShader regardless of this switch — see [E2E rendering modes](#e2e-rendering-modes).
- CI runs the **functional** E2E suite only — the screenshot matrix is excluded from `ci.yml` via `--grep-invert @screenshots` (see [CI](./13.ci.md)). CI splits the functional suite across four shards; within a shard Playwright runs serially and retries twice (`CI=1` in `playwright.config.js`). The committed screenshot matrix is verified separately by the `Screenshots` workflow, not by `ci.yml`.
- `playwright.config.js` sets no `actionTimeout` override. A tight bound was tried and reverted because software-rendered (SwiftShader) actionability stalls can exceed several seconds under load, causing false failures. Actions therefore fall back to Playwright's default bound (the test timeout).

## E2E rendering modes

`playwright.config.js` defines two Playwright projects with different rendering requirements:

| Project       | Specs collected                                                | Renderer                                                                                             | Renderer trigger                                           |
| ------------- | -------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| `chromium`    | Functional specs + README heroes (`ui-states.spec.js` ignored) | Full Chromium build (`channel: "chromium"`); `--use-angle=metal` on macOS, default backend elsewhere | GPU locally; SwiftShader when `CI=1` / `E2E_SWIFTSHADER=1` |
| `screenshots` | `tests/e2e/screenshots/**/*.spec.js` except `readme.spec.js`   | Bundled Chromium (no `channel`), pinned SwiftShader                                                  | Always software-rendered, regardless of environment        |

The functional project (`chromium`) keeps GPU as its local default so test subsets stay fast. CI (`CI=1`) and `E2E_SWIFTSHADER=1` swap it to SwiftShader, the deterministic software renderer CI has always used. SwiftShader is much slower locally, so keep `E2E_SWIFTSHADER=1` for renderer-specific checks rather than everyday runs. On a fresh machine, `npx playwright install chromium` installs the full build; CI installs `chromium --with-deps`.

The `screenshots` project captures the committed matrix and is **always** software-rendered with the bundled Chromium build, whatever the environment. GPU rasterisation (ANGLE/Metal) is not byte-stable across browser launches: repeated full-matrix runs drifted sub-perceptually with no code, version or fixture change (edge-localised anti-aliasing). Pinning the capture renderer to SwiftShader removes that launch-to-launch drift, so a given machine's captures are reproducible run-to-run. It passes `--use-angle=swiftshader --enable-unsafe-swiftshader` plus `--force-color-profile=srgb --disable-lcd-text --font-render-hinting=none --disable-gpu-rasterization --disable-partial-raster --num-raster-threads=1`, which pin the colour pipeline and text rasterisation. The README heroes are deliberately excluded from this project (`testIgnore`) — they cold-start on a random country against live tiles and are meant to differ every run — so they stay on the GPU `chromium` path.

The `screenshots` project is always SwiftShader-rendered, but the SwiftShader worker pool is pinned to a single thread **only on the deterministic path**:

- [`isDeterministicRun()`](../tests/e2e/helpers/determinism.js) is `CI || E2E_SWIFTSHADER_PIN === "1" || E2E_SCREENSHOTS_COMMIT === "1"`. When that predicate holds, `determinismSetup.js` writes `[Processor] ThreadCount=1` to `SwiftShader.ini` in the browser's working directory before any browser launches, and `determinismTeardown.js` removes it.
- The pin exists because SwiftShader's default multi-threaded rasterisation of antialiased vector geometry is not bit-reproducible across browser launches: a sub-level pixel flip appears intermittently in desktop-landscape captures. Serialising it removes the launch-to-launch flip, but does not by itself guarantee byte-equality with the committed matrix (see [Screenshot determinism](#screenshot-determinism)).
- `playwright.config.js` pairs the pin with `workers: isDeterministicRun() ? 1 : undefined`: a deterministic run is single-worker, a plain local run uses Playwright's default parallelism. An explicit `--workers=N` still overrides either way — do not pass it on the deterministic path, since concurrent workers reintroduce the contention flake (the page's main thread is starved and the animation-settle poller times out with nothing actually stuck).

The pin therefore applies to:

- `CI` — both the functional shard job and the matrix capture shards, since `CI=1`.
- `E2E_SWIFTSHADER_PIN=1` — an explicit local opt-in for reproducible local captures that does not write the committed matrix.
- `E2E_SCREENSHOTS_COMMIT=1` — the in-place re-baseline, which implies the whole deterministic path.

The `Screenshots` workflow's aggregate `verify` job runs on `ubuntu-latest` and only decodes and compares the captured files, so it does not render or use the pin. A plain local run renders the GPU-capable Chromium build, writes no `SwiftShader.ini` and stays fast. The pin's cost is significant — the matrix takes much longer under it — which is why the settle ceilings are widened (`waitForAnimationsSettled` 30 s → 300 s in `helpers/layout.js`; `waitForMapIdle` 60 s → 180 s in `helpers/mapIdle.js`).

`--deny-permission-prompts` is passed in **all** rendering paths, so headed runs deny un-granted permissions (e.g. geolocation) deterministically instead of hanging on an interactive prompt. Specs that need a position grant it explicitly via CDP — `context.grantPermissions()` plus `setGeolocation()` — and the CDP grant overrides the deny switch.

## Local iteration loops

Helper scripts tighten the edit-run loop; they are plain Node ESM under `scripts/`. Unit tests run once with `npm test` (Vitest) — fast enough that the loops below focus on E2E. The watch and diff loops need no extra packages; the CI fetch tool additionally needs the `gh` CLI.

### Watch loops

`npm run watch:e2e` runs the functional suite once, then reruns it whenever a file under `src/` or `tests/e2e/` changes. `npm run watch:matrix` does the same for the screenshot matrix. Both debounce changes (~300 ms, collapsing edit bursts) and allow **one Playwright run at a time** — a change that lands mid-run queues exactly one follow-up, never a stack. Output is the compact `line` reporter; nothing auto-opens. Ctrl-C stops the loop, terminating the running child cleanly.

Extra arguments pass straight through to `playwright test`:

```bash
npm run watch:e2e -- tests/e2e/core.spec.js
npm run watch:matrix -- --grep "captures desktop landscape states"
```

Defaults are injected only when not already supplied. The functional loop (`watch:e2e`) targets the `chromium` project and passes `--grep-invert @screenshots`, so README heroes are not regenerated and the matrix is not captured while watching. The matrix loop (`watch:matrix`) targets the `screenshots` project — and, because every matrix spec is tagged `@screenshots`, the grep-invert default is deliberately skipped there so the loop actually collects its specs.

### Screenshot diff loop

The local loop is **relative and visual**: capture after a change and diff it against a previous capture tree — or against the committed matrix — to see exactly which captures moved. Diff a fresh capture against the committed matrix, or point `--baseline` and `--candidate` at two local trees to compare before and after directly. A deterministic run writes to the gitignored temp tree, never the committed one:

```bash
E2E_SWIFTSHADER_PIN=1 npm run test:matrix   # deterministic captures → .opencode/tmp/screenshots/
npm run screenshots:diff                    # report only; exits 0
npm run screenshots:diff -- --fail-on-diff  # exit 1 on any difference
npm run screenshots:diff -- --html          # writes .opencode/tmp/screenshot-diff/index.html
npm run screenshots:bundle -- --committed screenshots --captured .opencode/tmp/screenshots --out .opencode/tmp/diff-bundle  # reviewable diff bundle (before/after/diff PNGs + index.html)
```

The diff compares the two trees by sha256 and reports **changed**, **only in baseline** and **only in candidate** files (any `diag/` directory is skipped). Local captures are deterministic run-to-run on a given machine, but rendering can differ sub-perceptually between machine environments: a small, stable set of one- to two-level differences against the committed tree is drift, not a regression, and it cancels out in a before/after comparison of two local trees. Treat a locally visible before/after change as the acceptance signal for UI work (`--html` gives the side-by-side view); targeted `--grep` runs keep the loop tight. GitHub's `Screenshots` workflow remains the authority for the committed matrix, comparing decoded pixels within a strict tolerance rather than bytes (`npm run screenshots:verify` runs the same check locally). The same bundle the workflow attaches when a run moves the matrix can be generated locally with `npm run screenshots:bundle` — per-file before/after/diff PNGs alongside a self-contained `index.html`, `summary.md` and `report.json`.

### CI-sourced re-baseline

Committed-matrix re-baselining is sourced from CI and deliberately decoupled from pushes. After a change that intentionally moves captures, the next `Screenshots` workflow run on `master` — the daily schedule (07:30 UTC) or a manual dispatch — captures a fresh matrix: verification against the old committed set reports exactly which captures moved, and the workflow's `refresh` job rebuilds the baseline from that same run's captures and commits it as `github-actions[bot]`, so the developer's side is just `git pull`. This automatic path is primary: a `master` push neither runs nor waits on the matrix. It fires only on a genuine beyond-tolerance move (sub-tolerance drift passes and never triggers it) and only when the capture set is complete and valid, so a partial or empty set is never blessed (the job fails and the run stays red for a human). A pull request never heals: a red verification there is a review signal, presented as a diff bundle and — for same-repository PRs — a sticky comment (see [CI — Screenshot matrix workflow](./13.ci.md#screenshot-matrix-workflow)). On `master` a healed or cleanly deferred run ends green; two guards defer the heal rather than push into trouble — a `ci.yml` run in flight on `master`, or `master` having advanced past the run's SHA — and the next scheduled run is expected to heal. There is no dispatched re-verification loop: the next run verifies.

Manual fetching is the **exception** path — a pull request, or a run whose capture set was failed or incomplete:

```bash
npm run screenshots:fetch -- --run <run-id>          # dry run: download, assemble, compare (sha256)
npm run screenshots:fetch -- --run <run-id> --write  # write the assembled matrix into screenshots/
```

The tool downloads the run's shard artefacts (it needs the `gh` CLI), assembles them into one matrix and compares it against the committed tree; only with `--write` does it update `screenshots/`. Before writing anything it validates the assembled set — all six shards present, no `diag/**`, every file a valid PNG, and no committed file missing from the set unless `--allow-removals` is passed (which lets a `--write` remove those files) — and it writes a report beside the assembled tree. Review the written matrix, commit it, and the next workflow run verifies green; the fetch tool was validated end-to-end against a green run, whose assembled matrix matched the committed tree exactly. `--artifacts <dir>` assembles from an already-downloaded shard tree (the layout the `refresh` job feeds it) instead of fetching with `gh`; `--branch <name>` fetches the latest completed run for a branch instead of a run id. The older `npm run test:matrix:update` still writes the committed tree from local captures and remains valid only where the machine's rendering matches the CI capture environment.

> `account`, `collections` and `maps` specs are marked `test.describe.skip` while their features are commented out in `src/main.js` (lines 16–20, 113–116). Remove the skip when the features ship.

## Map-asset fixtures

MapLibre previously loaded the style, sprites and glyphs from live origins during E2E runs. Under load, `https://www.ogis.org` returned HTTP 429 without CORS headers, which surfaced as browser console errors and made `expectNoConsoleErrors` fail intermittently in the `ui-states` and `sw` specs. The suite now serves those assets from committed fixtures, so every spec except the README hero captures runs without touching the live origin.

The fixture set — its contents, serving, degradation policy and refresh workflow — is defined canonically in [Terminology — Fixture set](./1.terminology.md#fixture-set).

Every spec except the README hero spec imports `test` from [`tests/e2e/helpers/test.js`](../tests/e2e/helpers/test.js); its `context` fixture installs the stubs ([`tests/e2e/helpers/mapAssets.js`](../tests/e2e/helpers/mapAssets.js)) before any page exists, so stubbed responses also cover service-worker requests. The stub serves the style URL from the pinned fixture (substituting the placeholder with the page origin) and blocks any unexpected external request; tiles, glyphs and sprites load same-origin from the [E2E Vite middleware](../tests/fixtures/map/vitePlugin.mjs) at `/__e2e_map__/**` with permissive CORS headers.

Unvendored tiles and glyph ranges never reach the network — the middleware's empty-200 degradation (see [Terminology — Fixture set](./1.terminology.md#fixture-set)) keeps the offline-download spec fast, since it deliberately prefetches all 256 ranges per fontstack and none may take a round-trip. A missing sprite or `style.json` fixture fails loudly (a `404`, or a throw in the Playwright stub at request time) — drift fails either way.

[`refresh.mjs`](../tests/fixtures/map/refresh.mjs) is the generator; it pads the demo bounds by one tile margin at every zoom, so a 1280×720 viewport at the screenshot zoom never hits a gap:

```bash
npm run fixtures:refresh
```

## Writing E2E tests

```js
import { test, expect } from "./helpers/test.js";

test.describe("My feature / My heading", () => {
  test("does the thing", async ({ page }) => {
    await page.goto("/");
    await expect(page.locator(".my-element")).toBeVisible();
  });
});
```

- Import `test`/`expect` from `./helpers/test.js` so the map-asset stubs are installed on the context (see [Map-asset fixtures](#map-asset-fixtures)); a spec should never import the base `test` from `@playwright/test` directly — the README hero spec is the deliberate exception (see [Screenshot determinism](#screenshot-determinism))
- Track and assert a clean console with `trackConsoleErrors(page)` / `expectNoConsoleErrors(page)` from `helpers/console.js` — shared by the `sw`, `ui-states` and `routes` specs. It filters console errors whose URL is the Mapterhorn or Esri World Imagery host: Esri is deliberately served a 404, and the Mapterhorn filter is defensive against the raster overlay's occasional tile gaps.
- Use `page.addInitScript` to seed `localStorage` before navigation
- Storage keys: `ogis_{namespace}_{instanceId}` — the default id is `'app'`, so the view key is `ogis_view_app`. Read persisted values through `readStoredState(raw)` from [`helpers/storage.js`](../tests/e2e/helpers/storage.js): it unwraps the `{ __ogisState: 1, version, data }` envelope and still accepts legacy bare values
- Camera ownership and pane state are mirrored on `.ogis-root` as stable attributes: `data-modes` is the space-separated active mode ids (`follow`, `draw`, `navigate`) in registration order and is absent when none are active; `data-pane` is `info`, `menu` or `closed`. Assert these for hand-offs instead of inferring camera ownership from chip labels alone
- Settings are OS-derived and write nothing — there is no `ogis_settings_*` key to seed or assert
- Pin the browser timezone with `test.use({ timezoneId })` when a test depends on cold-start country focus — timezone resolution sits above locale in the cascade, so the fitted country is deterministic on any host machine (`core.spec.js` uses `Europe/London`)
- Poll for throttled async side-effects with `expect.poll()` rather than `waitForTimeout`

### Waiting for the map

The map and panel waits are shared — [`tests/e2e/helpers/panel.js`](../tests/e2e/helpers/panel.js) exports `waitForMapReady`, `waitForPanelSettled`, `openMenuPanel` and `openMenuTab`, and the map-focused specs (`core`, `locate`, `follow`, `map-actions`, `recordings`, `routes`) import them.

`waitForMapReady(page)` waits on three cheap, deterministic conditions:

1. the `#menu-button` chip is visible;
2. `.ogis-map` has `data-map-ready="true"` (explicit 30 s backstop);
3. `.ogis-panel` carries neither the offcanvas `showing` nor `hiding` class — a defensive guard, since the app has no Bootstrap JS and those transitional classes are not expected to appear.

`waitForPanelSettled(page)` additionally waits for the panel's CSS `transform` to reach `none` (the 0.25 s offcanvas slide), so geometry is measured only after it has settled; `openMenuPanel(page)` clicks the menu chip, asserts the `show` class, then waits for that settle. Both use explicit 30 s timeouts.

`data-map-ready` is set by `useMap` at MapLibre `style.load` — the same point the map instance is published and `map:ready` is emitted — so the map is usable and its features are wired up. It deliberately does **not** wait for MapLibre's render-bound `load` or the `data-map-idle` settle; `data-map-idle` is a predicate-driven signal published by `useMap` once `!map.isMoving() && map.areTilesLoaded()` holds: MapLibre's `idle` is the primary trigger, `movestart`/`zoomstart` clear the attribute, and `moveend`/`zoomend`/`sourcedata`/`load` arm a bounded animation-frame retry (MapLibre can skip `idle` entirely when the final render pass schedules no next frame). It is used only where a rendered tile set is actually asserted: the screenshot specs (through the shared wait helper), `sw.spec.js`, and a few cold-start checks in `core.spec.js`.

`data-map-state` is the lifecycle companion: `loading`, `ready` or `error`. A failed map has `data-map-state="error"` and no `data-map-ready`, so recovery tests can assert the failure state directly instead of racing `waitForMapReady`.

Screenshot specs wait on that idle settle through `waitForMapIdle(page, testInfo, { timeout = 180000 })` in [`helpers/mapIdle.js`](../tests/e2e/helpers/mapIdle.js), which asserts `data-map-idle="true"` and, on timeout, attaches a `map-idle-diagnostics` text attachment to the test report before rethrowing the original error. The attachment records page state (URL, `navigator.onLine`, the map's `data-map-ready`/`data-map-idle` values), the in-flight requests held by `trackPendingRequests(page)`, and failed or aborted resources from the Performance Resource Timing API — both capped so a pathological run cannot attach an unbounded blob. The tracker must be installed before navigation, which the `page` fixture in `helpers/test.js` guarantees for every spec. This exists because a stalled live raster or TileJSON request blocks MapLibre's `idle` event and MapLibre applies no per-request timeout, so a flaky origin otherwise fails as a bare "attribute did not become true" with nothing pointing at the culprit. The tracker is the primary signal: resource timing only records completed responses, so a request still stalled at timeout may not appear there at all.

All former `waitForLoadState("networkidle")` calls were replaced by `waitForMapReady`: network idle is slower and non-deterministic (tiles and glyphs can keep streaming), whereas the app-ready signal is a definite point in app state.

For camera moves, wait on the expected URL hash rather than a tile render. Locate's `waitForCameraSettle(page, expectedHash)` polls the URL (written on MapLibre `moveend`) until it matches the target view; anchoring on the _expected_ hash is race-safe, since a pending move's pre-move hash differs and the wait cannot resolve early. The locate spec derives its expected hash live from the production orient helpers (`fitZoomForDisc`, `horizonDistanceMetres`, `orientCameraDefaults`), imported through the dev server's module graph, so it follows the real viewport and formula instead of a hardcoded zoom. A full tile-render wait (`data-map-idle`) after a locate orientation flight (the viewport-fitted horizon-disc zoom + terrain/hillshade) is prohibitively slow under SwiftShader + load, but no locate assertion inspects a rendered tile set. Even locate's cold load uses `waitForMapReady` — the locate spec has no full map-idle wait. Locate budgets: `waitForCameraSettle` uses its shared 30000 ms default, `LOCATE_TIMEOUT` 60000 ms, file-level `test.setTimeout(420000)`.

The follow specs take a different route for the driver itself. While the follow camera owns the map its per-frame moves are deliberately not persisted, so the hash holds the pre-follow view and cannot be the settle signal; they read camera state through the map instance instead — `getMapInstance(instanceId)` in the page's module graph — for pitch, bearing, zoom, centre and the followed coordinate's projected screen position, and assert the hash only for the once-per-stop persist (and, after stop, for the released suppression). The integration spec derives its expected zooms from the production `navigationZoomForSpeed` through the same module graph and asserts the settled 45° third-person rest pitch. It also needs fixes that carry a speed and heading, which `context.setGeolocation` cannot express: `installGeolocationMock` ([`helpers/locate.js`](../tests/e2e/helpers/locate.js)) keeps the `watchPosition` callbacks on the page so a test can publish crafted fixes, and the compass is driven by streamed `deviceorientationabsolute` events — a single event would be cleared by the ~8 s heading watchdog.

### Routes navigation coverage

The routes navigation spec drives follow mode through `installGeolocationMock`, so fixes can be published after the watcher starts, and treats the top-centre navigation card as the user-visible contract: `.ogis-nav-control`'s `data-state`, compact label and accessible label. The menu chip remains recording-only. It covers:

- the locating, off-route, on-route and far-away card states;
- the green dashed `.ogis-nav-connector` polyline while off route within 1 km — it starts at the locate marker's centre and ends at the nearest point on the route — and its removal on route, beyond 1 km and on Stop;
- Stop ownership — navigation stops a follow it started, but leaves a follow the user started before Navigate running;
- navigation ending when the route is hidden or deleted, or when Locate stops or errors;
- one geolocation watcher for the session, released on Stop.

The far-fix case also exercises Locate's marker recovery. At distant coordinates a terrain DEM error can abort MapLibre's move dispatch and leave an HTML marker at a stale projection, so `useLocate` re-syncs markers on map `idle` and `moveend`, retrying on a bounded 120 s window (`MARKER_RETRY_TIMEOUT_MS` in [`useLocate.js`](../src/composables/useLocate.js)) until the map reports itself settled.

### Resilience coverage

[`tests/e2e/resilience.spec.js`](../tests/e2e/resilience.spec.js) covers the cross-cutting failure paths:

- the static boot fallback when the main module fails to load;
- corrupt stored state: unusable stores boot with defaults, the raw value is quarantined and the console stays clean;
- cross-tab view sync, including the no-echo check when the originating tab closes;
- a failed style document shows the overlay, and Retry recovers after the route is unblocked;
- WebGL context loss shows the error state and restoration clears it;
- unsupported WebGL shows the `unsupported` message.

Restore coverage lives with the features that own it:

- **Locate** — [`tests/e2e/features/locate.spec.js`](../tests/e2e/features/locate.spec.js) (`Locate / Restore`) seeds an envelope and covers an active restore, a following restore that keeps following a live fix, the OS-permission gate (no prompt, stored session cleared), a silent pre-fix error and persistence of later accepted fixes.

- **Recordings** — [`tests/e2e/features/recordings.spec.js`](../tests/e2e/features/recordings.spec.js) reads the envelope and asserts the interrupted active track restores as paused.

## Screenshots

Playwright generates the committed screenshot artefacts under `screenshots/`:

| Path                                                                  | Spec                                      | Contents                                                                                                                                                                                                                                                                                                                       |
| --------------------------------------------------------------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `DARK.jpg`, `LIGHT.jpg` (repo root)                                   | `tests/e2e/screenshots/readme.spec.js`    | 1280×720 README heroes (live cold start, random country) with the Info panel open                                                                                                                                                                                                                                              |
| `screenshots/{phone,tablet,desktop}/{portrait,landscape}/<state>.png` | `tests/e2e/screenshots/ui-states.spec.js` | core chrome states and the locate permission modals, at every device/orientation combination                                                                                                                                                                                                                                   |
| `screenshots/desktop/landscape/<state>.png`                           | `tests/e2e/screenshots/ui-states.spec.js` | the fully-populated feature states (routes, route navigation, offline region, saved recording) and the secondary UI states (idle/paused recording, empty/error routes, empty offline regions, expanded privacy disclosure, locate-following, following with the Info pane open (`follow-info-open`) and the locate error chip) |

That is the full committed matrix: the core chrome states and the locate permission modals across every viewport, plus the feature and secondary UI states at desktop landscape.

A local full-suite run (`npm run test:e2e`) regenerates the README heroes (`DARK.jpg`/`LIGHT.jpg`) in place but does not collect the matrix; capturing the matrix separately with `npm run test:matrix` writes to a gitignored temp dir — it never replaces the committed PNGs. Committed-matrix re-baselining is **CI-sourced** and decoupled from pushes (see [CI-sourced re-baseline](#ci-sourced-re-baseline)): when a scheduled (or manually dispatched) `master` run detects that the matrix moved, the `Screenshots` workflow's `refresh` job rebuilds `screenshots/` from that run's own captures; fetching those captures manually is the exception path. `npm run test:matrix:update` remains an in-place local re-baseline (headless, deterministic), valid only on a machine whose rendering matches the CI capture environment:

```bash
npm run screenshots:fetch -- --run <run-id> --write   # manual CI-sourced re-baseline (exception path)
npm run test:matrix:update                            # in-place local re-baseline (matching environments only)
```

Run the matrix without touching the committed PNGs, or target the whole `@screenshots` set or the README heroes:

```bash
npm run test:matrix
E2E_SCREENSHOTS_DIR=".opencode/tmp/ogis-shots" npm run test:matrix
npm run test:matrix -- --grep @screenshots
npm run test:e2e -- tests/e2e/screenshots/readme.spec.js
```

`ui-states.spec.js` resolves its capture root in order: `E2E_SCREENSHOTS_DIR` if set; else the committed `screenshots/` only when `E2E_SCREENSHOTS_COMMIT === "1"`; else a gitignored temp dir (`.opencode/tmp/screenshots/`). A plain local run therefore writes to the temp dir by default and cannot touch the committed PNGs; set `E2E_SCREENSHOTS_DIR` to redirect an exploratory or headed capture to any other throwaway directory.

Captures must run **headless**. The `screenshots` project pins `headless: true`, but `--headed` overrides that pin, so the real protection is `assertSafeOutputRoot()` — the first statement of `capture()` — which refuses to write into the committed `screenshots/` directory unless the run is both headless **and** explicitly opted in with `E2E_SCREENSHOTS_COMMIT=1`. A headed capture composites the corner-control chips (`backdrop-filter`/`box-shadow` GPU layers) and window chrome differently and is not byte-reproducible; every other output root (the default temp dir, an `E2E_SCREENSHOTS_DIR` override) is allowed from either mode.

> [!WARNING]
> A plain local run already writes to a gitignored temp dir, so the committed PNGs are safe by default. Prefer the CI-sourced `screenshots:fetch` flow for re-baselining; use `E2E_SCREENSHOTS_COMMIT=1` in place only on a headless host whose rendering matches the CI capture environment, so the committed PNGs are never replaced by a frame that CI cannot reproduce.

Screenshots are committed so the README and docs render on GitHub. The matrix is re-baselined from the `Screenshots` workflow's own captures — automatically by the `refresh` job on a scheduled or manually dispatched `master` run, with `npm run screenshots:fetch -- --run <run-id> --write` as the manual exception path; `E2E_SCREENSHOTS_COMMIT=1` remains an in-place local re-baseline for machines whose rendering matches CI. The workflow verifies the committed matrix within a strict pixel tolerance (`scripts/verify-matrix.js`); `ci.yml` excludes the `@screenshots` specs (see [CI](./13.ci.md)). `ui-states.spec.js` snapshots without comparing — the tolerance comparison is the GitHub workflow's, not the spec's. Every capture also asserts zero console/page errors.

The README heroes (`DARK.jpg`, `LIGHT.jpg`) are deliberately kept as JPEG and are regenerated **in place** by a full-suite run. That is intentional, not a bug: they are live random-country cold starts that differ every run by design, so unlike the deterministic matrix they are overwritten afresh on every run. See [Screenshot determinism](#screenshot-determinism).

Matrix captures are written as lossless PNG. Losslessness matters beyond the file size: the capture gate compares frames byte-for-byte, and JPEG's DCT smeared a sub-level sub-pixel flip across a whole 8×8 block, disguising a one-level change as a much larger block difference. PNG makes a genuine flip show up as the real pixel change, so the three-frame fixed-point gate below can tell a converged surface from a drifting one.

### Screenshot determinism

The deterministic path makes captures reproducible run-to-run on a given machine; verification against the committed matrix is pixel-tolerant in the CI capture environment. Captures run in the dedicated `screenshots` project, which is always SwiftShader-rendered and pins the colour/text pipeline (see [E2E rendering modes](#e2e-rendering-modes)) — GPU rasterisation is not byte-stable across launches, which is what previously left `closed.png` with two anti-aliasing variants. The single-thread SwiftShader pin and the one-worker gate are applied only on the deterministic path (`CI`, `E2E_SWIFTSHADER_PIN=1`, or `E2E_SCREENSHOTS_COMMIT=1`); a plain local run is unpinned and parallel (see [E2E rendering modes](#e2e-rendering-modes)). A machine can be deterministic run-to-run and still drift sub-perceptually from the committed bytes, so the committed matrix is not ratified by local comparison — re-baseline from the workflow's captures (see [CI-sourced re-baseline](#ci-sourced-re-baseline)).

Determinism rests on deliberate capture measures:

- `ui-states.spec.js` seeds `Math.random` before boot (stable auto-assigned feature colours and route ids) and pins clock-derived values (recording/offline timestamps, the live elapsed timer, the Storage API estimate).
- Map assets come from the committed fixture set pinned to the [demo area](#map-asset-fixtures), so tiles, sprites and glyphs are identical every run.
- `useMap` passes MapLibre `fadeDuration: 0` when `VITE_E2E_FIXTURES === "1"` (a test-only gate; the production bundle is unchanged). The label-collision fade is time-based (`Placement.symbolFadeChange`), the symbol shader culls symbols below 0.1 opacity, and a capture taken after the map stops rendering can freeze a mid-fade frame with missing labels. A zero fade makes every rendered frame show symbols fully opaque; fades are entrance-only, so steady-state rendering and production output are unchanged.
- A fail-fast guard ([`assertE2eFixturesActive`](../tests/e2e/helpers/mapIdle.js), called from `waitForMapIdle`) checks that the running map's resolved `_fadeDuration` is `0` and throws otherwise. `playwright.config.js` sets `reuseExistingServer: !CI`, so a stale dev server started on the test port without `VITE_E2E_FIXTURES=1` would otherwise be silently reused, compiling a bundle with MapLibre's default 300 ms fade and making every capture timing-dependent. The guard turns that into an actionable error instead of a mysterious flaky matrix.
- `playwright.config.js` pins `locale: "en-CA"` for every project and `timezoneId: "America/St_Johns"` for the `screenshots` project, so unit/date formatting is stable across machines and panel timestamps render in the demo area's Newfoundland zone.
- [`waitForLayoutSettled`](../tests/e2e/helpers/layout.js) waits for every CSS animation/transition inside the app root to finish, the MapLibre canvas drawing buffer to match its container (a `ResizeObserver` on both the container and canvas plus one animation frame, with a 30 s ceiling), the app's `data-map-idle` signal, the in-flight glyph fetches to drain, and the paint settle below. Its animation wait polls on an interval rather than `requestAnimationFrame`: under a full multi-worker run Chromium throttles rAF in a backgrounded page, so a `raf` poller can stop re-checking a predicate that is already satisfiable, timing out with the page settled. A timeout dumps the offending animations (selector, property/name, playState, timing) in the thrown error.
- `normaliseCaptureState(page, testInfo)` wraps `waitForLayoutSettled` and applies the two capture-time pins — the scale-control refresh, then the terrain depth pin — immediately before every `capture()`, so each PNG is generated from the same normalised state.
- [`waitForMapQuiet`](../tests/e2e/helpers/mapIdle.js) waits for MapLibre's own composite state to hold still (placement and style/source updates idle, no pending layer/source work), then forces a render (`renderOnce` — a single synchronous `map.redraw()` plus a `render` listener, with a 2 s fallback) and re-confirms the clean predicate, repeats the render/predicate pair, and ends with two presented frames. The former fixed-duration `renderBurst` windows are gone; render-completion signals replace the sleeps. A committed placement does not always schedule a render — `Style._updatePlacement` can report "no change" once the new placement has no transitions — and a screenshot never triggers a MapLibre render, so the settle must actively drive renders.
- `waitForGlyphsLoaded` drains **all** in-flight map-asset requests (tiles, glyph ranges and sprites — not just `/fonts/`) before the paint settle, so a late glyph-triggered re-placement runs against a fully cached asset set. This is what `waitForLayoutSettled` calls.
- `waitForGlyphsQuiesce` is a stricter variant — it holds until no map-asset request is in flight **and** no new request has started (`assetStarts` catches a request that starts and finishes inside a single poll), for two consecutive 50 ms polls — and currently has **no call site**.
- [`waitForMapPainted`](../tests/e2e/helpers/mapIdle.js) is `waitForMapIdle` → `waitForMapQuiet` → `renderOnce` → two presented frames, with no fixed 500/800/300 ms windows.
- `capture()` is an active render-then-compare loop:
  - Each round drives `renderOnce` + two presented frames (`presentFrames`), then a **freshness probe**: a temporary full-viewport overlay is toggled on and off, and the shot is discarded unless the forced repaint visibly changes the captured frame — proving the compositor is live rather than surfacing a stale (older but internally coherent) frame.
  - The shot is accepted only once **three consecutive lossless frames are byte-identical**. Two matching frames are not enough: a sub-level rasterisation flip can land between two comparisons and only diverge on a later frame, so a still-flipping surface must never be accepted.
  - Bounded at `MAX_ROUNDS = 12`; the probe at `MAX_PROBES = 10`. If no three-frame fixed point is reached the capture **throws** rather than writing a drifting frame.
- A reduced capture-time style suppression (`stabilizeCaptureRendering`, applied at the five capture call sites) disables `backdrop-filter` and `box-shadow` via an injected style tag (`*,*::before,*::after{…}`). These GPU-composited layers left a small fraction of pixels drifting under a full multi-worker run even though the underlying page was identical; a full-removal attempt reintroduced the drift, so the suppression stays. It is capture-only — production rendering is untouched — and the earlier border override was removed.
- A terrain depth pin (`pinTerrainDepthFar`, applied to **every** capture via `normaliseCaptureState`) clears the terrain depth framebuffer to the far plane and freezes `painter.maybeDrawDepth`, making the symbol shader's `calculate_visibility()` factor exactly 1. MapLibre multiplies every symbol's alpha by that factor, which samples the terrain depth framebuffer; the framebuffer is redrawn only when the camera matrix changes — not when a raster-DEM tile's _data_ finishes loading — so a symbol on the terrain surface could sample as "in front" (alpha ≈1.0) or, after an unrelated camera change, as "slightly behind" (alpha ≈0.87). That was the intermittent sub-pixel variant on the demo's food POI in `feature-offline` and on several label states (e.g. `phone/landscape`); pinning the factor for every capture makes it deterministic rather than masking a timing race. Best-effort — a missing map/terrain leaves the capture untouched.
- A scale-control refresh (`refreshScaleControl`, applied to every capture) calls the public `ScaleControl.setUnit()`, which is the only way to force `updateScale()` outside a `move` event. `updateScale()` derives the bar's inline width from `map._container.clientWidth/clientHeight` and `map.unproject()`/`map.project()`; a panel-driven container resize fires no `move`, so the width could stay pinned to a container size from before the resize — or a transient width sampled mid-transition — and vary run to run for an identical final state. The refresh runs **before** the terrain pin (the pin leaves the terrain ray-cast used by `unproject()` inconsistent until the next render) and temporarily detaches `map.terrain` for the synchronous recompute (restored before any render), so the value is a pure function of the settled camera and container rather than the route-fit DEM load state. Best-effort — an absent control leaves the bar untouched.
- Each capture writes a diagnostics JSON **after** the write (it never affects the PNG), and only when `E2E_SCREENSHOTS_DIR` is set — committed in-place runs write nothing — to `${E2E_SCREENSHOTS_DIR}/diag/<E2E_SCREENSHOTS_DIR basename>/<device>-<orientation>-<state>.json`. It records the map camera, canvas size, source ids, symbol-layer pairs, label features from `querySourceFeatures`, tile-cache entries, the glyph-atlas state (`glyphRanges`: loaded and pending ranges plus the glyph count per font stack, read from `map.style.glyphManager.entries` — a plain object in MapLibre 5.x, not a `Map`), map-fixture resource timings and the settle flags, so a non-reproducible capture can be diffed to locate the differing input. The `feature-offline` capture — the only one that has shown run-to-run variance — also writes a raw map-canvas PNG (the surrounding chrome is excluded because the committed artefact is already a lossless PNG, so a full-page diagnostic copy would duplicate it exactly) and a three-shot canvas-stability hash series.

**Verification:** the committed matrix is reproduced within a strict pixel tolerance in the CI capture environment — the `Screenshots` workflow is the authority; local captures are diagnostic, not CI evidence.

- _Locally_, a deterministic run (`E2E_SWIFTSHADER_PIN=1` or `E2E_SCREENSHOTS_COMMIT=1`) reproduces itself run-to-run on the same machine, but rendering can drift sub-perceptually from the committed bytes across machine environments — even on a machine that previously reproduced the matrix — so local captures are compared relatively rather than ratified (see [Screenshot diff loop](#screenshot-diff-loop)).
- _On GitHub runners_, the [`Screenshots` workflow](../.github/workflows/screenshots.yml) regenerates the matrix in six macOS shards (`macos-15`) under the deterministic pin, and each shard verifies its captures against the committed PNGs within a strict pixel tolerance ([`scripts/verify-matrix.js`](../scripts/verify-matrix.js)).
- The aggregate `verify` job (`ubuntu-latest`) then checks the full committed matrix in both directions — every committed PNG captured within tolerance, and no extra captures. It is the authoritative matrix check and, with no branch protection configured, an advisory one: on a pull request a moved matrix goes red with a diff bundle and sticky comment, while on a scheduled or dispatched `master` run the move is handed to the `refresh` heal.
- Linux (`ubuntu-latest`) does **not** reproduce the matrix — font substitution changes DOM text metrics (panel copy wraps) and canvas rasterisation differs — which is why the capture shards are macOS-only.
- This is mechanism-backed evidence, not a proof of universal determinism: the normalisations pin the symbol-shader visibility factor, the scale bar's width and the SwiftShader rasterisation order — the inputs known to vary — not every conceivable raster difference.
- They are applied to every capture, so a handful of captures can differ from an older committed baseline generated before the generalisation (the terrain pin changes symbol alpha on draped features and some labels; the scale refresh changes stale bar widths); the pixel tolerance absorbs the remaining sub-level launch-to-launch flake.
- When a change intentionally moves captures, `master` heals itself on its next scheduled (or manually dispatched) run — the `refresh` job, guarded against racing a `ci.yml` run or blessing a stale baseline; use `screenshots:fetch` only for a pull request or a failed/incomplete capture set (see [CI-sourced re-baseline](#ci-sourced-re-baseline)).

The README heroes remain the deliberate exception — **intentionally non-deterministic live captures**. Each is a genuine cold start against `?country=random` over live (un-stubbed) map tiles, so the framed country and imagery differ every run; they are the suite's only live-network output. `readme.spec.js` therefore imports Playwright's base `test` rather than `helpers/test.js`, and stays on the GPU `chromium` project. They are also the one pair deliberately left as JPEG (`quality: 80`) and excluded from the deterministic `screenshots` project (`testIgnore`): a full-suite run regenerates `DARK.jpg` and `LIGHT.jpg` in place on every run, and that in-place refresh is a feature, not a bug.

**Conventions:**

- README heroes are 1280×720; the matrix uses each device's viewport from `VIEWPORTS` in `ui-states.spec.js`
- README heroes are live captures of a random-country cold start (`?country=random`) and differ every run by design; the matrix view is pinned to the demo area (geometry from `fixtures/demo.mjs`, `screenshotZoom` re-exported via `fixtures/map/demoArea.mjs`)
- Dark is the suite default (`colorScheme: 'dark'` in `playwright.config.js`); the light hero opts in explicitly
- Test names describe the UI state being captured
- Add a screenshot when the visual output meaningfully illustrates the behaviour

The matrix specs carry generous file-level timeout budgets, sized for SwiftShader's slow stability checks — the renderer the `screenshots` project always uses: `ui-states.spec.js` uses `test.setTimeout(900000)` — one matrix test loops every core chrome state for a single viewport, so the 15-minute budget leaves ample headroom under SwiftShader — while `readme.spec.js` and `sw.spec.js` use `120000`. `tests/e2e/core.spec.js` and `tests/e2e/features/recordings.spec.js` carry the same `120000` budget for their click interactions and reloads. `tests/e2e/features/routes.spec.js` uses `60000`: a software-rendered (SwiftShader) click-actionability stall can exceed the default 30 s budget even when the target is visible. `tests/e2e/features/offline.spec.js` branches its file budget on the renderer — `test.setTimeout(isSwiftShaderRun() ? 120000 : 30000)`, since a software-rendered pointer move can starve the 30 s default — and its download test raises its own budget to `300000` for its real-network download.

Both screenshot specs — `ui-states.spec.js` and `readme.spec.js` — use the shared 180 s `waitForMapIdle` (see [Waiting for the map](#waiting-for-the-map)) and configure file-scope `retries: 1`: a stalled live raster or TileJSON request under full-suite load can delay map-idle, so this guards local regenerations across every test in each file, not just the six matrix viewports. CI is unaffected — it excludes the `@screenshots` specs and applies its own global `retries: 2`.
