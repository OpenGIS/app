# Features

A feature is a self-contained bundle of logic, a panel, and (optionally) a map-corner control chip. Features are installed from `src/main.js` before the app mounts.

---

## Feature structure

A feature is a plain object with an `install(ctx)` method:

```
src/features/{name}/
  index.js            ← feature object + business logic
  {Name}Button.vue    ← corner control chip (optional)
  {Name}Panel.vue     ← side panel tab (optional)
```

---

## Feature context

`install(ctx)` receives a context object built in `src/main.js`:

```js
{
  app,           // Vue app instance
  instanceId,    // string — for storage scoping
  map,           // shallowRef<Map | null> — reactive map handle
  emitter,       // EventEmitter singleton
  useStorage,    // (namespace, definition) → { state, flush, reset } — pre-scoped persisted state
  useSettings,   // () → OS-derived units; no instanceId, nothing stored
  useLocale,     // () → { locale, mapLanguageTag, formatLocale, t } — translations resolved per instance; nothing stored
  getMap,        // () → MapLibre map instance or null
  onMapReady,    // (cb) → cb({ map, addSource, addLayer }) with auto-cleanup
  onCleanup,     // (fn) → registers a feature-owned cleanup for app destroy
  on,            // EventEmitter wrappers
  once,
  off,
  emit,
  provide,       // (key, value) → app.provide
  addButton,     // (config) → adds a corner control chip (+ panel tab)
  addPanel,      // (config) → adds a panel tab
}
```

### `addButton(config)`

Registers a control chip in the map's bottom-right corner (and, when a `panel` is supplied, a side-panel tab):

```js
addButton({
  id: "my-feature", // panel tab id — match it in setActivePanel()
  icon: "route", // used when no component is supplied
  position: "bottom-right", // the only rendered position
  component: MyButton, // Vue component rendering an IconButton chip
  panel: {
    title: () => t("menu.myFeature"), // a string, or a thunk for translations
    component: MyPanel,
  },
});
```

- Buttons are rendered by the corner-controls overlay ([`src/components/ui/controls.vue:86`](../src/components/ui/controls.vue#L86)); a button without `position: 'bottom-right'` is not rendered.
- With a `panel`, the button also becomes a panel tab. A plain (icon/label) button opens that panel on click; a `component` button handles its own click and can call `setActivePanel()` / `openPanel()` itself.
- `id` should match the panel tab id used with `setActivePanel()`.

### `addPanel(config)`

Registers a panel-only tab in the side panel navigation (`.panel-nav`) — no corner button. The config is pushed into the `navigatorPanels` registry ([`src/main.js:153`](../src/main.js#L153)) and rendered as a tab via `panelTabs` ([`src/components/ui/panels.vue:42`](../src/components/ui/panels.vue#L42)):

```js
addPanel({
  id: "my-feature",
  icon: "cloud-arrow-up",
  title: () => t("menu.myFeature"), // a string, or a thunk for translations
  component: MyPanel,
});
```

A `title` may be a plain string or a thunk returning one. Features use a thunk that calls `t()` so the tab label re-evaluates when the locale changes — the registry resolves the label at render time ([`panels.vue:25`](../src/components/ui/panels.vue#L25)).

With Routes currently the only installed panel, `panels.vue` adds `panel-nav--single` and the theme renders the lone tab as a compact, label-only header with its icon hidden. Keep supplying `icon` — the markup is retained, and the icon returns with the normal icon+label layout as soon as a second panel is registered (see [UI — Panel](./5.ui.md#panel)).

### `onMapReady(callback)`

Registers a callback that fires once the MapLibre map is ready. The callback receives `{ map, addSource, addLayer }`. Sources and layers added via these helpers are automatically removed on app destroy:

```js
onMapReady(({ map, addSource, addLayer }) => {
  addSource('my-source', { type: 'geojson', data: featureCollection });
  addLayer({ id: 'my-layer', type: 'circle', source: 'my-source', paint: { ... } });
});
```

The callback is guarded at call time: a throw is reported with `{ source: "map-ready" }` and cannot break `map:ready` delivery to other features. `installFeature` also tracks the registration's disposer, so a feature that fails during install does not leave a pending map-ready callback behind. The callback runs once.

### `onCleanup(fn)`

Registers a cleanup for resources the feature owns — its own watchers, timers and event listeners:

```js
const stopWatch = watch(source, onChange);
onCleanup(stopWatch);
onCleanup(unbindMapListener);
```

- Cleanups run newest first on app destroy, before the tracked source and layer removal.
- A cleanup failure is reported with `{ source: "feature-cleanup" }`; the remaining cleanups still run.
- `installFeature` tracks the registration, so a failed install runs the cleanup and then removes it from the app-level registry.
- The registration returns an idempotent remover that removes the cleanup without running it.
- Only register what the feature owns. Shared composables (`useGeoJSON`, `useLocate`, `useActions`) outlive any single feature and must not be disposed from one; they provide their own terminal teardown for app-level use.

### Returning a teardown

A feature may return a teardown function from `install(ctx)` for the resources it owns, as an alternative to registering them individually with `onCleanup`:

```js
import { watch } from "vue";

export const MyFeature = {
  install() {
    const stopWatch = watch(source, onChange);

    return () => {
      stopWatch();
      // any other feature-owned teardown
    };
  },
};
```

`installFeature` registers a returned function through the same cleanup registry as `onCleanup`, so it runs on app destroy. It is not run during install — a successful install only registers it. A context without `onCleanup` (as in minimal unit-test contexts) skips that registration without throwing. Register each resource once, either through `onCleanup` or in the returned teardown, so destroy does not tear it down twice.

## Persistence and restore

Features persist state through `ctx.useStorage(namespace, definition)`, a thin wrapper around [`usePersistedState`](../src/resilience/persistedState.js):

```js
const stored = useStorage("my-feature", {
  version: 1,
  defaults: { items: [] },
  hydrate: hydrateMyFeature,
}).state;
```

- Give the store a namespace, a current `version` and explicit `defaults`.
- Supply a `hydrate` when stored data can be legacy, malformed or partly untrustworthy. Repair field-level problems; throw to reject an uninterpretable top-level value. See [State and resilience — Hydration and validation](./16.state-and-resilience.md#hydration-and-validation).
- Bump `version` when the stored shape changes incompatibly, and handle earlier versions in the hydrator.
- Run side-effecting restores after mount; a pure render-only restore (such as route visibility) may run during install. A restore must never open the app's own permission explainer or claim the camera; a browser-native prompt can still appear when the platform cannot report a stored grant (see the Apple WebKit exception in [State and resilience](./16.state-and-resilience.md#locate-restore)).
- Make restore failure silent and non-throwing. If another feature must wait for your restore, expose a promise (as `useLocate` does with `restoreComplete`).
- Persist intent, not derived values (distance, speed, live pose while a controller owns the camera).
- Only opt into `crossTab` when applying an external write is safe and cannot echo. The `view` store and the shared content store (`routes`) opt in; durable tab-owned stores (`locate`, `navigation`) never do — see [Durable tab-owned sessions](#durable-tab-owned-sessions).
- Shared content is last-writer-wins: an external write replaces the shared array wholesale, with no merge or conflict resolution. Give the definition an `onSync` that reconciles the feature's in-memory and map state with the replacement: remove or re-render the visible rows and GeoJSON features. Keep reconciliation defensive — unknown ids, malformed documents and a not-yet-ready map must not throw. See [State and resilience — Cross-tab sync](./16.state-and-resilience.md#cross-tab-sync).

Full contract, store inventory and worked examples: [State and resilience](./16.state-and-resilience.md).

### Durable tab-owned sessions

Use a durable tab-owned store when one session belongs to one tab but must survive a reload or app quit — for example locate or route navigation:

- Store the session in `localStorage` (`storage: "local"`) with an `ownerId` in the defaults. Do not use `storage: "session"` for restoreable sessions: a session store is lost when the tab closes and reintroduces the loss this model exists to prevent.
- Take the owner id from [`getSessionTabId()`](../src/resilience/sessionChannel.js). Where storage is available it lives in `sessionStorage`, so it survives a same-tab reload and changes after an app quit; otherwise it falls back to a document-lifetime id. Include it in the hydrator so a non-empty id survives only alongside the restored session data — a restorable locate mode and fix, or a route.
- Before restoring a session whose `ownerId` differs from the current tab, call [`isSessionOwnerAlive(ownerId, { instanceId })`](../src/resilience/sessionChannel.js). If it resolves `true`, leave the stored session untouched. If it resolves `false`, claim it by writing the current tab id before restoring. Unsupported `BroadcastChannel`, construction failure, a malformed reply and a timeout all resolve `false`, so a dead owner is never treated as live.
- Answer probes with [`listenForSessionProbes(instanceId, getOwnerId)`](../src/resilience/sessionChannel.js) while this tab actually owns the session; `getOwnerId()` returns the owner id only in the live state and `null` otherwise. Stop the listener through `featureCtx.onCleanup` or the feature's returned teardown.
- A same-tab reload keeps the owner id, so it restores directly. A new tab or a tab reopened after an app quit gets a new id and probes the stored owner.
- Migrate legacy session values before creating the store (`migrateSessionToLocal(namespace, instanceId)`). Do not hydrate during migration — the store's normal boot path does that afterwards.
- Never opt a durable tab-owned store into `crossTab`, and never let one tab clear another live tab's session just because it did not restore it.

## Map modes

A feature that takes the camera for longer than a single move — following or navigating — registers a mode with [`useActions`](../src/composables/useActions.js): an `active` ref plus a synchronous, idempotent `stop({ handoff })`. A feature that fits the camera for a one-shot action calls `claimMap()` before the fit, or expresses the action as a descriptor in [`src/actions.js`](../src/actions.js) and runs it through `perform`.

A hand-off stop (`{ handoff: true }`) releases the camera and any view-persistence suppression without persisting, so the incoming action's camera move is the one that persists; a full stop tears the mode down and may persist once. See [UI — UI actions and map modes](./5.ui.md#ui-actions-and-map-modes).

## Registering a feature

In `src/main.js`, import and install the feature before `app.mount()` through `installFeature`:

```js
import { RoutesFeature } from "./features/routes/index.js";
import { installFeature } from "./resilience/boot.js";

installFeature("routes", RoutesFeature, featureCtx);
```

`installFeature` isolates the install: registrations made through `addButton`, `addPanel`, `on`, `once`, `onMapReady` and `onCleanup` are tracked, and a throw rolls them back in reverse order before the failure is reported. The other features still install and the app still mounts. `provide` cannot be rolled back. A function returned by `install` is registered automatically through the same cleanup registry; see [Returning a teardown](#returning-a-teardown). See also [State and resilience — Feature install isolation](./16.state-and-resilience.md#feature-install-isolation).

## Routes — worked example

The Routes feature (`src/features/routes/`) is the only core feature installed
in SPA front-end only mode. It imports GPX and GeoJSON files into versioned
track documents, renders route lines and waypoints on the map via `useGeoJSON`,
keeps the documents in `localStorage`, and restores route visibility and
follow-mode navigation. All controls live in its side panel. Full UI and
navigation detail is in [Routes](./11.routes.md).

### Feature object (`index.js`)

```js
export const RoutesFeature = {
  install({
    useStorage,
    useSettings,
    getMap,
    onMapReady,
    instanceId,
    provide,
    addPanel,
    onCleanup,
    useLocale,
  }) {
    const routes = useStorage("routes", {
      version: 1,
      defaults: [],
      hydrate: hydrateRoutes,
      crossTab: true,
      onSync: () => reconcileRoutes(),
    }).state;
    assignTrackColors(routes);

    migrateSessionToLocal("navigation", instanceId);
    const navigationStore = useStorage("navigation", {
      version: 2,
      storage: "local",
      defaults: {
        routeId: null,
        visible: [],
        followOwned: false,
        ownerId: null,
      },
      hydrate: hydrateNavigation,
    });

    const { isMetric } = useSettings();
    const { t } = useLocale();
    const geoJSON = useGeoJSON(instanceId);

    // ... rendering, visibility, navigation and restore ...

    addPanel({
      id: "routes",
      icon: "graph-down",
      title: () => t("menu.routes"),
      component: RoutesPanel,
    });

    provide("routes", {
      routes,
      navigating,
      error,
      isMetric,
      importTracks,
      deleteRoute,
      showOnMap,
      hideOnMap,
      toggleVisibility,
      isVisible,
      startNavigation,
      stopNavigation,
      shareTrack,
      formatDistance,
    });
  },
};
```

### GeoJSON integration

`renderRoute(route)` projects the stored document into map features with
`lineGeometry` ([`index.js:148`](../src/features/routes/index.js#L148)):

```js
geoJSON.setFeature({
  type: "Feature",
  id: `routes-route-${route.id}`,
  geometry: lineGeometry(route), // LineString or MultiLineString
  properties: {
    "ogis.color": route.color,
    "ogis.width": 4,
    "ogis.opacity": 0.85,
    "ogis.direction": true,
  },
});
```

- One usable segment becomes a `LineString`; several become a
  `MultiLineString`. Segments with fewer than two valid points are omitted.
- Waypoints render as separate `Point` features with a 5 px radius in the same
  colour, under `routes-waypoint-{id}-{index}`.
- `ogis.direction: true` adds the static direction chevrons described in
  [GeoJSON](./6.geojson.md#direction-chevrons); direction follows point order,
  not timestamps or bearing data.
- The stored colour is reused, so a route keeps its swatch and map colour across
  sessions.

### Storage

Route documents are shared content in `localStorage` under
`ogis_routes_{instanceId}` (version 1, an array), with live cross-tab sync and an
`onSync` that reconciles rows and map features. Visibility and navigation
ownership use a separate durable `localStorage` store,
`ogis_navigation_{instanceId}` (version 2), created after the one-time session
migration and never synced across tabs. Its persisted shape is:

```js
{
  routeId: "m1abc2d-x9k2p1q7",   // or null
  visible: ["m1abc2d-x9k2p1q7"],
  followOwned: true,
  ownerId: "1f0c9c4e-6b2a-4f7e-9f1e-2a3b4c5d6e7f",
}
```

`hydrateRoutes` migrates legacy route shapes with `migrateRoute`, sanitises every
document and point, drops invalid documents and keeps the first document when
two share an id. A stored route is a v2 track document
([`index.js:47`](../src/features/routes/index.js#L47)):

```js
{
  v: 2,
  id: "m1abc2d-x9k2p1q7",
  kind: "route",
  name: "Morning Loop",
  gpxType: "trk",
  createdAt: null,
  source: { format: "gpx", filename: "morning.gpx", groupId: "…", index: 0 },
  segments: [{ points: [{ lat: 48.949011, lng: -55.652574, ele: 42 }] }],
  waypoints: [],
  color: "#3498db",
}
```

Distance is always derived from the geometry with `documentDistance`; numbers
are never stored. The `navigation` store persists `routeId`, the `visible` id
list, `followOwned` and the owning tab's `ownerId`; its hydrator trims ids,
dedupes the visible list, keeps a navigated route visible, and keeps
`followOwned`/`ownerId` only alongside a route. A second live tab probes the
owner and leaves a live session untouched. See
[Routes — Storage](./11.routes.md#storage) and
[State and resilience — Route visibility and navigation restore](./16.state-and-resilience.md#route-visibility-and-navigation-restore).

### Sharing and export

`shareTrack(route, "gpx" | "geojson")`
([`index.js:516`](../src/features/routes/index.js#L516)) projects the v2 document
with `toGPX` or `toGeoJSON`, names it with `trackFilename`, and calls `shareFile`
— the Web Share API when available, otherwise a download. GPX uses the custom
writer described in [Tracks — Export](./15.tracks.md#export); GeoJSON includes
elevation as the third ordinate and per-point times in
`properties.coordinateProperties.times`.

### Components

The feature is panel-only — it registers no corner chip.

- **`RoutesPanel.vue`** — file input, import error line, one row per document
  with colour swatch, distance, waypoint count, Show/Hide, Navigate/Stop, a Share
  menu (GPX/GeoJSON) and Delete behind a native `window.confirm`; injects
  `routes` from `provide`.
- **Registered mode** — `install` registers a `navigate` mode with `useActions`
  so a sustained navigation owns the camera ([`index.js:528`](../src/features/routes/index.js#L528)).
- **Top-centre card** — Routes publishes `menuNavigation` through
  `useUI().setMenuNavigation` ([`index.js:492`](../src/features/routes/index.js#L492));
  the core chrome renders it in `NavigationControl.vue`, not on the menu chip
  (see [Routes — Navigation](./11.routes.md#navigation)).

### State shape

The in-memory runtime state is:

```js
{
  routes: [],          // v2 route and waypoint documents (shared, synced)
  navigating: null,    // id of the route being navigated
  visible: new Set(),  // route ids shown on the map, mirrored into navigation.visible
  error: null,         // last import failure (sentinel code)
}
```

Visibility is restored from the navigation store during install without fitting
or claiming the camera. Navigation restores non-blocking, awaits
`locate.restoreComplete`, and resumes only when locate re-enters `following`
with a usable route line. A restored navigation never fits or claims the camera.
See [State and resilience — Route visibility and navigation restore](./16.state-and-resilience.md#route-visibility-and-navigation-restore).

## Adding a new feature

1. Create `src/features/{name}/index.js` with an `install(ctx)` method
2. Create `src/features/{name}/{Name}Button.vue` and `{Name}Panel.vue` as needed
3. Register in `src/main.js` through `installFeature("name", MyFeature, featureCtx)`
4. Persist state with `ctx.useStorage(namespace, { version, defaults, hydrate })`; restore silently after mount, without the app's own explainer or a camera claim (see [Persistence and restore](#persistence-and-restore))
5. Localise: render every user-visible string through `t()` (destructure `useLocale` from the context) and keep logic layers language-free, emitting stable sentinel codes for the panel to map (see [Locale](./7.locale.md#message-codes-and-sentinel-errors))
6. Add unit tests in `tests/unit/` for pure logic
7. Add an E2E spec in `tests/e2e/features/{name}.spec.js` for integration
