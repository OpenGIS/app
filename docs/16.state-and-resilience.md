# State and resilience

> How ogis.app persists user state, contains failures, restores sessions and recovers from a broken map.

## Overview

Resilience is layered rather than a single catch-all. Each layer limits the blast radius of the one below it:

| Layer            | Implementation                                                                                    | Prevents                                                  |
| ---------------- | ------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| Persisted state  | [`src/resilience/persistedState.js`](../src/resilience/persistedState.js)                         | Corrupt or stale values breaking a feature on reload      |
| Hydration        | [`src/resilience/hydrators/`](../src/resilience/hydrators/)                                       | Repairable data becoming unusable runtime objects         |
| Boot containment | [`src/resilience/errors.js`](../src/resilience/errors.js), [`boot.js`](../src/resilience/boot.js) | One feature or listener taking down the whole app         |
| Domain restore   | `useLocate`, Routes and their hydrators                                                           | A crash losing an active session or navigation            |
| Map recovery     | [`src/resilience/mapRecovery.js`](../src/resilience/mapRecovery.js), `useMap`                     | A failed style or lost WebGL context leaving a blank page |
| Static fallback  | [`index.html`](../index.html)                                                                     | A failed module load leaving an empty document            |

The guiding rules are:

- The healthy path stays quiet: no global toast, no production console noise.
- Persist user intent, not derived or transient data.
- A restore never throws, never opens the app's own permission explainer and never blocks app mount. On Apple WebKit the browser may still show its native geolocation prompt if the stored grant has lapsed.
- Corruption is isolated to one store where possible.
- Contained failures go through `reportError`, which logs through the development-only debug channel.

## Persisted state

### `usePersistedState(namespace, definition, instanceId?)`

Creates a reactive store bound to one storage key. The instance id is resolved from `inject("ogisAppId", "app")` when omitted.

```js
import { usePersistedState } from "@/resilience/persistedState.js";

const { state, flush, reset } = usePersistedState("my-feature", {
  version: 1,
  defaults: { items: [] },
  hydrate: hydrateMyFeature,
  debounce: 250,
  crossTab: false,
});
```

| Definition field | Default   | Purpose                                                                                                    |
| ---------------- | --------- | ---------------------------------------------------------------------------------------------------------- |
| `version`        | `1`       | Current schema version.                                                                                    |
| `defaults`       | `{}`      | Deep-cloned initial state. Its container type must match the hydrated data.                                |
| `storage`        | `"local"` | `"local"` or `"session"`. Session storage is never cross-tab.                                              |
| `crossTab`       | `false`   | Apply writes from other tabs through the `storage` event.                                                  |
| `debounce`       | `250`     | Coalescing window in milliseconds. `0` writes on the next tick.                                            |
| `hydrate`        | —         | Synchronous `(data, { version, namespace, instanceId }) => cleanedData`. Throw to reject the stored value. |
| `onSync`         | —         | Runs after an external write is applied: `(state, { namespace, instanceId, source: "external" })`.         |

The returned API is `{ state, flush, reset }`:

- `state` — reactive data. External syncs replace it in place, so the top-level reference stays valid (arrays splice, objects replace their properties). A nested reference held by a feature, such as `state.saved`, is re-pointed by that feature's `onSync`.
- `flush()` — clears the pending debounce timer and writes now.
- `reset()` — removes the store key, restores defaults and suppresses the resulting watch echo.

Features normally receive the same function as `featureCtx.useStorage(namespace, definition)` and read `.state`; see [Features](./10.features.md#persistence-and-restore).

Keys follow the instance-scoped format `ogis_{namespace}_{instanceId}`; see [Instances](./3.instances.md). One store exists per `(instanceId, namespace)`: repeated calls return the same object. `resetInstanceState(instanceId)` removes the current instance's keys from both `localStorage` and `sessionStorage`, including quarantine copies. It matches only the app's known store namespaces with an exact `ogis_{namespace}_{instanceId}` or `ogis_quarantine_{namespace}_{instanceId}` comparison, so another instance whose id ends with this one — for example `trip_app` when resetting `app` — is left untouched. The known namespaces are listed in [Instances](./3.instances.md).

### Envelope and versions

Every write is a versioned envelope:

```json
{
  "__ogisState": 1,
  "version": 1,
  "data": { "items": [] }
}
```

- A bare value is legacy data at version `0`.
- A stored version newer than the definition is rejected and quarantined, so a downgrade preserves the newer raw value instead of silently overwriting it.
- Older versions are passed to `hydrate` with `context.version`.
- Bump `version` when the stored shape changes incompatibly and let the hydrator migrate older input.
- Hydration does not rewrite storage. A legacy bare value stays untouched until the first mutation, then the normal write path emits an envelope.
- Writes are skipped when the serialised envelope is unchanged.

### Hydration, defaults and quarantine

A store boots from defaults, then applies the stored value when it decodes and hydrates successfully:

1. Read and parse the raw string.
2. Unwrap the envelope, or treat a bare value as version `0`.
3. Run `hydrate` when supplied; otherwise require the value's container type to match `defaults`.
4. Require the hydrator's result to have the same container type as `defaults`.

A failed step falls back to defaults and copies the raw value to `ogis_quarantine_{namespace}_{instanceId}`. Quarantine is diagnostic only: it is one slot per store and instance, so a later invalid value overwrites it. The failure is logged through the `state` debug channel, not reported as a user-facing error.

An invalid `storage` event from another tab is ignored rather than quarantined.

Tracking stores are more forgiving than their top-level container rule suggests: individual invalid documents and points are dropped while valid siblings survive. See [Hydration and validation](#hydration-and-validation).

### Writes, debounce and quota

A deep watcher coalesces routine changes through `debounce`. The view store uses a 300 ms window; other stores use the 250 ms default. Critical transitions flush immediately instead of waiting for the window:

- **Locate** — mode changes, the first accepted fix of a session and a permission grant. Later fixes stay debounced.
- **Navigation** — navigation start/stop and route visibility changes.
- **Recordings** — start, pause, discard, save and delete. GPS points added mid-recording stay debounced.

Imported route documents and other non-critical saved-data writes remain debounced. Pending writes also flush on `pagehide` and when the document becomes hidden, so a normal reload, tab close or app switch writes the last change. Neither event is guaranteed on a hard kill or force-quit, so a force-quit can still lose the most recent routine debounced write; the states that define a restorable session are written immediately rather than left in that window.

Storage failures are silent by design:

- A missing or throwing `localStorage`/`sessionStorage` is treated as unavailable.
- Quota, privacy-mode and serialisation failures leave state in memory, log through the debug channel and retry on a later mutation.
- No modal, toast or console error is raised.

### Cross-tab sync

`crossTab: true` attaches one `storage` listener per window. When another tab writes the matching key, the receiving store:

1. decodes and hydrates the new value;
2. clears any pending local write and replaces its state without echoing back;
3. runs `onSync`, if defined;
4. emits `state:sync` with `{ namespace, instanceId, source: "external", key }`.

Invalid external values are ignored. The **view** store opts in: its `onSync` applies the external camera through `applyExternalView`, which skips while a controller owns the camera or persistence is suppressed; the programmatic `jumpTo` suppresses its own `moveend` so the receiving tab does not write the value back.

The shared content stores — `routes`, saved `recordings` and `offline-regions` — also opt in. Their `onSync` reconciles each feature's in-memory and map state with the replacement document: visible rows and GeoJSON features are removed or re-rendered, navigation stops when its route disappears, and the shown offline overlay is redrawn or cleared. Shared content is last-writer-wins: an external write replaces the shared array contents (routes, offline regions) or the object's properties (saved recordings) wholesale, not merged, and there is no conflict resolution beyond the replacement. When an object-shaped store receives an external write its properties are replaced, so a feature that holds a nested array reference (such as saved recordings) must re-point it during `onSync`.

`locate`, `navigation` and `recording-active` are durable but tab-owned. They live in `localStorage` so a reload or app quit can restore them, each value carries an `ownerId`, and they never opt in to cross-tab sync. A second live tab probes the owner over a per-instance `BroadcastChannel` before restoring; while the owner answers, the second tab leaves the stored session untouched. The `sync` store remains shared content in `localStorage` without live cross-tab sync because it is dormant in front-end-only mode.

### Durable tab-owned sessions

The `locate`, `navigation` and `recording-active` stores use `localStorage`, so a session survives a reload and a full app quit. They stay tab-owned through an owner id rather than storage lifetime:

- Each store records `ownerId` from `getSessionTabId()`, which keeps an id in `sessionStorage` where storage is available — it survives a reload but is new after an app quit — and otherwise falls back to a document-lifetime id. A same-tab reload therefore sees its own owner id and restores without a probe; a new tab, or a tab reopened after an app quit, sees a different id and probes the stored owner.
- Before restoring a session whose `ownerId` belongs to another tab, the tab calls `isSessionOwnerAlive(ownerId)`. It posts a probe on the per-instance `ogis-session-{instanceId}` `BroadcastChannel` and resolves `true` only when the matching owner replies before the timeout (250 ms by default). Unsupported `BroadcastChannel`, construction failure, a malformed reply, a timeout or a missing owner id all resolve `false`, so a dead owner is never mistaken for a live one.
- The owner tab answers through `listenForSessionProbes(instanceId, getOwnerId)` only while it actually owns the session — locate in `active` or `following`, an active navigation, or a recording that is recording or paused. If the probe times out, the session is treated as abandoned and the restoring tab claims the owner id.
- A live owner's session is left untouched: the second tab neither restores it nor clears it. Channels are per instance, so iframes with different `?id=` values do not answer each other's probes.

`storage: "session"` remains available to the primitive for tab-scoped values and tests: it reads and writes `sessionStorage` under the same key format, with cross-tab sync forced off. Production durable sessions no longer select it. Quarantine copies always use localStorage.

### Migration from session storage

Earlier versions kept `locate`, `navigation` and the active recording in `sessionStorage`. On boot, before the store is created, each tab performs a one-time migration:

- `migrateSessionToLocal(namespace, instanceId)` copies a raw session value into `localStorage` and removes the session key only after a successful local write. The session value wins when both areas hold one.
- `migrateRecordingsSession(instanceId)` moves a legacy session `ogis_recording-active_{instanceId}` value into localStorage, then moves a non-null `active` document from `ogis_recordings_{instanceId}` into the local active store when that store is empty (an existing local active value wins). The saved store is rewritten as saved-only only after any active write succeeds. A value with no `active` property, or malformed input, is left untouched.
- `migrateLocalToSession` is retained for tests and older callers but is no longer used by production.
- `useLocate` and Routes call the migration immediately before creating their store; Recordings calls `migrateRecordingsSession` before creating either store.
- Migration never hydrates the value; the store's normal boot path does that afterwards. It is best-effort, never throws and logs failures through the `state` debug channel.

- `view` stores the last persisted camera. `center` and `zoom` may be `null` before the first meaningful fit; `pitch` and `bearing` default to 0.

- `offline-regions` holds downloaded-region metadata only; tiles live in the service-worker Cache API. See [Offline](./12.offline.md).
- `navigation` holds route visibility and navigation ownership. See [Routes](./11.routes.md#visibility).
- `sync` is the offline sync queue for the backend-dependent features. It is dormant while the app runs in SPA front-end only mode.
- Track documents are validated and sanitised on hydrate. See [Hydration and validation](#hydration-and-validation) and [Tracks — Migration and storage](./15.tracks.md#migration-and-storage).

Invalid data is copied to `ogis_quarantine_{namespace}_{instanceId}` while the store falls back to defaults.

## Hydration and validation

Hydrators repair what can be repaired and reject what cannot. A rejected top-level value quarantines the whole store; a rejected entry is dropped from a valid container.

| Store              | Repaired                                                                                                                                                                              | Rejected or dropped                                                                                                                                                                                                               |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `view`             | Missing `pitch`/`bearing` become 0; a centre with non-finite or out-of-range coordinates becomes `null`; a non-finite zoom becomes `null`; legacy bare `{ mapView }` is accepted.     | A non-object top level, or a present `mapView` that is not an object, rejects the store.                                                                                                                                          |
| `recordings`       | Legacy saved documents migrate; points and waypoints sanitise; extra waypoint metadata is preserved. Legacy `{ saved, active }` values are accepted with `active` ignored.            | A non-object top level or non-array `saved` rejects the store. Invalid saved documents are dropped; duplicate ids keep the first document.                                                                                        |
| `recording-active` | The active document migrates and sanitises; points and waypoints are repaired; a non-empty `ownerId` survives only with an active document.                                           | A non-object top level rejects the store. A null/missing `active` becomes `null`; an active document needs at least two usable points.                                                                                            |
| `routes`           | Legacy route shapes migrate; points and waypoints sanitise; documents are forced to `v: 2` and `kind: "route"`.                                                                       | A non-array top level rejects the store. Invalid documents are dropped. When two documents share an id, the first wins.                                                                                                           |
| `offline-regions`  | Valid entries keep their fields and extra metadata; coordinates, zooms, counts and timestamps are validated for safe panel formatting.                                                | A non-array top level rejects the store. Entries with a missing id/name, inverted or out-of-range bounds, `minZoom > maxZoom`, negative counts/bytes or a non-finite `createdAt` are dropped; duplicate ids keep the first entry. |
| `locate`           | The permission flag accepts `true`, `"true"` or `1`; a finite heading is kept and a non-finite heading becomes `null`; a non-empty `ownerId` survives only with a restorable session. | A non-object top level rejects the store. Only `active` and `following` are restorable modes; an invalid or missing fix drops both mode and fix.                                                                                  |
| `navigation`       | Strings are trimmed; `visible` is deduped in first-seen order; a navigated route is always added to `visible`; `followOwned` and a non-empty `ownerId` survive only with a route.     | A non-object top level rejects the store. Empty and non-string ids are dropped.                                                                                                                                                   |
| `sync`             | Non-array `queue`/`failed` values become arrays; items with a usable id are kept.                                                                                                     | A non-object top level rejects the store. Items without a string or finite numeric id are dropped.                                                                                                                                |

### Track document sanitisation

`hydrateRecordings` and `hydrateRoutes` run the canonical migration helpers and then [`sanitiseTrackDocument`](../src/utils/track/model.js). That function:

- normalises every point with `normalisePoint`, dropping non-finite or out-of-range coordinates;
- drops empty segments and rejects a document with no usable segment points;
- normalises waypoints with `normaliseWaypoint`, which scrubs coordinates and optional `ele`/`t` while preserving descriptive extras (`name`, `desc`, `cmt`, `sym`, `type`, `links`, …);
- forces `v: 2`, the requested `kind`, a trimmed or generated id, and safe scalar fields.

A v2 document is therefore revalidated on every hydrate, not trusted because its `v` field says 2.

### Corrupt-state boot

When a store is unusable:

- the app mounts normally with that store's defaults;
- other stores hydrate independently;
- the raw value remains available under the quarantine key;
- the feature renders its empty state (for example, an empty recordings list);
- no modal, console error or boot fallback appears.

The E2E corrupt-state case seeds an invalid recordings value and a malformed offline region, then asserts defaults, quarantine and a clean console; see [Testing — Resilience coverage](./9.testing.md#resilience-coverage).

## Crash containment

### Error reporting

[`reportError(error, context)`](../src/resilience/errors.js) normalises any thrown value into an `Error`, logs it through the development-only `resilience` debug channel and returns it. It never throws. In production the debug logger is a no-op, so containment does not spam the console.

[`installGlobalErrorHandlers(target)`](../src/resilience/errors.js) installs capture-phase `error` and `unhandledrejection` listeners once per target. It ignores resource-load failures, which have no script error or message, and never calls `preventDefault()`, so the browser's own diagnostics remain visible.

[`installVueErrorHandler(app)`](../src/resilience/errors.js) routes component errors through the same reporter. When the contained error comes from the root instance — or no instance is available — it also calls `window.__ogisBoot.fail()` immediately, so a root setup or initial-render failure shows the static fallback without waiting for the watchdog. A child component error is contained without triggering the fallback, and `fail()` is a no-op after a successful boot.

There is no error-reporting backend. Containment is local and diagnostic only.

### Listener isolation

[`EventEmitter.emit`](../src/classes/EventEmitter.js) catches each listener independently and reports failures with `{ source: "emitter", event, index }`. One throwing listener no longer prevents later listeners from running or aborts the emitting feature.

### Feature install isolation

[`installFeature(name, feature, baseContext, { onError })`](../src/resilience/boot.js) installs one feature inside a boundary:

- `addButton`, `addPanel`, `on`, `once`, `onMapReady` and `onCleanup` return disposers, and the wrapper records each one.
- If `install` throws, the recorded disposers run in reverse order before the error is reported.
- An `onCleanup` disposer runs the registered cleanup and then removes it from the app-level registry, so a rollback cannot leave a booked cleanup behind (and removal still happens if the cleanup throws).
- A broken feature therefore cannot leave a partial panel, button, listener or feature-owned watcher/timer behind.
- On a successful install, `onCleanup` callbacks stay registered with `main.js`; on app destroy they run newest first, before the tracked source and layer removal.
- A teardown function returned by a successful `install` is registered through the wrapped `onCleanup`, so it joins the same registry as an explicit cleanup and runs on app destroy — not immediately during install. A base context without `onCleanup` (minimal unit-test contexts) skips that registration and the install still succeeds.
- Cleanup failures are reported with `{ source: "feature-cleanup" }`; one failure does not stop the rest.
- `provide` has no Vue counterpart to undo, so a provide made before the throw remains registered. The accepted trade-off is that a failed feature's provide is unused.
- The function returns `false`; the next feature still installs and the app still mounts.

`onMapReady` callbacks are also guarded at call time: a throwing callback is reported with `{ source: "map-ready" }` and does not break the `map:ready` emitter or other features.

### Composable self-cleaning

Shared composables own app-wide state, so a feature must never dispose them. They clean up after themselves instead:

- `useGeoJSON` creates its source and layers inside a guard. A failed setup removes anything already added, reports `{ source: "geojson-setup", instanceId }` and returns `false` rather than throwing out of the map-ready listener, so a partial dead overlay manager is never left behind. `cleanup()` sets the map reference to `null` first and tolerates partial setup and throwing MapLibre accessors/removers, reporting `{ source: "geojson-cleanup" }`. The manager is only published to the instance cache after creation succeeds.
- `useGeoJSON` exposes a terminal `dispose()` that removes its `map:ready` and `destroy` listeners, cleans up the map, clears its feature sets and drops the cached manager only when it is still the cached one. Routes, recordings and offline share the manager, so no single feature calls it.
- `useActions` and `useLocate` also expose a terminal `dispose()` for their shared registry/state, with creation wrapped so a throw removes any partial cache entry before rethrowing. `useLocate.dispose()` uses the lower-level teardown helpers, so it never writes a cleared mode to persisted storage.
- A feature uses `featureCtx.onCleanup` for resources it owns (its own watchers, listeners and timers), not for shared composables.

### Boot sequence

1. `index.html` installs its own early error/rejection listeners and boot watchdog before any module loads.
2. [`src/main.js`](../src/main.js) installs the global error handlers first.
3. The Vue app is created, `installVueErrorHandler` is attached and the app context is provided.
4. Each core feature is installed through `installFeature`; failures are contained and reflected in that feature's UI only.
5. `app.mount("#app")` runs.
6. The root component's `onMounted` callback calls `window.__ogisBoot.ready()`, so boot success means the root actually mounted. A root setup or initial-render failure is contained by the Vue error handler, which calls `window.__ogisBoot.fail()` immediately; the callback never runs, and the static fallback is shown.
7. Service-worker setup runs afterwards, contained: a worker failure cannot turn a successful mount into a boot fallback.

The outer `try/catch` around `boot()` reports a failure and calls `window.__ogisBoot.fail(error)`.

The API client follows the same principle: importing [`src/api/client.js`](../src/api/client.js) no longer throws when no backend base URL is configured. `requireApiBaseUrl()` and the request interceptor fail lazily only when a backend request is actually made, keeping front-end-only mode bootable.

### Static boot fallback

[`index.html`](../index.html) contains a self-contained fallback that works without the app bundle:

- it is hidden on the healthy path;
- capture-phase `error` and `unhandledrejection` listeners show it when the main module fails before mount;
- a watchdog shows it after 30 s by default, as a backstop when the immediate signals do not fire; `window.__ogisBootWatchdogMs` overrides the delay (used by tests);
- `window.__ogisBoot.ready()` hides it and clears the watchdog; it is called from the root component's `onMounted`, so a contained root failure never hides it, and a late ready signal is ignored after a failure;
- `window.__ogisBoot.fail()` shows it; the Vue error handler calls this immediately for a root error;
- copy is English or French from `navigator.language`;
- **Reload** reloads the page;
- **Reset app data** removes the current instance's known-namespace keys and quarantine copies from both localStorage and sessionStorage — exact key matches, so a suffix-colliding instance is untouched — unregisters service workers and deletes `ogis-*` caches, bounded by a short timeout, then reloads.

The fallback is boot-only. Runtime failures after mount are contained by the feature, emitter, Vue or map layers and do not replace a working app with this screen.

## Locate restore

Locate persists a minimal restorable session in the durable `localStorage` store under `ogis_locate_{instanceId}`:

```json
{
  "permissionGranted": true,
  "mode": "active",
  "lastFix": {
    "lat": 48.949011,
    "lng": -55.652574,
    "accuracy": 12,
    "heading": null,
    "at": 1760000000000
  },
  "ownerId": "1f0c9c4e-6b2a-4f7e-9f1e-2a3b4c5d6e7f"
}
```

- `mode` is `"active"`, `"following"` or `null`. `error` and inactive states are never restorable.
- `lastFix` is the last accepted fix: coordinates, accuracy, optional heading and epoch milliseconds. Speed is not persisted.
- `permissionGranted` is durable in the same `localStorage` store, so the Trust explainer does not reappear after a reload or app quit once the user has confirmed it.
- `ownerId` is the tab that owns the restorable session. It is cleared together with the mode and fix.
- Any mode other than `active`/`following` clears the persisted mode, fix and owner.

### Restore flow

Restore is scheduled once per instance in a post-boot microtask and exposed as `restoreComplete`, a promise that always resolves:

1. Read the stored mode, fix and owner.
2. Stop silently if there is no stored mode (a legacy permission-only value is left untouched).
3. Require the stored permission flag and a valid fix. A same-tab reload still matches the stored owner id and proceeds directly. If the owner belongs to another tab, probe its liveness; while it answers, leave the stored session untouched and stop. A dead owner, or no owner, is claimed by this tab.
4. Require the OS geolocation permission state. The state is read through a bounded query with a 2 s default (`LOCATE_PERMISSION_QUERY_TIMEOUT_MS`); a timeout, a missing Permissions API, a rejected query or a malformed result all count as unknown. Apple WebKit has one exception, described below.
5. Seed the position from the stored fix and start `watchPosition` in restore mode.
6. Re-enter `following` when the stored mode was following.
7. Keep the internal restoring flag until the first accepted fix, so an early error stays silent. `restoreComplete` always settles when the restore attempt ends, either way and not necessarily after the first fix; the bounded permission query means a hanging query cannot hold it open.

Restore never opens the app's own permission explainer. On Chromium and Firefox a denied or prompting permission, a timed-out, throwing or malformed permission query, or an unavailable Permissions API all clear the persisted session.

Apple WebKit (identified by `navigator.vendor` containing `"Apple"`) can report `"prompt"` after the user has already granted access (WebKit bug 275479). On that engine, a prompting or unavailable (`null`) permission state is treated as potentially granted when the stored fix is no older than 24 hours (`LOCATE_RESTORE_MAX_AGE_MS`); the normal restore attempt is then made. That attempt calls `watchPosition`, so if the stored grant has actually lapsed the browser may show its native geolocation prompt; restore itself never opens the app's explainer. A stale fix still clears the session, and `denied` never restores. If geolocation errors before the first fix, the silent restore teardown below applies unchanged. The [`canRestoreLocate`](../src/resilience/locateRestore.js) decision rule and the bounded [`queryGeolocationPermission`](../src/resilience/locateRestore.js) helper are unit-tested, and the E2E case simulates an Apple vendor string with a `prompt` result; neither exercises a real Apple WebKit geolocation stack. The timeout path is unit-tested and simulated in E2E with a query that never resolves.

### Silent failure

A restore that fails before its first fix is silent in the app:

- no error modal;
- no console error;
- mode returns to inactive and the stored session is cleared;
- `restoreComplete` still resolves.

Restore yields to an active locate session: if locate is already active when the permission query resolves, the restore leaves it alone. The attempt captures the stored mode and fix at boot, so a session the user starts and then stops before the query resolves is not treated as a cancellation signal.

### Watch and orientation

`watchPosition` runs with `enableHighAccuracy: true` and a 15 s timeout, so a restorable session cannot sit on “Locating…” forever when the device produces no fix. The first accepted fix of a session persists `{ lat, lng, accuracy, heading, at }` immediately, together with a permission grant; later fixes use the debounced write path. Internal motion derivation continues to use `performance.now()` and is not stored.

A timeout after at least one accepted fix is transient: `GeolocationPositionError.code === 3` can arrive while the device is stationary, so the watcher, current session (including following) and persisted locate state stay intact. The user keeps following and navigation instead of silently losing them. Before the first fix behaviour is unchanged: a restored session tears down silently, while a user-started session enters the normal error state.

A boot restore deliberately skips the iOS `DeviceOrientationEvent.requestPermission()` gesture requirement. Heading stays unavailable until the user triggers orientation permission again; the position marker is used meanwhile.

Recordings watch with `enableHighAccuracy: true`, a 2 s `maximumAge` and a 15 s timeout (`RECORDING_GPS_TIMEOUT_MS`). A denied, revoked, timed-out or unavailable GPS pauses the session and preserves the active recording — including a session with zero points — while the panel shows a localised inline error naming the cause. Pausing clears the watch, so no further errors re-enter. The message is in-memory only: it is cleared on start, resume and discard and is not persisted, so a restored paused recording shows no error after a reload. See [Active recording restore](#active-recording-restore) for the paused-restore flow and [Features — Recordings](./10.features.md#recordings--worked-example).

## Route visibility and navigation restore

Routes persists route visibility and navigation ownership in the durable `localStorage` store under `ogis_navigation_{instanceId}`:

```json
{
  "routeId": "m1abc2d-x9k2p1q7",
  "visible": ["m1abc2d-x9k2p1q7", "m1abc2d-a1b2c3d4"],
  "followOwned": true,
  "ownerId": "1f0c9c4e-6b2a-4f7e-9f1e-2a3b4c5d6e7f"
}
```

- `routeId` is the route being navigated, or `null`.
- `visible` is the set of route documents shown on the map.
- `followOwned` records whether navigation started the follow session, so stopping navigation knows whether to stop locate too.
- `ownerId` is the tab that owns the navigating session; it is set while navigating and cleared when navigation stops.

### Visibility restore

Imported routes still start hidden. Visibility is now persisted:

- `showOnMap`, `hideOnMap` and `deleteRoute` update the store.
- On install, persisted visibility is restored before navigation.
- Restore uses `showOnMap(id, { fit: false, claim: false, persist: false })`: it renders the line and waypoints but neither fits the camera nor claims it from another mode.
- The stored camera view is therefore unchanged by a visibility restore.
- IDs with no matching route document are pruned; the store is rewritten only when something was dropped.

`showOnMap(id, options)` accepts `{ fit = true, claim = true, persist = true }`. A normal Show keeps all three; restore turns all three off. `claim` takes the camera from an active follow, draw or navigation mode; `persist` writes visibility back to the navigation store.

### Navigation restore

Navigation is persisted durably and restored for the tab, not shared across tabs:

1. Visibility restores during feature install.
2. `restoreNavigation()` runs non-blocking. If the stored owner belongs to another tab, it probes liveness first; while the owner answers, the navigation session is left untouched and the restore stops. A dead owner, or no owner, is claimed by this tab.
3. It then awaits `locate.restoreComplete`.
4. It resumes only when locate actually re-entered `following`, the route still exists and has usable line geometry.
5. The user may navigate or change state while the restore is pending; the restore then leaves that state alone.
6. A restored navigation never fits or claims the camera; the follow camera resumes through the normal locate path.

Failure semantics:

- A missing route or no usable line geometry clears `routeId`/`followOwned`; any visibility restored for other routes is left intact.
- A denied or unavailable geolocation restore, or locate not re-entering following, clears navigation but leaves the visibility list untouched.
- Every failure is silent: the app opens no explainer or modal and logs no console error.

`followOwned` is preserved across the reload. A restored navigation that owned follow stops locate when navigation stops; a follow the user owned before navigation survives stopping the restored navigation. This mirrors the live behaviour described in [Routes — Navigation](./11.routes.md#navigation). Navigation also stops when the route is hidden or deleted, or when Locate leaves following.

There is no new UI for visibility or navigation restore; the existing route rows and top-centre navigation card are unchanged.

## Active recording restore

The active recording is persisted as `{ active, ownerId }` in the durable `localStorage` store `ogis_recording-active_{instanceId}` (version 2). `migrateRecordingsSession` runs first: it moves a legacy session value into localStorage and splits a legacy local `{ saved, active }` value, leaving the saved store intact if the active write fails.

`restoreStoredActive` runs after install:

1. Read the active document. A missing document, or one with fewer than two usable points, is not restored.
2. If the stored `ownerId` belongs to another tab, probe its liveness. While the owner answers, leave the recording untouched and mark it foreign so this idle tab does not clear it. A dead owner, or no owner, is claimed by this tab.
3. Load the claimed document as **paused**; the GPS watch is not restarted. The panel reports elapsed time from the last recorded point's `t` minus `createdAt`, clamped at zero.
4. A user action (start or resume) takes ownership and clears the foreign marker.

There is no auto-resume: an interrupted recording stays paused until the user resumes or discards it. A denied, revoked, timed-out or unavailable GPS failure during recording pauses and preserves the session (zero points included); the inline error is in-memory only and never persisted. A paused session with fewer than two points is persisted but dropped on the next boot by `hydrateRecordingActive`. See [Tracks — Migration and storage](./15.tracks.md#migration-and-storage) and [Features — Recordings](./10.features.md#recordings--worked-example).

## Map recovery

`useMap` publishes a user-facing lifecycle status alongside its internal readiness flags:

| Status    | Meaning                                                                                      |
| --------- | -------------------------------------------------------------------------------------------- |
| `loading` | Construction or style loading is in progress. No overlay is rendered.                        |
| `ready`   | The style-load initialiser completed; the map instance is published and `map:ready` follows. |
| `error`   | The map cannot be used. The failure surface is shown.                                        |

### Failure codes

| Code          | Cause                                                                                    |
| ------------- | ---------------------------------------------------------------------------------------- |
| `unsupported` | The browser cannot create a WebGL context, or a capability check reports no support.     |
| `init`        | The MapLibre constructor failed for another reason, or the style-load initialiser threw. |
| `style`       | The style document itself failed to load, or the style watchdog expired.                 |
| `contextLost` | The WebGL context was lost.                                                              |

`mapStatusMessageKey(code)` maps these to `map.status.*` locale keys, falling back to `map.status.unavailable` for an unknown code. The keys are `map.status.unavailable`, `map.status.unsupported`, `map.status.init`, `map.status.style` and `map.status.contextLost`; the Retry button uses `map.status.retry`. All exist in both EN and FR.

### Style watchdog and error classification

`MAP_STYLE_TIMEOUT_MS` is 20 s. A positive finite `window.__ogisMapStyleTimeoutMs` overrides it for tests; `resolveStyleTimeout` rejects missing, zero, negative and non-numeric overrides.

Only the style **document** fast-fails:

- the map is still loading, the style has not loaded and the event carries the configured style URL;
- a `sourceId` disqualifies the event, so source, tile, glyph, sprite and DEM failures are routine and ignored.

A style that never arrives is caught by the watchdog rather than leaving the app loading forever.

### WebGL context loss

The canvas listens for `webglcontextlost` and `webglcontextrestored`:

- loss prevents the browser default, sets `contextLost` and shows the failure surface;
- restoration returns the map to `ready` when it had already reached ready;
- if the map was still loading, restoration clears the error, returns to `loading` and restarts the style watchdog.

### Retry and the failure surface

`retryMap()` performs a full page reload. This is deliberate: calling `setStyle` in-app would rerun the large style-load initialiser and risk duplicate listeners and controls.

[`App.vue`](../src/App.vue) renders a quiet, centred `.ogis-map-status` card with `role="alert"`, a localised message and a Retry button. It exists only in the error state; the healthy path renders nothing. The message and retry copy live under `map.status.*` in both locale files. See [UI — Map failure surface](./5.ui.md#map-failure-surface).

### Debug and test signals

The map container publishes:

| Attribute        | Values                      | Purpose                               |
| ---------------- | --------------------------- | ------------------------------------- |
| `data-map-state` | `loading`, `ready`, `error` | Lifecycle state, including failures.  |
| `data-map-ready` | `"true"` while ready        | Success signal; removed on failure.   |
| `data-map-idle`  | `"true"` once settled       | Render-settle signal for screenshots. |

See [Map — readiness signals](./4.map.md#map-readiness-signals) and [Testing — Resilience coverage](./9.testing.md#resilience-coverage).

## Developer guidance

### Define persisted state

- Give every store a namespace, a current `version` and explicit `defaults`.
- Use a hydrator whenever stored data can be legacy, malformed or only partly trustworthy. Repair field-level problems; throw to reject an uninterpretable container.
- Bump the version when the shape changes incompatibly and handle earlier versions in the hydrator.
- Run restored values through the same validation as imported data. A `v: 2` field is not proof of validity.
- Reach the store through `featureCtx.useStorage(namespace, definition)` and read `.state`; use `flush()` only when a write must land immediately.

### Restore safely

- Run side-effecting restores after mount or after the dependency they need has settled; a pure render-only restore may run during install. Do not open the app's own permission explainer during boot; a browser-native prompt can still appear when the platform cannot report the stored grant.
- Gate permission-dependent restores on the OS permission state and fail to defaults when it is not granted. Any accuracy workaround (such as the Apple WebKit `prompt`-state exception) must stay narrow and verify a recent stored fix.
- Make restore failures silent and non-throwing. A crash must not surface an error modal.
- Expose a completion promise when another feature must order its restore after yours (`locate.restoreComplete` is the worked example).
- Do not claim the camera or fit bounds during a restore. Persisted view and navigation both restore without taking the map.

### What not to persist

- Derived values that can be recomputed (distance, speed, live camera pose during a controlled move).
- Large track payloads or binary data in storage; it shares a small origin quota.
- Permission or session state that cannot be safely revalidated after a reload.
- Tab-local sessions that belong to another tab (GPS following, navigation ownership) without an owner id and liveness check; durable tab-owned stores use `ownerId` plus `BroadcastChannel` probing instead.

### Keep the healthy path quiet

- Report contained failures with `reportError`, not `console.error`; production builds drop debug output.
- Prefer a local, explanatory surface (such as the map failure card) over a global toast. There is no global notice system.
- Let the emitter isolate listeners; do not add ad-hoc try/catch around every emit.

### Test hooks

- `__resetPersistedStateForTests()` — dispose every store and the module-level storage listener between unit tests.
- `window.__ogisBootWatchdogMs` — shorten the static fallback watchdog in E2E.
- `window.__ogisMapStyleTimeoutMs` — shorten the map style watchdog in E2E.
- `window.__ogisLocatePermissionTimeoutMs` — shorten the bounded geolocation permission query in E2E (finite positive number; production default stays 2 s).
- `window.__ogisLocateRestoreComplete` — the app instance's locate restore promise, exposed only when `VITE_E2E_FIXTURES=1`; await it instead of importing the module and risking a duplicate instance.
- `data-map-state`, `data-map-ready` and `data-map-idle` — assert map lifecycle and settle states.
- `readStoredState(raw)` in [`tests/e2e/helpers/storage.js`](../tests/e2e/helpers/storage.js) — unwrap an envelope or read a legacy bare value in E2E. Durable tab-owned stores (`locate`, `navigation`, `recording-active`) and the saved recordings store all live in `localStorage`; a legacy `sessionStorage` seed still migrates at boot.

## Limitations and deliberate exclusions

- **No recording auto-resume.** An interrupted active recording restores as a paused line; it does not restart the GPS watch.
- **Recording visibility is not restored.** Saved recording Show/Hide is in-memory only, so saved recordings start hidden after a reload. Route visibility is the persisted exception; see [Tracks — Current limitations](./15.tracks.md#current-limitations).
- **UI and panel state are not restored.** Pane choice, active menu tab, expanded state and transient control state are in-memory only. A reload resets them; desktop then auto-opens the Info pane, while narrower layouts start closed.
- **Map projection is not restored.** Every load boots in globe; the persisted view covers centre, zoom, pitch and bearing only. See [Map — View orientation](./4.map.md#view-orientation).
- **Theme, units and locale are not stored.** Theme and units follow the OS/browser; locale follows `?locale=` or the browser languages. All are storage-free and update live, so there is nothing to restore; each load re-derives them.
- **Hard kills can lose recent routine writes.** Critical transitions — locate mode changes, the first fix and a permission grant, navigation start/stop and visibility, and recording start/pause/discard/save/delete — write immediately. A normal reload, tab close or app switch also flushes the pending debounced write. A crash or force-quit can still skip that flush and lose the most recent routine write (such as a later GPS fix or an imported route document), but the states that define a restorable session are no longer left in that window.
- **Restore never opens the app's own permission explainer.** A denied permission always clears the stored locate session. A prompt or unavailable Permissions API also clears it, except on Apple WebKit with a fix no older than 24 hours; there, `watchPosition` may make the browser show its native prompt if the grant has lapsed.
- **Orientation permission is not restored on iOS.** It needs a user gesture, so heading is unavailable until the user retries.
- **Navigation restores only into following.** If locate does not re-enter following, navigation clears and visibility stays.
- **Map retry is a full reload.** There is no in-app style swap.
- **Routine map errors do not surface.** Only an unsupported/WebGL failure, a style-document failure, the style watchdog or an init failure show the card.
- **No error telemetry.** Reporting is local and development-only.
- **Storage failures are silent.** State stays in memory for the session but is not persisted.
- **Offline downloads can be partial.** A region is saved with the map data that succeeded, and the panel warns when some requests failed; a download with no successful map tiles is refused rather than saved. See [Offline — The download flow](./12.offline.md#the-download-flow).
- **Durable sessions are tab-owned, not tab-scoped storage.** `locate`, `navigation` and `recording-active` live in `localStorage` and carry an `ownerId`, so a reload or app quit restores them. A second live tab probes the owner and leaves its session untouched; a dead owner's session is claimed by the next tab to restore it.
- **Quarantine is one slot per store and instance.** It is a debugging aid, not a history.
- **The static fallback is boot-only.** It is not a general runtime error page.

### Known integration gaps

These are non-deliberate gaps in the current tree, not product decisions.

**Minor**

- **The offline region overlay is not restored after reload.** Deleting the shown region removes its polygon immediately, and another tab's deletion clears it, but a reload starts with no overlay.
- **The offline size estimate counts tiles only.** `estimateRegion` omits the glyph pre-fetch, so the panel's estimated size understates the bytes the download actually requests; the download progress denominator includes glyphs. See [Offline — Known limitations](./12.offline.md#known-limitations).
