# State and resilience

> How ogis.app persists user state, contains failures, restores sessions and recovers from a broken map.

## Overview

Resilience is layered rather than a single catch-all. Each layer limits the blast radius of the one below it:

| Layer            | Implementation                                                                                    | Prevents                                                  |
| ---------------- | ------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| Persisted state  | [`src/resilience/persistedState.js`](../src/resilience/persistedState.js)                         | Corrupt or stale values breaking a feature on reload      |
| Hydration        | [`src/resilience/hydrators/`](../src/resilience/hydrators/)                                       | Repairable data becoming unusable runtime objects         |
| Boot containment | [`src/resilience/errors.js`](../src/resilience/errors.js), [`boot.js`](../src/resilience/boot.js) | One feature or listener taking down the whole app         |
| Domain restore   | `useLocate`, Routes and their hydrators                                                           | A crash losing an active session or navigation            |
| Map recovery     | [`src/resilience/mapRecovery.js`](../src/resilience/mapRecovery.js), `useMap`                     | A failed style or lost WebGL context leaving a blank page |
| Static fallback  | [`index.html`](../index.html)                                                                     | A failed module load leaving an empty document            |

The guiding rules are:

- The healthy path stays quiet: no global toast, no production console noise.
- Persist user intent, not derived or transient data.
- A restore never throws, never opens the app's own permission explainer and never blocks app mount. On Apple WebKit the browser may still show its native geolocation prompt if the stored grant has lapsed.
- Corruption is isolated to one store where possible.
- Failures are reported through the development-only debug logger.

## Persisted state

### `usePersistedState(namespace, definition, instanceId?)`

Creates a reactive store bound to one storage key. The instance id is resolved from `inject("ogisAppId", "app")` when omitted.

```js
import { usePersistedState } from "@/resilience/persistedState.js";

const { state, flush, reset } = usePersistedState("my-feature", {
  version: 1,
  defaults: { items: [] },
  hydrate: hydrateMyFeature,
  debounce: 250,
  crossTab: false,
});
```

| Definition field | Default   | Purpose                                                                                                    |
| ---------------- | --------- | ---------------------------------------------------------------------------------------------------------- |
| `version`        | `1`       | Current schema version.                                                                                    |
| `defaults`       | `{}`      | Deep-cloned initial state. Its container type must match the hydrated data.                                |
| `storage`        | `"local"` | `"local"` or `"session"`. Session storage is never cross-tab.                                              |
| `crossTab`       | `false`   | Apply writes from other tabs through the `storage` event.                                                  |
| `debounce`       | `250`     | Coalescing window in milliseconds. `0` writes on the next tick.                                            |
| `hydrate`        | —         | Synchronous `(data, { version, namespace, instanceId }) => cleanedData`. Throw to reject the stored value. |
| `onSync`         | —         | Runs after an external write is applied: `(state, { namespace, instanceId, source: "external" })`.         |

The returned API is `{ state, flush, reset }`:

- `state` — reactive data. External syncs replace it in place, so existing `state.*` references stay valid (arrays splice, objects merge keys).
- `flush()` — clears the pending debounce timer and writes now.
- `reset()` — removes the store key, restores defaults and suppresses the resulting watch echo.

Features normally receive the same function as `featureCtx.useStorage(namespace, definition)` and read `.state`; see [Features](./10.features.md#persistence-and-restore).

Keys follow the instance-scoped format `ogis_{namespace}_{instanceId}`; see [Instances](./3.instances.md). One store exists per `(instanceId, namespace)`: repeated calls return the same object. `resetInstanceState(instanceId)` removes every `ogis_*_{instanceId}` localStorage key for one instance, including quarantine copies, and leaves other instances untouched.

### Envelope and versions

Every write is a versioned envelope:

```json
{
  "__ogisState": 1,
  "version": 1,
  "data": { "items": [] }
}
```

- A bare value is legacy data at version `0`.
- A stored version newer than the definition is rejected and quarantined, so a downgrade preserves the newer raw value instead of silently overwriting it.
- Older versions are passed to `hydrate` with `context.version`.
- Bump `version` when the stored shape changes incompatibly and let the hydrator migrate older input.
- Hydration does not rewrite storage. A legacy bare value stays untouched until the first mutation, then the normal write path emits an envelope.
- Writes are skipped when the serialised envelope is unchanged.

### Hydration, defaults and quarantine

A store boots from defaults, then applies the stored value when it decodes and hydrates successfully:

1. Read and parse the raw string.
2. Unwrap the envelope, or treat a bare value as version `0`.
3. Run `hydrate` when supplied; otherwise require the value's container type to match `defaults`.
4. Require the hydrator's result to have the same container type as `defaults`.

A failed step falls back to defaults and copies the raw value to `ogis_quarantine_{namespace}_{instanceId}`. Quarantine is diagnostic only: it is one slot per store and instance, so a later invalid value overwrites it. The failure is logged through the `state` debug channel, not reported as a user-facing error.

An invalid `storage` event from another tab is ignored rather than quarantined.

Tracking stores are more forgiving than their top-level container rule suggests: individual invalid documents and points are dropped while valid siblings survive. See [Hydration and validation](#hydration-and-validation).

### Writes, debounce and quota

A deep watcher coalesces changes through `debounce`. The view store uses a 300 ms window; other stores use the 250 ms default. Pending writes flush on `pagehide` and when the document becomes hidden, so a normal reload, tab close or app switch writes the last change. Neither event is guaranteed on a hard kill or force-quit, so the most recent debounced write can be lost and the app resumes from the last successful write.

Storage failures are silent by design:

- A missing or throwing `localStorage`/`sessionStorage` is treated as unavailable.
- Quota, privacy-mode and serialisation failures leave state in memory, log through the debug channel and retry on a later mutation.
- No modal, toast or console error is raised.

### Cross-tab sync

`crossTab: true` attaches one `storage` listener per window. When another tab writes the matching key, the receiving store:

1. decodes and hydrates the new value;
2. clears any pending local write and replaces its state without echoing back;
3. runs `onSync`, if defined;
4. emits `state:sync` with `{ namespace, instanceId, source: "external", key }`.

Invalid external values are ignored. Only the **view** store opts in. Its `onSync` applies the external camera through `applyExternalView`, which skips while a controller owns the camera or persistence is suppressed; the programmatic `jumpTo` suppresses its own `moveend` so the receiving tab does not write the value back.

Only `view` has live cross-tab sync. `locate`, `navigation` and `recordings.active` are intended to be tab-owned, but they currently use shared `localStorage` keys with `crossTab` disabled, so another tab can read and restore them at boot; this is a known gap, not enforced tab ownership. `routes`, `recordings.saved`, `offline-regions` and `sync` are shared content with no cross-tab sync or conflict resolution. See [Known integration gaps](#known-integration-gaps).

### Session storage

`storage: "session"` reads and writes `sessionStorage` under the same key format. Cross-tab sync is forced off because session storage is already tab-scoped. Quarantine copies still use localStorage. No current store selects session storage; it exists for future tab-local state.

| Namespace         | Version | Key                                 | Shape                                                       | Cross-tab | Hydrator                |
| ----------------- | ------- | ----------------------------------- | ----------------------------------------------------------- | --------- | ----------------------- |
| `view`            | 1       | `ogis_view_{instanceId}`            | `{ mapView: { center, zoom, pitch, bearing } }`             | Yes       | `hydrateView`           |
| `recordings`      | 1       | `ogis_recordings_{instanceId}`      | `{ saved: TrackDocument[], active: TrackDocument \| null }` | No        | `hydrateRecordings`     |
| `routes`          | 1       | `ogis_routes_{instanceId}`          | `TrackDocument[]`                                           | No        | `hydrateRoutes`         |
| `offline-regions` | 1       | `ogis_offline-regions_{instanceId}` | `Region[]`                                                  | No        | `hydrateOfflineRegions` |
| `locate`          | 2       | `ogis_locate_{instanceId}`          | `{ permissionGranted, mode, lastFix }`                      | No        | `hydrateLocate`         |
| `navigation`      | 1       | `ogis_navigation_{instanceId}`      | `{ routeId, visible, followOwned }`                         | No        | `hydrateNavigation`     |
| `sync`            | 1       | `ogis_sync_{instanceId}`            | `{ queue, failed }`                                         | No        | `hydrateSync`           |

- `view` stores the last persisted camera. `center` and `zoom` may be `null` before the first meaningful fit; `pitch` and `bearing` default to 0.
- `recordings` and `routes` hold canonical `v: 2` track documents shared with [Tracks](./15.tracks.md).
- `offline-regions` holds downloaded-region metadata only; tiles live in the service-worker Cache API. See [Offline](./12.offline.md).
- `navigation` holds route visibility and navigation ownership. See [Routes](./11.routes.md#visibility).
- `sync` is the offline sync queue for the backend-dependent features. It is dormant while the app runs in SPA front-end only mode.
- Track documents are validated and sanitised on hydrate. See [Hydration and validation](#hydration-and-validation) and [Tracks — Migration and storage](./15.tracks.md#migration-and-storage).

Invalid data is copied to `ogis_quarantine_{namespace}_{instanceId}` while the store falls back to defaults.

## Hydration and validation

Hydrators repair what can be repaired and reject what cannot. A rejected top-level value quarantines the whole store; a rejected entry is dropped from a valid container.

| Store             | Repaired                                                                                                                                                 | Rejected or dropped                                                                                                                                                                           |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `view`            | Missing `pitch`/`bearing` become 0; unusable centre or zoom becomes `null`; legacy bare `{ mapView }` is accepted.                                       | A non-object top level, or a present `mapView` that is not an object, rejects the store.                                                                                                      |
| `recordings`      | Legacy saved/active documents migrate; points and waypoints sanitise; extra waypoint metadata is preserved.                                              | A non-object top level or non-array `saved` rejects the store. Invalid saved documents are dropped; an active document needs at least two usable points.                                      |
| `routes`          | Legacy route shapes migrate; points and waypoints sanitise; documents are forced to `v: 2` and `kind: "route"`.                                          | A non-array top level rejects the store. Invalid documents are dropped. When two documents share an id, the first wins.                                                                       |
| `offline-regions` | Valid entries keep their fields and extra metadata; coordinates, zooms, counts and timestamps are validated for safe panel formatting.                   | A non-array top level rejects the store. Entries with a missing id/name, inverted or out-of-range bounds, `minZoom > maxZoom`, negative counts/bytes or a non-finite `createdAt` are dropped. |
| `locate`          | The permission flag accepts `true`, `"true"` or `1`; a finite heading is kept and a non-finite heading becomes `null`.                                   | A non-object top level rejects the store. Only `active` and `following` are restorable modes; an invalid or missing fix drops both mode and fix.                                              |
| `navigation`      | Strings are trimmed; `visible` is deduped in first-seen order; a navigated route is always added to `visible`; `followOwned` survives only with a route. | A non-object top level rejects the store. Empty and non-string ids are dropped.                                                                                                               |
| `sync`            | Non-array `queue`/`failed` values become arrays; items with a usable id are kept.                                                                        | A non-object top level rejects the store. Items without a string or finite numeric id are dropped.                                                                                            |

### Track document sanitisation

`hydrateRecordings` and `hydrateRoutes` run the canonical migration helpers and then [`sanitiseTrackDocument`](../src/utils/track/model.js). That function:

- normalises every point with `normalisePoint`, dropping non-finite or out-of-range coordinates;
- drops empty segments and rejects a document with no usable segment points;
- normalises waypoints with `normaliseWaypoint`, which scrubs coordinates and optional `ele`/`t` while preserving descriptive extras (`name`, `desc`, `cmt`, `sym`, `type`, `links`, …);
- forces `v: 2`, the requested `kind`, a trimmed or generated id, and safe scalar fields.

A v2 document is therefore revalidated on every hydrate, not trusted because its `v` field says 2.

### Corrupt-state boot

When a store is unusable:

- the app mounts normally with that store's defaults;
- other stores hydrate independently;
- the raw value remains available under the quarantine key;
- the feature renders its empty state (for example, an empty recordings list);
- no modal, console error or boot fallback appears.

The E2E corrupt-state case seeds an invalid recordings value and a malformed offline region, then asserts defaults, quarantine and a clean console; see [Testing — Resilience coverage](./9.testing.md#resilience-coverage).

## Crash containment

### Error reporting

[`reportError(error, context)`](../src/resilience/errors.js) normalises any thrown value into an `Error`, logs it through the development-only `resilience` debug channel and returns it. It never throws. In production the debug logger is a no-op, so containment does not spam the console.

[`installGlobalErrorHandlers(target)`](../src/resilience/errors.js) installs capture-phase `error` and `unhandledrejection` listeners once per target. It ignores resource-load failures, which have no script error or message, and never calls `preventDefault()`, so the browser's own diagnostics remain visible.

[`installVueErrorHandler(app)`](../src/resilience/errors.js) routes component errors through the same reporter.

There is no error-reporting backend. Containment is local and diagnostic only.

### Listener isolation

[`EventEmitter.emit`](../src/classes/EventEmitter.js) catches each listener independently and reports failures with `{ source: "emitter", event, index }`. One throwing listener no longer prevents later listeners from running or aborts the emitting feature.

### Feature install isolation

[`installFeature(name, feature, baseContext, { onError })`](../src/resilience/boot.js) installs one feature inside a boundary:

- `addButton`, `addPanel`, `on`, `once` and `onMapReady` return disposers, and the wrapper records each one.
- If `install` throws, the recorded disposers run in reverse order before the error is reported.
- A broken feature therefore cannot leave a partial panel, button or listener behind.
- `provide` has no Vue counterpart to undo, so a provide made before the throw remains registered. The accepted trade-off is that a failed feature's provide is unused.
- The function returns `false`; the next feature still installs and the app still mounts.

`onMapReady` callbacks are also guarded at call time: a throwing callback is reported with `{ source: "map-ready" }` and does not break the `map:ready` emitter or other features.

### Boot sequence

1. `index.html` installs its own early error/rejection listeners and boot watchdog before any module loads.
2. [`src/main.js`](../src/main.js) installs the global error handlers first.
3. The Vue app is created, `installVueErrorHandler` is attached and the app context is provided.
4. Each core feature is installed through `installFeature`; failures are contained and reflected in that feature's UI only.
5. `app.mount("#app")` runs.
6. `window.__ogisBoot.ready()` marks boot success immediately after mount.
7. Service-worker setup runs afterwards, contained: a worker failure cannot turn a successful mount into a boot fallback.

The outer `try/catch` around `boot()` reports a failure and calls `window.__ogisBoot.fail(error)`.

The API client follows the same principle: importing [`src/api/client.js`](../src/api/client.js) no longer throws when no backend base URL is configured. `requireApiBaseUrl()` and the request interceptor fail lazily only when a backend request is actually made, keeping front-end-only mode bootable.

### Static boot fallback

[`index.html`](../index.html) contains a self-contained fallback that works without the app bundle:

- it is hidden on the healthy path;
- capture-phase `error` and `unhandledrejection` listeners show it when the main module fails before mount;
- a watchdog shows it after 30 s by default; `window.__ogisBootWatchdogMs` overrides the delay (used by tests);
- `window.__ogisBoot.ready()` hides it and clears the watchdog; `window.__ogisBoot.fail()` shows it;
- copy is English or French from `navigator.language`;
- **Reload** reloads the page;
- **Reset app data** removes the instance's localStorage keys, unregisters service workers and deletes `ogis-*` caches, bounded by a short timeout, then reloads.

The fallback is boot-only. Runtime failures after mount are contained by the feature, emitter, Vue or map layers and do not replace a working app with this screen.

## Locate restore

Locate persists a minimal restorable session under `ogis_locate_{instanceId}`:

```json
{
  "permissionGranted": true,
  "mode": "active",
  "lastFix": {
    "lat": 48.949011,
    "lng": -55.652574,
    "accuracy": 12,
    "heading": null,
    "at": 1760000000000
  }
}
```

- `mode` is `"active"`, `"following"` or `null`. `error` and inactive states are never restorable.
- `lastFix` is the last accepted fix: coordinates, accuracy, optional heading and epoch milliseconds. Speed is not persisted.
- Any mode other than `active`/`following` clears both the persisted mode and fix.

### Restore flow

Restore is scheduled once per instance in a post-boot microtask and exposed as `restoreComplete`, a promise that always resolves:

1. Read the stored mode and fix.
2. Stop silently if there is no stored mode (a legacy permission-only value is left untouched).
3. Require the stored permission flag, a valid fix and `navigator.permissions.query({ name: "geolocation" })` returning `"granted"`. Apple WebKit has one exception, described below.
4. Seed the position from the stored fix and start `watchPosition` in restore mode.
5. Re-enter `following` when the stored mode was following.
6. Keep the internal restoring flag until the first accepted fix, so an early error stays silent. `restoreComplete` resolves when the restore attempt ends either way, not necessarily after the first fix.

Restore never opens the app's own permission explainer. On Chromium and Firefox a denied or prompting permission, a throwing permission query or an unavailable Permissions API all clear the persisted session.

Apple WebKit (identified by `navigator.vendor` containing `"Apple"`) can report `"prompt"` after the user has already granted access (WebKit bug 275479). On that engine, a prompting or unavailable (`null`) permission state is treated as potentially granted when the stored fix is no older than 24 hours (`LOCATE_RESTORE_MAX_AGE_MS`); the normal restore attempt is then made. That attempt calls `watchPosition`, so if the stored grant has actually lapsed the browser may show its native geolocation prompt; restore itself never opens the app's explainer. A stale fix still clears the session, and `denied` never restores. If geolocation errors before the first fix, the silent restore teardown below applies unchanged. The [`canRestoreLocate`](../src/resilience/locateRestore.js) decision rule is unit-tested, and the E2E case simulates an Apple vendor string with a `prompt` result; neither exercises a real Apple WebKit geolocation stack.

### Silent failure

A restore that fails before its first fix is silent in the app:

- no error modal;
- no console error;
- mode returns to inactive and the stored session is cleared;
- `restoreComplete` still resolves.

Restore yields to an active locate session: if locate is already active when the permission query resolves, the restore leaves it alone. The attempt captures the stored mode and fix at boot, so a session the user starts and then stops before the query resolves is not treated as a cancellation signal.

### Watch and orientation

`watchPosition` runs with `enableHighAccuracy: true` and a 15 s timeout, so a restorable session cannot sit on “Locating…” forever when the device produces no fix. Every accepted fix persists `{ lat, lng, accuracy, heading, at }`; internal motion derivation continues to use `performance.now()` and is not stored.

A timeout after at least one accepted fix is transient: `GeolocationPositionError.code === 3` can arrive while the device is stationary, so the watcher, current session (including following) and persisted locate state stay intact. The user keeps following and navigation instead of silently losing them. Before the first fix behaviour is unchanged: a restored session tears down silently, while a user-started session enters the normal error state.

A boot restore deliberately skips the iOS `DeviceOrientationEvent.requestPermission()` gesture requirement. Heading stays unavailable until the user triggers orientation permission again; the position marker is used meanwhile.

Recordings restore an interrupted active track as **paused**; recording auto-resume is out of scope. See [Features — Recordings](./10.features.md#recordings--worked-example).

## Route visibility and navigation restore

Routes persists route visibility and navigation ownership under `ogis_navigation_{instanceId}`:

```json
{
  "routeId": "m1abc2d-x9k2p1q7",
  "visible": ["m1abc2d-x9k2p1q7", "m1abc2d-a1b2c3d4"],
  "followOwned": true
}
```

- `routeId` is the route being navigated, or `null`.
- `visible` is the set of route documents shown on the map.
- `followOwned` records whether navigation started the follow session, so stopping navigation knows whether to stop locate too.

### Visibility restore

Imported routes still start hidden. Visibility is now persisted:

- `showOnMap`, `hideOnMap` and `deleteRoute` update the store.
- On install, persisted visibility is restored before navigation.
- Restore uses `showOnMap(id, { fit: false, claim: false, persist: false })`: it renders the line and waypoints but neither fits the camera nor claims it from another mode.
- The stored camera view is therefore unchanged by a visibility restore.
- IDs with no matching route document are pruned; the store is rewritten only when something was dropped.

`showOnMap(id, options)` accepts `{ fit = true, claim = true, persist = true }`. A normal Show keeps all three; restore turns all three off. `claim` takes the camera from an active follow, draw or navigation mode; `persist` writes visibility back to the navigation store.

### Navigation restore

Navigation is persisted and restored, not session-only:

1. Visibility restores during feature install.
2. `restoreNavigation()` runs non-blocking and awaits `locate.restoreComplete`.
3. It resumes only when locate actually re-entered `following`, the route still exists and has usable line geometry.
4. The user may navigate or change state while the restore is pending; the restore then leaves that state alone.
5. A restored navigation never fits or claims the camera; the follow camera resumes through the normal locate path.

Failure semantics:

- A missing route or no usable line geometry clears `routeId`/`followOwned`; any visibility restored for other routes is left intact.
- A denied or unavailable geolocation restore, or locate not re-entering following, clears navigation but leaves the visibility list untouched.
- Every failure is silent: the app opens no explainer or modal and logs no console error.

`followOwned` is preserved across the reload. A restored navigation that owned follow stops locate when navigation stops; a follow the user owned before navigation survives stopping the restored navigation. This mirrors the live behaviour described in [Routes — Navigation](./11.routes.md#navigation). Navigation also stops when the route is hidden or deleted, or when Locate leaves following.

There is no new UI for visibility or navigation restore; the existing route rows and top-centre navigation card are unchanged.

## Map recovery

`useMap` publishes a user-facing lifecycle status alongside its internal readiness flags:

| Status    | Meaning                                                                                      |
| --------- | -------------------------------------------------------------------------------------------- |
| `loading` | Construction or style loading is in progress. No overlay is rendered.                        |
| `ready`   | The style-load initialiser completed; the map instance is published and `map:ready` follows. |
| `error`   | The map cannot be used. The failure surface is shown.                                        |

### Failure codes

| Code          | Cause                                                                                    |
| ------------- | ---------------------------------------------------------------------------------------- |
| `unsupported` | The browser cannot create a WebGL context, or a capability check reports no support.     |
| `init`        | The MapLibre constructor failed for another reason, or the style-load initialiser threw. |
| `style`       | The style document itself failed to load, or the style watchdog expired.                 |
| `contextLost` | The WebGL context was lost.                                                              |

`mapStatusMessageKey(code)` maps these to `map.status.*` locale keys, falling back to `map.status.unavailable` for an unknown code. The keys are `map.status.unavailable`, `map.status.unsupported`, `map.status.init`, `map.status.style` and `map.status.contextLost`; the Retry button uses `map.status.retry`. All exist in both EN and FR.

### Style watchdog and error classification

`MAP_STYLE_TIMEOUT_MS` is 20 s. A positive finite `window.__ogisMapStyleTimeoutMs` overrides it for tests; `resolveStyleTimeout` rejects missing, zero, negative and non-numeric overrides.

Only the style **document** fast-fails:

- the map is still loading, the style has not loaded and the event carries the configured style URL;
- a `sourceId` disqualifies the event, so source, tile, glyph, sprite and DEM failures are routine and ignored.

A style that never arrives is caught by the watchdog rather than leaving the app loading forever.

### WebGL context loss

The canvas listens for `webglcontextlost` and `webglcontextrestored`:

- loss prevents the browser default, sets `contextLost` and shows the failure surface;
- restoration returns the map to `ready` when it had already reached ready;
- if the map was still loading, restoration clears the error, returns to `loading` and restarts the style watchdog.

### Retry and the failure surface

`retryMap()` performs a full page reload. This is deliberate: calling `setStyle` in-app would rerun the large style-load initialiser and risk duplicate listeners and controls.

[`App.vue`](../src/App.vue) renders a quiet, centred `.ogis-map-status` card with `role="alert"`, a localised message and a Retry button. It exists only in the error state; the healthy path renders nothing. The message and retry copy live under `map.status.*` in both locale files. See [UI — Map failure surface](./5.ui.md#map-failure-surface).

### Debug and test signals

The map container publishes:

| Attribute        | Values                      | Purpose                               |
| ---------------- | --------------------------- | ------------------------------------- |
| `data-map-state` | `loading`, `ready`, `error` | Lifecycle state, including failures.  |
| `data-map-ready` | `"true"` while ready        | Success signal; removed on failure.   |
| `data-map-idle`  | `"true"` once settled       | Render-settle signal for screenshots. |

See [Map — readiness signals](./4.map.md#map-readiness-signals) and [Testing — Resilience coverage](./9.testing.md#resilience-coverage).

## Developer guidance

### Define persisted state

- Give every store a namespace, a current `version` and explicit `defaults`.
- Use a hydrator whenever stored data can be legacy, malformed or only partly trustworthy. Repair field-level problems; throw to reject an uninterpretable container.
- Bump the version when the shape changes incompatibly and handle earlier versions in the hydrator.
- Run restored values through the same validation as imported data. A `v: 2` field is not proof of validity.
- Reach the store through `featureCtx.useStorage(namespace, definition)` and read `.state`; use `flush()` only when a write must land immediately.

### Restore safely

- Run side-effecting restores after mount or after the dependency they need has settled; a pure render-only restore may run during install. Do not open the app's own permission explainer during boot; a browser-native prompt can still appear when the platform cannot report the stored grant.
- Gate permission-dependent restores on the OS permission state and fail to defaults when it is not granted. Any accuracy workaround (such as the Apple WebKit `prompt`-state exception) must stay narrow and verify a recent stored fix.
- Make restore failures silent and non-throwing. A crash must not surface an error modal.
- Expose a completion promise when another feature must order its restore after yours (`locate.restoreComplete` is the worked example).
- Do not claim the camera or fit bounds during a restore. Persisted view and navigation both restore without taking the map.

### What not to persist

- Derived values that can be recomputed (distance, speed, live camera pose during a controlled move).
- Large track payloads or binary data in localStorage; it shares a small origin quota.
- Permission or session state that cannot be safely revalidated after a reload.
- Tab-local sessions that belong to another tab (GPS following, navigation ownership) unless the store is explicitly per-tab.

### Keep the healthy path quiet

- Report contained failures with `reportError`, not `console.error`; production builds drop debug output.
- Prefer a local, explanatory surface (such as the map failure card) over a global toast. There is no global notice system.
- Let the emitter isolate listeners; do not add ad-hoc try/catch around every emit.

### Test hooks

- `__resetPersistedStateForTests()` — dispose every store and the module-level storage listener between unit tests.
- `window.__ogisBootWatchdogMs` — shorten the static fallback watchdog in E2E.
- `window.__ogisMapStyleTimeoutMs` — shorten the map style watchdog in E2E.
- `data-map-state`, `data-map-ready` and `data-map-idle` — assert map lifecycle and settle states.
- `readStoredState(raw)` in [`tests/e2e/helpers/storage.js`](../tests/e2e/helpers/storage.js) — unwrap an envelope or read a legacy bare value in E2E.

## Limitations and deliberate exclusions

- **No recording auto-resume.** An interrupted active recording restores as a paused line; it does not restart the GPS watch.
- **Recording visibility is not restored.** Saved recording Show/Hide is in-memory only, so saved recordings start hidden after a reload. Route visibility is the persisted exception; see [Tracks — Current limitations](./15.tracks.md#current-limitations).
- **UI and panel state are not restored.** Pane choice, active menu tab, expanded state and transient control state are in-memory only. A reload resets them; desktop then auto-opens the Info pane, while narrower layouts start closed.
- **Map projection is not restored.** Every load boots in globe; the persisted view covers centre, zoom, pitch and bearing only. See [Map — View orientation](./4.map.md#view-orientation).
- **Theme, units and locale are not stored.** Theme and units follow the OS/browser; locale follows `?locale=` or the browser languages. All are storage-free and update live, so there is nothing to restore; each load re-derives them.
- **Hard kills can lose recent writes.** A normal reload, tab close or app switch flushes the pending debounced write. A crash or force-quit can skip that flush, leaving the app to resume from the last successful write; a normal reload or close is unaffected.
- **Restore never opens the app's own permission explainer.** A denied permission always clears the stored locate session. A prompt or unavailable Permissions API also clears it, except on Apple WebKit with a fix no older than 24 hours; there, `watchPosition` may make the browser show its native prompt if the grant has lapsed.
- **Orientation permission is not restored on iOS.** It needs a user gesture, so heading is unavailable until the user retries.
- **Navigation restores only into following.** If locate does not re-enter following, navigation clears and visibility stays.
- **Map retry is a full reload.** There is no in-app style swap.
- **Routine map errors do not surface.** Only an unsupported/WebGL failure, a style-document failure, the style watchdog or an init failure show the card.
- **No error telemetry.** Reporting is local and development-only.
- **Storage failures are silent.** State stays in memory for the session but is not persisted.
- **Quarantine is one slot per store and instance.** It is a debugging aid, not a history.
- **The static fallback is boot-only.** It is not a general runtime error page.
- **Session storage exists but is unused.** No current store selects it.

### Known integration gaps

These are non-deliberate gaps in the current tree, not product decisions.

**Should-fix**

- **Cross-tab ownership is not enforced.** `locate`, `navigation` and `recordings.active` use shared `localStorage` keys with `crossTab` disabled, so another tab can restore them at boot; see [Cross-tab sync](#cross-tab-sync).
- **Offline region downloads ignore per-URL failures.** A region can be persisted with zero or partial cached tiles, and there is no per-request timeout, so progress can hang until the user presses Cancel.
- **Recording geolocation has no error path or timeout.** The watch uses a null error callback and no timeout, so a denied, revoked or unavailable GPS can leave the recording UI running with no points; a restored paused recording shows `0:00` until resume.
- **Boot success can mask a blank app.** Vue's error handler contains a root setup or render failure, but `window.__ogisBoot.ready()` runs immediately after `app.mount()` returns, hiding the static fallback and potentially leaving a blank app.
- **The locate permission query has no timeout.** A stalled `navigator.permissions.query` leaves `locate.restoreComplete` pending, which also holds route-navigation restore open indefinitely.
- **Feature-install rollback has a composable blind spot.** Rollback covers wrapped registrations but not side effects inside composables; a failed `useGeoJSON` setup can leave a partial, dead overlay manager.

**Minor**

- **Service-worker cache writes are unhandled.** Cache puts can reject without surfacing the failure.
- **Service-worker registration failures only log to the console.**
- **Share/download fallback failures are silent.**
- **The offline region overlay is not restored or removed on delete.** The shown polygon is not removed when its region is deleted, and is not restored after reload.
- **`hydrateView` does not range-check longitude.** A finite but out-of-range longitude is accepted.
