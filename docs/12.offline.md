# Offline — PWA shell and opportunistic map cache

ogis.app is an installable PWA whose service worker keeps the app shell available without a connection and opportunistically caches map resources as the user browses. There is no user-managed region download: map coverage offline is limited to the tiles, glyphs, sprites and styles previously fetched while online.

---

## Overview

Offline support is built on two cooperating pieces:

- **[`public/sw.js`](../public/sw.js)** — a hand-rolled service worker (no Workbox) that caches the app shell and cross-origin map resources as they are fetched.
- **[`src/utils/serviceWorker.js`](../src/utils/serviceWorker.js)** — registration gating, including the dev self-heal that removes a stale worker.

Installability is separate from caching: [`public/manifest.json`](../public/manifest.json) declares the **PWA** metadata (`display: standalone`), so the app can be installed from the browser install prompt or Add to Home Screen. There is no backend and no separate tile provider; the worker caches what the normal map requests already fetch.

| Capability                       | Without a connection                                                                                                   |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Boot the app shell               | Works when the shell was cached on an earlier visit                                                                    |
| Load app code and styles         | Same-origin hashed assets are served cache-first after the first fetch                                                 |
| Show previously viewed map areas | Tiles, glyphs, sprites and styles come from the map cache                                                              |
| Show areas never viewed online   | Not cached — tiles are missing and MapLibre renders the available background or gaps                                   |
| Navigate a stored route          | Works on a compass-capable device: navigation is client-side GPS and stored geometry; the basemap coverage stays local |
| Download a region explicitly     | Not offered                                                                                                            |

## The service worker

`public/sw.js` maintains two caches ([`public/sw.js:6-8`](../public/sw.js#L6-L8)):

| Cache | Name            | Contents                                                                                               |
| ----- | --------------- | ------------------------------------------------------------------------------------------------------ |
| Shell | `ogis-shell-v1` | App shell: `/`, `/index.html`, and same-origin hashed JS/CSS bundles                                   |
| Map   | `ogis-map-v1`   | Cross-origin map resources: style JSON, vector/raster tiles, DEM hillshades, glyphs, sprites, TileJSON |

The activate handler deletes every cache that is not in `CACHE_ALLOWLIST` — the two caches above ([`public/sw.js:48-61`](../public/sw.js#L48-L61)). Bumping a cache name therefore invalidates the old cache on the next activation.

The map cache is scoped by hostname: any path on these hosts is a candidate for opportunistic caching ([`public/sw.js:14-19`](../public/sw.js#L14-L19)):

```
tiles.openfreemap.org
tiles.mapterhorn.com
tile.ogis.app
raw.githubusercontent.com
```

Cross-origin requests to any other host pass through untouched and are not cached.

### Registration and gating

Registration is controlled by [`src/utils/serviceWorker.js`](../src/utils/serviceWorker.js) (`setupServiceWorker()`), called at the end of [`src/main.js`](../src/main.js#L200). The worker itself ([`public/sw.js`](../public/sw.js)) is environment-agnostic; only the registration is gated:

| Context                                   | Behaviour                                                                                     |
| ----------------------------------------- | --------------------------------------------------------------------------------------------- |
| Production build (`import.meta.env.PROD`) | Registers `/sw.js`                                                                            |
| Dev with `VITE_SW=1`                      | Registers `/sw.js` — the opt-in used by E2E                                                   |
| Dev (default)                             | Does **not** register; unregisters any existing worker and deletes every cache for the origin |

The dev default is deliberate **self-healing**: registering the worker in Vite dev is harmful because the worker is cache-first for same-origin requests (see [Fetch strategy](#fetch-strategy)), so it used to cache Vite's dev module graph and `/@vite/client` — which hardcodes a per-server-instance HMR token. The stale token broke the WebSocket (`[vite] failed to connect to websocket`) and left a corrupted module graph. Now a normal dev visit removes the old registration and purges all origin caches, so a poisoned profile recovers on its next reload.

`setupServiceWorker()` returns `{ registered, cleanedRegistrations, cleanedCaches }`. A registration failure is reported through `reportError` with `{ source: "service-worker", phase: "register" }` and still resolves with `registered: false`; dev cleanup problems log through the `service-worker` debug channel. Its browser globals and reporter are injectable, so the behaviour is unit-tested in [`tests/unit/serviceWorker.test.js`](../tests/unit/serviceWorker.test.js).

The E2E webServer opts in with `VITE_SW: "1"` ([`playwright.config.js:174`](../playwright.config.js#L174)) so the browser suite exercises the SW paths; [`tests/e2e/sw.spec.js`](../tests/e2e/sw.spec.js) asserts the worker registers on load and that a reload boots cleanly while it is in control.

### Fetch strategy

The fetch handler ([`public/sw.js:63`](../public/sw.js#L63)) branches by request type:

- **Navigation** (`request.mode === 'navigate'`) — **network-first**, falling back to the cached `index.html` offline. A successful response also refreshes the cached shell so hashed asset references stay in sync after a deploy.
- **Cross-origin map resources** — **cache-first** with a network fallback on the allowlisted hosts. Only successful GET responses are stored; opaque or error responses are skipped. A resource fetched while online is therefore available on later offline visits; one that was never fetched is not.
- **Same-origin assets** — **cache-first** with a network fallback, populating the shell cache on first fetch.

Every cache write follows the same path: `cacheResponse` clones the response, passes the `cache.put` promise to `event.waitUntil(...)` so the write is not cancelled when the worker goes idle, and swallows a rejection so a failed cache write cannot break the response returned to the page ([`public/sw.js:29-37`](../public/sw.js#L29-L37)). This applies to navigation shell refreshes, cross-origin map resources and same-origin assets alike.

### Updates, eviction and reset

The worker has no message handler and the app never deletes individual cached URLs. Entries are added by the fetch strategy above; they are removed or replaced only through these paths:

- **Cache versioning** — cache names carry a `-v1` suffix; bumping a name in `public/sw.js` leaves the old cache outside `CACHE_ALLOWLIST`, and the next activate deletes it.
- **Browser eviction** — the Cache API shares the origin's storage quota with everything else. Under storage pressure the browser may evict cached responses; the app neither requests persistent storage nor reports cache usage, so there is no in-app quota or persistence indicator.
- **Reset app data** — the static boot fallback's **Reset app data** action unregisters service workers and deletes every `ogis-*` cache, alongside removing the current instance's known storage keys ([`index.html`](../index.html)). It is the only in-app way to clear map coverage wholesale.
- **Shell refresh** — a successful online navigation rewrites the cached shell (`/index.html`), so a deploy's new hashed asset references replace the old ones.

Tiles and glyphs for a rebuilt upstream style can become unreachable when the provider changes a dated TileJSON slug; there is no individual purge or refresh path. A cache-name bump is the developer-side reset.

## What works without a connection

- **App shell and UI** — previously cached HTML, CSS and JavaScript boot from the shell cache. A first-ever visit still needs a connection to install anything.
- **Map coverage** — only resources already fetched are available. Panning or zooming into an area that was never viewed online leaves tiles missing; there is no background prefetch and no coverage estimate.
- **Route navigation** — the guidance logic is entirely client-side (GPS plus stored route geometry), so it keeps running offline while the basemap is limited to cached coverage. Navigation still requires a compass-capable device: the boot capability probe is local and needs no network, but an incapable device disables Navigate. See [Routes — Navigation](./11.routes.md#navigation).
- **Installed mode** — an installed PWA opens standalone with no URL bar; same-origin navigations remain full SPA reloads (see [Terminology](./1.terminology.md#core-terms)).

## No user-managed downloads

The former Offline Maps feature has been removed in full. There is no side-panel tab, region selection, draw mode, size estimate, download progress, cancellation, saved-region list, Show overlay or Delete action, and no `offline-regions` store. The worker also no longer listens for a `DELETE_URLS` message: nothing in the app requests a per-URL purge. Map caching is entirely opportunistic — it follows the map resources the user's normal browsing requests.

## Known limitations

- **Only viewed areas are cached.** Offline map coverage cannot be chosen in advance; it is whatever the user happened to fetch while online.
- **No estimates or progress.** There is no tile-count, byte-size, quota or completion UI, and no warning when a pan crosses into uncached coverage.
- **Eviction is browser-controlled.** The app cannot pin map data, and the browser may reclaim it under storage pressure.
- **A first connection is required** to load the app and populate any cache.
- **Upstream URL churn leaves stale entries.** A changed tile template or dated TileJSON slug can strand cached responses that the current style no longer requests.
- **No individual purge.** Clearing map coverage requires a cache-name bump or **Reset app data**; stale URLs are not deleted individually.
- **The allowlist bounds coverage.** Map resources served from hosts outside the allowlist are not cached at all.
