# Tracks — versioned route, recording and waypoint model

> The canonical `v: 2` document model shared by Routes and Recordings: shape,
> conventions, import/export behaviour, migration and caveats.

The track model lives in [`src/utils/track/`](../src/utils/track/). It is the
single stored representation for imported routes, saved GPS recordings and
waypoint-only documents. GPX and GeoJSON are import/export formats around that
model — GeoJSON is also the transient render projection used by `useGeoJSON` —
never the source of truth.

## Document shape

```js
{
  v: 2,
  id: "m1abc2d-x9k2p1q7",
  kind: "route",              // "route" | "recording" | "waypoints"
  name: "Morning Loop",       // string or null
  gpxType: "trk",             // "trk" | "rte" | null
  createdAt: 1760000000000,   // epoch ms or null
  source: {
    format: "gpx",            // "gpx" | "geojson" | "gps" | "legacy"
    filename: "morning.gpx",  // optional
    groupId: "m1abc2d-...",   // documents imported from one file share this
    index: 0,                 // document index within the import
  },
  segments: [
    {
      points: [
        { lat: 48.949011, lng: -55.652574, ele: 42, t: 1760000000000 },
      ],
    },
  ],
  waypoints: [
    {
      lat: 48.95,
      lng: -55.65,
      ele: 40,
      t: 1760000000000,
      name: "Camp",
      desc: "Night stop",
      cmt: "Note",
      sym: "Flag",
      type: "Stop",
      links: [{ href: "https://example.com", text: "Details" }],
    },
  ],
  color: "#3498db",
  duration: 5400000,           // recordings only, milliseconds
}
```

| Field       | Notes                                                                                                                                 |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `v`         | Always `2` for the current model. Migration passes v2 documents through unchanged.                                                    |
| `kind`      | `route` also covers imported lines that originate as GPX routes; `waypoints` holds no line segments.                                  |
| `name`      | Trimmed string or `null`. Import falls back to the filename stem; the UI and download filename use translated or generated fallbacks. |
| `gpxType`   | Source element type. `null` for recordings and waypoint-only documents.                                                               |
| `createdAt` | Epoch milliseconds or `null`; for recordings this is the start time.                                                                  |
| `source`    | Import provenance. `filename` and `groupId`/`index` are absent for GPS captures and legacy migration.                                 |
| `segments`  | Line continuity. Each segment is independent; an empty array is valid for waypoint-only documents.                                    |
| `waypoints` | Standalone points. Never counted as part of the line or its distance.                                                                 |
| `color`     | Presentation colour assigned by [`assignTrackColors`](../src/utils/track/colors.js#L32); not user data.                               |
| `duration`  | Saved recording duration in milliseconds. Omitted for routes and waypoint-only documents.                                             |

### Points

```js
{ lat, lng, ele?, t? }
```

- `lat` and `lng` are decimal degrees (WGS 84) and are required.
- `ele` is metres above sea level.
- `t` is epoch milliseconds.
- When unknown, `ele` and `t` are omitted — never written as `null` or an empty
  string. A genuine `0` elevation or timestamp is kept.

### Waypoints

A waypoint is a point document, not a member of a line segment. It carries the
same `lat`/`lng`/`ele`/`t` fields plus optional `name`, `desc`, `cmt`, `sym`,
`type` and `links` metadata.

Import attaches waypoints to the line document when a file contains exactly one
line. If it contains several lines, the waypoints become a sibling
`kind: "waypoints"` document so they are not silently duplicated onto one line.
A file with no lines produces a single waypoint-only document.

## Conventions

### Elevation

[`normaliseElevation`](../src/utils/track/model.js#L159) keeps finite values,
including `0`, and discards the common GPS sentinels `-9999`, `-19999` and
`-32768`. A missing or discarded elevation is omitted.

### Time

[`normaliseTime`](../src/utils/track/model.js#L167) accepts a `Date`, an ISO
string, or a number:

- numbers below `1e11` are treated as Unix seconds and multiplied by 1000;
- larger numbers are treated as epoch milliseconds;
- unparseable or empty values are omitted.

### Coordinates

[`normalisePoint`](../src/utils/track/model.js#L192) drops points whose
coordinates are non-finite or outside latitude ±90 / longitude ±180. A line
segment therefore keeps only valid points, and a segment with fewer than two
points is not rendered as a line.

### Distance

[`documentDistance`](../src/utils/track/model.js#L88) sums the haversine length
of each segment independently. It never joins the end of one segment to the
start of the next, and waypoints are excluded. Distance is always derived —
legacy documents that stored a `distance` value drop it during migration.

### Bounds

[`documentBounds`](../src/utils/track/model.js#L97) covers every segment point
and every waypoint, returning `[[minLng, minLat], [maxLng, maxLat]]` or `null`
for an empty document. Features fit the map to these bounds with 40 px padding.

### Navigation status

[`nearestPointOnTrack`](../src/utils/track/navigation.js#L37) returns the
closest point on a document to a user position, with its sphere-corrected
distance and bearing. Each segment is projected into a local plane around the
user; segments are never joined across gaps, and invalid points are skipped.
[`ON_ROUTE_METRES`](../src/utils/track/navigation.js#L8) is the 5 m tolerance
within which the position counts as on route. Routes uses both for its
top-centre navigation status and its off-route connector; the screen-space line
from the locate marker to the nearest route point is built with
[`geodesicLine`](../src/utils/track/navigation.js#L56) (see
[Routes — Navigation](./11.routes.md#navigation)).

## Import

[`parseTrackFile`](../src/utils/track/import.js#L568) reads a `File`/`Blob`,
rejects files over `MAX_TRACK_FILE_BYTES` (10 MB), and detects the format from
content rather than extension: a trimmed document starting with `<` is treated
as GPX, `{` as GeoJSON. Anything else raises `unsupported-format`.

### GPX

[`parseGPX`](../src/utils/track/import.js#L461) parses with
[`@tmcw/togeojson`](https://github.com/placemark/togeojson) and falls back to a
small `localName`-based reader when the library returns no features. The
fallback handles prefixed GPX documents such as `<gpx:gpx>`.

| GPX input                             | Result                                                                |
| ------------------------------------- | --------------------------------------------------------------------- |
| `<trk>` with one or more `<trkseg>`   | One `kind: "route"` document; each `<trkseg>` becomes a segment       |
| `<rte>` with `<rtept>`                | One `kind: "route"` document with `gpxType: "rte"`                    |
| `<wpt>` with `<trk>`/`<rte>`          | Attached to the single line document, or a sibling waypoints document |
| `<wpt>` only                          | One `kind: "waypoints"` document                                      |
| `<ele>`                               | Metres; sentinel elevations discarded                                 |
| `<time>`                              | Epoch milliseconds on the point                                       |
| `<name>`, `<desc>`, `<cmt>`, `<type>` | Preserved on the document or waypoint                                 |
| `<sym>`                               | Preserved on waypoints                                                |

A line document needs at least one segment with two usable points. Unnamed
lines fall back to the file stem; when a file yields several unnamed lines they
are numbered (`stem 1`, `stem 2`, …). Imports from one file share a `source`
`groupId` and carry increasing `source.index` values.

### GeoJSON

[`parseGeoJSON`](../src/utils/track/import.js#L515) accepts a
`FeatureCollection`, a single `Feature`, or a bare supported geometry.

| GeoJSON input                           | Result                                                                      |
| --------------------------------------- | --------------------------------------------------------------------------- |
| `LineString` / `MultiLineString`        | A `kind: "route"` document; each line string becomes a segment              |
| `Point` / `MultiPoint`                  | Waypoints                                                                   |
| Third coordinate ordinate               | Elevation in metres                                                         |
| `coordinateProperties.times` or `times` | Per-point times, flat or nested per segment                                 |
| `properties.time`                       | Waypoint/MultiPoint time; also the line document's `createdAt` when present |
| `properties._gpxType` / `gpxType`       | `"rte"` sets `gpxType: "rte"`; otherwise `"trk"`                            |

Times are applied only when their count matches the points exactly; a short or
misaligned list is dropped rather than shifting timestamps onto the wrong
points.

Unsupported geometry types (`Polygon`, `MultiPolygon`, and anything else) make
the file invalid — they are rejected, not skipped. In a collection, features with
`null` geometry are ignored. Feature IDs are kept when unique; duplicate or
missing IDs are replaced with generated ones.

> [!NOTE]
> Imported GeoJSON always becomes a route or waypoint document. Recordings are
> only created by the GPS capture flow; there is no GeoJSON recording import.

### Import errors

Parsing and size failures use [`TrackImportError`](../src/utils/track/import.js#L9)
with a stable `code`; the panel translates it and never shows the raw message.

| Code                     | Meaning                                           |
| ------------------------ | ------------------------------------------------- |
| `invalid-gpx`            | Malformed XML, non-GPX root, or unreadable GPX    |
| `invalid-geojson`        | Invalid JSON, array root, or unsupported geometry |
| `unsupported-format`     | Content is neither GPX nor GeoJSON                |
| `no-importable-features` | Nothing usable remained after validation          |
| `file-too-large`         | File exceeds the 10 MB import limit               |

See [Locale — Message codes and sentinel errors](./7.locale.md#message-codes-and-sentinel-errors)
for the `panel.routes.*` mappings.

## Export

Both export paths are pure projections of the v2 document. Sharing goes through
[`shareFile`](../src/utils/share.js), which uses the Web Share API when the
browser can share files and otherwise downloads the generated file.

### GPX

[`toGPX`](../src/utils/track/export.js#L104) writes a GPX 1.1 document with
`creator="ogis.app"`. Output is schema-ordered and XML-escaped.

- Waypoints are written first as `<wpt>`, in the order `ele`, `time`, `name`,
  `cmt`, `desc`, `sym`, `type`.
- A single-segment document with `gpxType: "rte"` is written as `<rte>` /
  `<rtept>`. Everything else is written as `<trk>` / `<trkseg>` / `<trkpt>`.
- Multiple segments produce multiple `<trkseg>` elements.
- A waypoint-only document writes `<wpt>` elements and no line element.
- Times are ISO 8601 strings; elevation is written only when present.

### GeoJSON

[`toGeoJSON`](../src/utils/track/export.js#L168) returns a `FeatureCollection`:

- the line is a `LineString` for one usable segment, or `MultiLineString` for
  several;
- elevation is the third coordinate ordinate;
- per-point times are written to `properties.coordinateProperties.times` as ISO
  strings, flat for one segment and nested for several — only when **every**
  point in the exported segments has a time;
- each waypoint becomes a `Point` feature with its metadata and `properties.time`;
- `properties._gpxType` records the source type;
- no `ogis.*` style properties are exported.

GeoJSON is intentionally transient for tracks: the app stores v2 documents and
projects them to GeoJSON only to render or export. Style properties such as
`ogis.color` and `ogis.direction` belong to the map layer, not the model.

## Round-trip caveats

The writer and parser cover the subset used by the app. They are **not** full
GPX 1.1 implementations and round trips are not guaranteed to be lossless.

- **GPX extensions and line metadata are dropped.** Track/route links, `<number>`,
  `<src>` and extensions (heart rate, cadence, power, etc.) are not imported or
  exported. Waypoint `links` are imported and exported to GeoJSON, but the GPX
  writer does not emit `<link>` elements.
- **A multi-segment route exports as a track.** `gpxType: "rte"` is only
  preserved on export when the document has at most one segment; multiple
  segments force `<trk>` / `<trkseg>`.
- **Waypoints can change documents.** A file with several lines imports its
  waypoints as a separate `kind: "waypoints"` document. Each document is shared
  separately, so combining them again is a manual step.
- **GeoJSON identifiers and styles are not round-tripped.** Exported GeoJSON has
  no feature IDs and no `ogis.*` properties, so re-importing generates new IDs
  and assignment colours. Unrelated source properties are discarded.
- **GeoJSON times are all-or-nothing.** Export omits coordinate times if any
  point in the exported segments lacks one; import drops a times list whose
  length does not match the points.
- **Unsupported GeoJSON geometry rejects the whole file.** A polygon mixed into
  a feature collection is an import error, not a skipped feature.
- **Name fallbacks can change.** An unnamed document takes the file stem, and
  numbered suffixes are added when one file yields several unnamed lines.
- **Sentinel and invalid values are lost by design.** Invalid coordinates,
  sentinel elevations and unparseable times are removed on import and cannot be
  restored on export.

## Migration and storage

Storage keys are unchanged from the legacy shapes:

```
ogis_routes_{instanceId}
ogis_recordings_{instanceId}
```

Migration is lazy, on feature install, and idempotent — a document already at
`v: 2` is returned unchanged.

| Legacy shape                                          | Migration                                                                                                                                           |
| ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Route `{ id, name, type, points }`                    | [`migrateRoute`](../src/utils/track/model.js#L31): `type: "rte"` becomes `gpxType: "rte"`, points become one segment, `source.format` is `"legacy"` |
| Saved recording `{ id, timestamp, points, duration }` | [`migrateRecording`](../src/utils/track/model.js#L48): `timestamp` becomes `createdAt`, points become one segment, `duration` is kept               |
| Active recording `{ points, startTime }`              | [`migrateActiveRecording`](../src/utils/track/model.js#L66): `startTime` becomes `createdAt`, points become one segment                             |

Legacy `distance` values are discarded because distance is now computed from
the geometry, per segment. Migration does not rewrite the storage key and does
not require the user to re-import anything; the first read after upgrade
persists the v2 shape through the normal storage binding.

Colours are assigned once with [`assignTrackColors`](../src/utils/track/colors.js#L32),
which prefers an unused palette colour and otherwise derives a stable colour
from the document ID.

## Feature integration

Routes and Recordings both consume the model through
[`src/utils/track/index.js`](../src/utils/track/index.js):

- builds line geometry with `lineGeometry` (one usable segment becomes a
  `LineString`, several become a `MultiLineString`);
- computes row distance with `documentDistance` and waypoint counts with
  `waypointCount`;
- fits bounds with `documentBounds`;
- locates the nearest point on a line with `nearestPointOnTrack` and applies the
  `ON_ROUTE_METRES` tolerance for navigation status;
- assigns colours with `assignTrackColors`;
- shares documents with `toGPX` / `toGeoJSON` and `trackFilename` /
  `trackMime`.

Both features set `ogis.direction: true` on their line features, so point order
drives the direction chevrons rendered by `useGeoJSON` (see
[GeoJSON — Direction chevrons](./6.geojson.md#direction-chevrons)). Timestamps
and bearing data are not used for direction.

See [Routes](./11.routes.md) for the import, visibility, sharing and navigation
UI, and [Features — Recordings](./10.features.md#recordings--worked-example) for
the recording flow.

## Current limitations

- **No track editing.** There is no point reordering, trimming, merging or
  per-point editing in the UI.
- **GPX subset only.** Extensions and several optional GPX elements are not
  modelled, as described in [Round-trip caveats](#round-trip-caveats).
- **No lossless round trips.** Exporting and re-importing normalises IDs,
  colours, metadata and document grouping.
- **GeoJSON is not a storage format.** Only the v2 document is persisted;
  render/export GeoJSON is regenerated on demand.
- **10 MB import cap.** Larger files are rejected before parsing.
- **localStorage quota.** Documents are stored as-is; very large tracks may not
  fit in the origin quota.
- **Visibility is session-only.** Route and recording Show/Hide state is held in
  memory and is not persisted; imported routes start hidden, and both routes and
  saved recordings start hidden after a reload.
- **No elevation or speed analytics.** Elevation and timestamps are retained in
  the model, but there is no profile, gain or pace view.
- **Separate documents share separately.** A multi-document import exports one
  file per row rather than recreating the original combined file.
