# Instances

How ogis.app handles instance isolation and storage scoping.

---

## One Instance Per Page

The normal deployment is a single Vue app mounted to `#app`. There is one instance per JS context — one browser tab, one iframe.

The `instanceId` (injected as `ogisAppId`) defaults to `'app'` and is only overridden via the `?id=` URL parameter for iframe embedding.

---

## Storage Key Format

Persisted state follows this key format in the storage area selected by the store definition (production stores use `localStorage`):

```
ogis_{namespace}_{instanceId}
```

| Key                         | Namespace          | Area  | Version | Purpose                                              | Cross-tab |
| --------------------------- | ------------------ | ----- | ------- | ---------------------------------------------------- | --------- |
| `ogis_view_app`             | `view`             | local | 1       | Map centre, zoom, pitch and bearing                  | Yes       |
| `ogis_recordings_app`       | `recordings`       | local | 2       | Saved recordings                                     | Yes       |
| `ogis_recording-active_app` | `recording-active` | local | 2       | Interrupted active recording and its owner           | No        |
| `ogis_routes_app`           | `routes`           | local | 1       | Imported route and waypoint documents                | Yes       |
| `ogis_offline-regions_app`  | `offline-regions`  | local | 1       | Downloaded offline region metadata                   | Yes       |
| `ogis_locate_app`           | `locate`           | local | 3       | Permission flag, restorable mode, last fix and owner | No        |
| `ogis_navigation_app`       | `navigation`       | local | 2       | Route visibility, navigation ownership and owner     | No        |
| `ogis_sync_app`             | `sync`             | local | 1       | Dormant backend sync queue                           | No        |

> [!NOTE]
> Every production state namespace above uses `localStorage`. `sessionStorage` holds only the per-tab identity `ogis_session-tab`, used by the durable tab-owned stores, plus any legacy values awaiting the one-time migration. The tab identity survives a reload but is new after an app quit; the stores themselves do not depend on it for durability. See [State and resilience — Durable tab-owned sessions](./16.state-and-resilience.md#durable-tab-owned-sessions).

The `routes` namespace holds an array of versioned `v: 2` track documents; the saved `recordings` namespace holds an object whose `saved` array contains them. Their shape and migration are described in [Tracks](./15.tracks.md). The `navigation` and `locate` schemas are covered in [State and resilience](./16.state-and-resilience.md).

Each value is written as a versioned envelope:

```json
{ "__ogisState": 1, "version": 1, "data": { "mapView": {} } }
```

A bare legacy value is read as version 0. An invalid value falls back to defaults and its raw contents are kept at `ogis_quarantine_{namespace}_{instanceId}` for debugging. The `instanceId` is always last, so both store keys and quarantine keys are easy to identify in browser DevTools.

The `view` store syncs the camera across tabs without an echo write. The shared content stores also sync live: `routes` and `offline-regions` are arrays, while saved `recordings` is an object whose `saved` array holds the documents. Another tab's add, update or removal replaces the shared array contents or the object's properties wholesale, and each feature reconciles its rows and map layers in response. The active recording is not shared: it lives in the durable `recording-active` local store. Shared content is last-writer-wins, with no merge. `locate`, `navigation` and `recording-active` are durable but tab-owned: each value carries an `ownerId`, and a liveness probe over a per-instance `BroadcastChannel` stops a second live tab from restoring or clearing another tab's session. They never opt in to cross-tab sync. The dormant `sync` queue remains shared content without live cross-tab sync. Values written to `sessionStorage` by earlier versions are copied into `localStorage` once at boot and removed from session storage; legacy `ogis_recordings` active documents move into the local active store. The full persisted-state contract — hydration, debounce, flush, reset, quota handling, durable sessions and the liveness probe — is in [State and resilience](./16.state-and-resilience.md#persisted-state); see also [Known integration gaps](./16.state-and-resilience.md#known-integration-gaps).

Restore is deliberately partial: locate sessions, an interrupted active recording and route visibility/navigation restore after a reload or app quit where permission and stored data allow, while UI/panel state, map projection, theme, units, locale and recording visibility do not. A second live tab does not restore or clear a session owned by another tab. The authoritative list, including hard-kill storage durability, is in [State and resilience — Limitations and deliberate exclusions](./16.state-and-resilience.md#limitations-and-deliberate-exclusions).

## `usePersistedState(namespace, definition, instanceId?)`

[`usePersistedState`](../src/resilience/persistedState.js) creates a reactive store that reads and writes through the versioned envelope:

```js
import { usePersistedState } from "@/resilience/persistedState.js";

const { state, flush, reset } = usePersistedState("my-feature", {
  version: 1,
  defaults: { enabled: false },
  hydrate: hydrateMyFeature,
});
```

The definition carries `version`, `defaults`, an optional `hydrate` and any of `storage`, `crossTab`, `debounce` and `onSync`. `state` is reactive, `flush()` writes immediately and `reset()` removes the key and restores defaults. Details and the full definition table are in [State and resilience — Persisted state](./16.state-and-resilience.md#persisted-state).

When called outside a component (e.g. in `src/main.js`), pass the `instanceId` explicitly:

```js
const store = usePersistedState(
  "recordings",
  { version: 2, defaults: { saved: [] } },
  instanceId,
);
```

Features receive the same facility through `featureCtx.useStorage(namespace, definition)` and read `.state`; there is no separate `useStorage` composable. See [Features — Persistence and restore](./10.features.md#persistence-and-restore).

`resetInstanceState(instanceId)` removes the current instance's keys from both `localStorage` and `sessionStorage`, including quarantine copies. It matches only the app's known store namespaces (`view`, `recordings`, `routes`, `offline-regions`, `locate`, `navigation`, `recording-active`, `sync`) with an exact `ogis_{namespace}_{instanceId}` or `ogis_quarantine_{namespace}_{instanceId}` comparison. This keeps a suffix-colliding instance untouched — resetting `app` does not remove `ogis_view_trip_app`, which belongs to `trip_app` — and other instances are left alone. The boot fallback's **Reset app data** action applies the same namespace-aware cleanup to both storage areas without importing the app, and additionally unregisters service workers and deletes `ogis-*` caches.

## iframe Isolation

When the app is embedded in an `<iframe>`, each iframe is a separate JS context with its own module instances and its own `sessionStorage`. The `?id=` URL parameter ensures their storage keys are distinct:

```
iframe A (?id=map-a): ogis_view_map-a
iframe B (?id=map-b): ogis_view_map-b
```

Without different IDs the two iframes would overwrite each other's saved view.
