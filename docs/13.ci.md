# CI — tests, releases and deployment

GitHub Actions runs the test suites, validates commit messages, cuts releases with semantic-release, and deploys to GitHub Pages.

---

## Two workflows

| Workflow                                                  | Role                                           | Pull request             | Push to `master`                                                  | `workflow_dispatch`     |
| --------------------------------------------------------- | ---------------------------------------------- | ------------------------ | ----------------------------------------------------------------- | ----------------------- |
| [`ci.yml`](../.github/workflows/ci.yml)                   | The fast gate                                  | `unit`, `e2e`, `commits` | `unit`, `e2e`, `commits`, then `release`, `deploy`                | —                       |
| [`screenshots.yml`](../.github/workflows/screenshots.yml) | The visual authority for the screenshot matrix | `screenshots`, `verify`  | `screenshots`, `verify`, then `refresh` on a verification failure | `screenshots`, `verify` |

**`ci.yml`** is the fast gate; **`screenshots.yml`** is the visual authority. The single required branch-protection check is the aggregate **`Screenshots — verify committed matrix`** job from `screenshots.yml` — not the `screenshots` shard job (see [why](#screenshot-matrix-workflow)).

### Runner setup

Both workflows share the same runner conventions:

- Node 24 is pinned in every job via `actions/setup-node` with the npm cache; every job that installs dependencies uses `npm ci`.
- The `e2e` job installs Chromium with `npx playwright install --with-deps chromium`; the `screenshots` capture shards install the plain `chromium` build.
- Job timeouts are explicit where they matter: 30 minutes per `e2e` shard, 180 minutes per `screenshots` capture shard, 10 minutes for the aggregate `verify`.
- Concurrency: `ci.yml` groups per ref (`ci-${{ github.ref }}`) and cancels in-progress runs for pull requests only; `screenshots.yml` uses its own per-ref group (`screenshots-${{ github.ref }}`) with the same PR-only cancellation. `deploy` has its own `pages` group with `cancel-in-progress: false`, so a deployment is never cut off mid-flight.
- The `e2e` job splits the functional suite across three shards — a quick gate, with Playwright running serially within each shard (`workers: 1` via the deterministic path). The `screenshots` workflow captures across six shards because each macOS capture is slow under the deterministic single-thread SwiftShader pin, and parallel shards keep the wall-clock time down.

## ci.yml — triggers and jobs

`unit`, `e2e` and `commits` run in parallel on every push and pull request. `release` and `deploy` follow only on `master` pushes; `release` requires `unit` and `commits` to pass and accepts `e2e` only as `success` or `skipped`. A push can skip the functional shards with the [skip marker](#skipping-the-e2e-shards).

```mermaid
flowchart TD
    push([push to master]) --> unit
    push --> e2e["e2e (3 shards, functional)"]
    push --> commits["commits (message check)"]
    pr([pull request]) --> unit
    pr --> e2e
    pr --> commits
    unit -->|passed| release["release (master only)"]
    e2e -->|success or skipped| release
    commits -->|passed| release
    release -->|released| deploy["deploy (GitHub Pages)"]
```

| Job       | Runs on                                                                | What it does                                                                                                                                                                                                             |
| --------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `unit`    | Every push and PR                                                      | `npm ci`, a Prettier format check (`npm run format:check`), then `npm test` (Vitest) with `CI=1`                                                                                                                         |
| `e2e`     | Every push and PR (skippable on push)                                  | Installs Chromium (`--with-deps`), runs the functional suite as a 3-shard matrix (`--grep-invert @screenshots --shard=N/3`, `CI=1`), uploads per-shard `playwright-report/` even on failure. 30-minute timeout per shard |
| `commits` | Every push and PR                                                      | Runs `node .github/scripts/checkCommits.mjs` over the push/PR range: every non-merge subject must follow Conventional Commits; needs only `git` and Node                                                                 |
| `release` | `master` pushes; `unit` and `commits` passed, `e2e` success or skipped | `npx semantic-release` with `GITHUB_TOKEN`; exposes `released` and `sha` outputs (the latter only on an actual release)                                                                                                  |
| `deploy`  | Only when `released == true`                                           | Checks out the released `sha`, builds `dist/`, uploads the Pages artefact and deploys to GitHub Pages                                                                                                                    |

- The `e2e` job is a three-shard matrix with `fail-fast: false`; each shard runs `npm run test:e2e -- --grep-invert @screenshots --shard=N/3` with `CI=1`, so CI uses SwiftShader software rendering and two retries. Because `CI=1` selects the deterministic path, the job also runs as a single worker under the single-thread SwiftShader pin (see [Testing — E2E rendering modes](./9.testing.md#e2e-rendering-modes)). The `@screenshots` matrix specs are excluded from `ci.yml` and verified instead by the separate [`screenshots.yml`](#screenshot-matrix-workflow) workflow. Each shard has a 30-minute timeout.
- The `e2e` job has no live map-asset dependency: the shared test fixture serves the MapLibre style, sprites and glyphs from the committed fixtures under `tests/fixtures/map/`, unvendored tiles/glyphs default to an instant empty 200, and the context-level stub blocks any other external request, so no shard fetches a live map origin. Refreshing those fixtures (`npm run fixtures:refresh`) is a manual local step and deliberately not part of CI — see [Testing — Map-asset fixtures](./9.testing.md#map-asset-fixtures).
- The `commits` job checks every message in the run's range: [`.github/scripts/checkCommits.mjs`](../.github/scripts/checkCommits.mjs) reads `BEFORE..AFTER` (the PR base for pull requests, the previous tip for pushes) and validates each non-merge subject, allowing the types tabled in [Conventional commits are required](#conventional-commits-are-required) — the same list as the checker's exported `ALLOWED_TYPES` — plus `revert`; git-native `Revert "…"` subjects are exempt. It uses only `git` and the Node standard library — nothing to install — and its `success` is a hard gate on `release`.
- Default workflow permissions are `contents: read`. `release` escalates to `contents: write`, `issues: write` and `pull-requests: write`; `deploy` needs `pages: write` and `id-token: write`.
- A push can skip the three functional shards with a marker in its head commit message — see [Skipping the e2e shards](#skipping-the-e2e-shards).
- `deploy` checks out the released commit — `needs.release.outputs.sha`, not `master` — so a mid-run push to `master` cannot leak unreleased commits into the build, then passes `VITE_API_BASE_URL` from the repository's Actions variables into `npm run build`.

> [!NOTE]
> Why the fast `ci.yml` gate excludes the screenshot matrix: GitHub runners render with SwiftShader, where captures are far slower than local GPU rendering, so running the matrix inline would consume a disproportionate amount of runner CPU. The matrix is verified instead by the separate [`screenshots.yml`](#screenshot-matrix-workflow) workflow, which reproduces the committed matrix in its macOS capture shards within a strict pixel tolerance and aggregates the check on Linux. Local verification stays relative and visual (see [Testing — Screenshot diff loop](./9.testing.md#screenshot-diff-loop)); committed-matrix re-baselining is sourced from this workflow's captures (see [Testing — CI-sourced re-baseline](./9.testing.md#ci-sourced-re-baseline)).

### Screenshot matrix workflow

[`.github/workflows/screenshots.yml`](../.github/workflows/screenshots.yml) is the deterministic authority for the committed screenshot matrix. It runs on pull requests, `master` pushes and `workflow_dispatch`, and has three jobs: the capture shards, an aggregate `verify` gate, and a `refresh` job that self-heals the baseline on `master` pushes.

- **`screenshots`** (capture) — a six-shard matrix on `macos-15` (`npx playwright test --project=screenshots --shard=N/6`), 180-minute timeout per shard.
  - Captures run with `CI=1` and no overrides, so `isDeterministicRun()` applies the single-thread SwiftShader pin and one worker, and `ui-states.spec.js` writes to the gitignored `.opencode/tmp/screenshots/` — never the committed tree.
  - Each shard then verifies every captured PNG against the committed `screenshots/` set with [`scripts/verify-matrix.js`](../scripts/verify-matrix.js), which compares decoded pixels rather than bytes: a file passes when every differing channel is within `--max-delta` (default 1) and it differs in at most `--max-pixels` pixels (default 64). It fails on a real change, a missing baseline, a dimension mismatch or zero captures, and lists the tolerated drift. It never rewrites the committed PNGs.
  - Each shard uploads `screenshots-shard-N` (the captures plus its verification report) with `if: always()`, retained for 7 days.
- **`verify`** (aggregate) — `needs: screenshots`, `if: always()`, `ubuntu-latest`, 10-minute timeout. It downloads every shard's captures (`pattern: screenshots-shard-*`, `merge-multiple: true`) and verifies the **full** committed matrix in both directions with `--mode full`: every committed PNG must have been captured within tolerance, and every captured matrix PNG must exist in the committed set (`diag/**` excluded). It writes and uploads a verification report.
- **`refresh`** (master auto-refresh) — `needs: [screenshots, verify]`, `if: always() && github.event_name == 'push' && github.ref == 'refs/heads/master' && needs.verify.result == 'failure'`, `ubuntu-latest`, 15-minute timeout, `contents: write` plus `actions: write`. It runs only when a `master` push genuinely moves the matrix — the tolerant aggregate verification FAILED — so it never fires on sub-tolerance drift, on a pull request or on `workflow_dispatch`. It re-downloads the same run's `screenshots-shard-*` captures and rebuilds the committed baseline with `npm run screenshots:fetch -- --artifacts captured --write`, which keeps every guard: all six shards present, a superset of the committed set (no removals), and valid PNGs. A partial or empty capture set fails the job with no commit and no fallback writes, leaving the run red for a human. When there is a change, it commits as `github-actions[bot]` (`test(e2e): refresh screenshot matrix from run <id>`), `git pull --rebase` + pushes to `master`, then dispatches a fresh run to re-verify (a `workflow_dispatch` is an allowed exception to the `GITHUB_TOKEN` recursion rule). A re-run that finds nothing to commit skips both the commit and the dispatch.

Only the capture shards need macOS: Linux (`ubuntu-latest`) substitutes fonts (panel copy wraps) and rasterises differently, so it cannot reproduce the macOS-captured matrix, whereas the aggregate `verify` job only decodes and compares pixels.

A run after an intentional capture move fails verification by design: the shards capture the new matrix, and the comparison reports exactly which captures differ from the old committed set. On a `master` push the `refresh` job then re-baselines automatically from that run's own captures and dispatches a re-verification, so the developer's side is just `git pull`. Manual fetching is the **exception** path — a pull request (where a red verify is a review signal and nothing is auto-committed), or a run whose capture set was failed or incomplete so `refresh` could not bless it: `npm run screenshots:fetch -- --run <run-id>` downloads and assembles the shard artefacts and compares them against the committed tree (read-only), and adding `--write` updates `screenshots/`. Review and commit the result; the next run verifies green. See [Testing — CI-sourced re-baseline](./9.testing.md#ci-sourced-re-baseline).

> [!IMPORTANT]
> The aggregate `verify` job — **`Screenshots — verify committed matrix`** — is the single, stable **required** check in branch protection, not the `screenshots` shard job. A shard can emit only some of its assigned captures and still pass its own per-shard step; the aggregate job sees the merged captures across every shard and closes that gap.

### Skipping the e2e shards

A push whose **head commit message** contains the marker `[skip e2e]` skips all three functional shards — useful for docs- or metadata-only changes. The match is case-insensitive and covers the whole message (subject and body); it applies to pushes only, so pull requests always run `e2e`. `unit` and `commits` still run, and `release` proceeds on a deliberate skip. The gate accepts only `e2e` `success` or `skipped`: any other `needs.e2e.result` — a failed shard, or a cancelled one — blocks both `release` and `deploy`. A single cancelled matrix shard is enough; the job-level `!cancelled()` covers only cancellation of the whole workflow run, so `release` also never runs on a cancelled workflow.

> [!WARNING]
> Any commit message containing the marker string triggers the skip — including one that merely quotes it. Paraphrase it when writing commit messages; the literal text is only safe in tracked files such as this document, because only commit messages are matched.

### Why release and deploy share one workflow

`GITHUB_TOKEN`-created pushes do not trigger further workflows. semantic-release pushes a version commit and a tag back to `master`; a separate deploy workflow listening for that push would never run. Keeping release and deploy in the same run side-steps this. The release commit message also carries `[skip ci]`, so that push does not re-trigger CI.

## Artefacts

Each of the three `e2e` shards uploads its own artefact — `e2e-artefacts-shard-1`, `e2e-artefacts-shard-2` and `e2e-artefacts-shard-3` — with `if: always()` so they are available for failed runs too. Each contains:

| Path                 | Contents                                       |
| -------------------- | ---------------------------------------------- |
| `playwright-report/` | The HTML report — first stop for a red e2e run |

Download the relevant shard from the **Artifacts** section of a workflow run. Retention is 14 days. `if-no-files-found: ignore` means a run that produced no report does not fail the upload step.

> [!NOTE]
> The screenshot matrix is not part of `ci.yml`; it is verified by the separate [`screenshots.yml`](#screenshot-matrix-workflow) workflow. The committed PNGs under `screenshots/` are re-baselined from that workflow's own captures — automatically by the `refresh` job on a `master` push — with `npm run screenshots:fetch -- --write` as the manual exception path; see [Testing — Screenshots](./9.testing.md#screenshots).

## Conventional commits are required

All commit messages must follow the [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) specification — semantic-release parses them to decide the next version and build the release notes, and a message that does not parse is invisible to that process. The `commits` job enforces the format on every push and PR: it validates each non-merge commit subject and fails on anything that does not parse, blocking `release` and therefore `deploy`. Only the subject (first line) is checked; bodies and footers are not validated.

Format: `<type>(optional scope): <description>`

| Type       | Use for                                              | Release impact |
| ---------- | ---------------------------------------------------- | -------------- |
| `feat`     | A new feature                                        | Minor          |
| `fix`      | A bug fix                                            | Patch          |
| `perf`     | A performance improvement                            | Patch          |
| `refactor` | A change that neither fixes a bug nor adds a feature | None           |
| `docs`     | Documentation only                                   | None           |
| `test`     | Tests only                                           | None           |
| `ci`       | CI configuration and scripts                         | None           |
| `chore`    | Maintenance that does not fit the above              | None           |
| `build`    | Build system or dependencies                         | None           |

The checker accepts the types above plus `revert`; git-native `Revert "…"` subjects are exempt from validation entirely.

Breaking changes use `!` after the type/scope (`feat(api)!: …`) or a `BREAKING CHANGE:` footer, and trigger a major release.

```
feat(offline): add region drawer
fix(sw): purge dev caches on startup
docs(testing): describe the screenshot matrix
ci: upload e2e artefacts
feat(locate)!: rename the locate API

BREAKING CHANGE: locate events now emit { position } instead of { lat, lng }.
```

## Releases with semantic-release

[`.releaserc.json`](../.releaserc.json) configures semantic-release on the `master` branch:

| Plugin                                      | Purpose                                                                                                              |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `@semantic-release/commit-analyzer`         | Determines the release type from commit messages                                                                     |
| `@semantic-release/release-notes-generator` | Builds the release notes                                                                                             |
| `@semantic-release/changelog`               | Writes `CHANGELOG.md`                                                                                                |
| `@semantic-release/npm`                     | Bumps `package.json` / `package-lock.json` (`npmPublish: false` — nothing is published to npm)                       |
| `@semantic-release/github`                  | Creates the GitHub release and tag                                                                                   |
| `@semantic-release/git`                     | Commits `CHANGELOG.md`, `package.json` and `package-lock.json` back to `master` as `chore(release): X.Y.Z [skip ci]` |

The `release` job snapshots `HEAD` before and after `npx semantic-release`; if it moved, the `released` output is `true`, the new `HEAD` — the version commit carrying the release tag — is captured as the `sha` output, and `deploy` runs. `deploy` checks out that SHA rather than `master`, pinning the build to exactly the released commit so a push landing mid-run cannot leak unreleased commits into the deployment. If no commit since the last tag warrants a release, nothing is released, no `sha` is set and `deploy` is skipped.

> [!NOTE]
> semantic-release resolves the GitHub repository from `repository.url` in [`package.json`](../package.json) — currently `https://github.com/OpenGIS/app.git`. Keep it in sync when the repository is renamed: a stale URL blocks releases.

## Running the same checks locally

Day-to-day local commands — unit tests, single-spec runs, the full E2E suite, formatting and the screenshot loops — are covered in [Testing](./9.testing.md); the [README development workflow](../README.md#development-workflow) presents them in order. The CI-only variants:

```bash
CI=1 npm run test:e2e -- --grep-invert @screenshots --shard=1/3  # exactly how CI runs a functional shard
E2E_SWIFTSHADER=1 npm run test:e2e   # reproduce CI's SwiftShader rendering locally
node .github/scripts/checkCommits.mjs  # validate HEAD's commit subject (CI passes BEFORE/AFTER)
```

- `CI=1` flips the switches in [`playwright.config.js`](../playwright.config.js): `retries: 2`, `forbidOnly`, `reuseExistingServer: false`, SwiftShader rendering and `workers: 1` (via `isDeterministicRun()`), so Playwright starts its own dev server on port 5184. `E2E_SWIFTSHADER=1` selects only the renderer.
- The commit checker defaults to just `HEAD`; set `BEFORE` and `AFTER` to SHAs to validate a range, as CI does.
- Screenshot verification has two modes: `--mode shard` (**the default**) verifies only the files a shard captured, ignoring committed files it did not capture; `--mode full` additionally requires a captured counterpart for every committed PNG. The workflow uses both:

```bash
# per capture shard
npm run screenshots:verify -- --committed screenshots --captured .opencode/tmp/screenshots --mode shard
# aggregate verify job (captures assembled from every shard)
npm run screenshots:verify -- --committed screenshots --captured <assembled> --mode full
```

### Service worker in E2E (`VITE_SW=1`)

The Playwright webServer starts Vite with `VITE_SW: "1"` ([`playwright.config.js:147`](../playwright.config.js#L147)), opting the test app into the app-shell service worker. This keeps the e2e run on the closest dev equivalent to production, and [`tests/e2e/sw.spec.js`](../tests/e2e/sw.spec.js) asserts the worker registers on load and that a reload boots cleanly while it is in control.

A normal `npm run dev` does **not** register the worker — it unregisters any existing one and clears the origin's caches instead, so profiles poisoned by an earlier dev registration self-heal. `VITE_SW=1` is the explicit opt-in. See [Offline — registration and gating](./12.offline.md#registration-and-gating) for the full behaviour and why.
